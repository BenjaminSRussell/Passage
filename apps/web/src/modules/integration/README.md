# integration (web module, PSG-35)

Screens for the edi service (`services/edi/api/openapi.yaml`), wired through `api/client.ts` to `/api/v1/edi/...`.

| Route | Page | Service call |
| --- | --- | --- |
| `/integration/partners` | Trading partners list, environment filter | `GET /partners` |
| `/integration/partners/new` | Create a partner (one `Idempotency-Key` per attempt) | `POST /partners` |
| `/integration/partners/:id` | Profile and its recent interchanges | `GET /partners/{id}`, `GET /interchanges?partnerId=` |
| `/integration/interchanges` | Interchanges, partner, direction (`?direction=OUT`) and 997 status filters | `GET /interchanges` |
| `/integration/interchanges/receive` | Record a pasted X12 interchange (an 850, or a partner 997 that is matched to an outbound document) | `POST /inbound/x12` |
| `/integration/interchanges/outbound` | Send EDI document: 856, 810 or 855 from a canonical JSON document prefilled with an example; shows the generated X12 (`?partnerId=` preselects) | `GET /partners`, `POST /partners/{id}/outbound` |
| `/integration/interchanges/:id` | Transactions with their canonical document (850 order, 856 packs, 810 invoice, 855 lines, 997 answers), the 997 sent or the partner 997 status | `GET /interchanges/{id}` |
| `/integration/interchanges/:id` (inbound with failures) | Reprocess card: Preview (dry run, no key) and Reprocess (one `Idempotency-Key` per attempt), outcome per transaction | `POST /interchanges/{id}:reprocess` |
| `/integration/interchanges/:id` (raw payload card) | Segment tree of the raw payload: ISA, GS, ST levels nested, each element with its X12 reference and dictionary name on hover; "Personal data masked" badge without `EDI_PII_VIEW` | `GET /interchanges/{id}/payload` |
| `/integration/messages` | Message monitor: every transaction newest first with its failing rule; partner, direction, status, set and ISA13 filters (`?status=`, `?direction=`, `?partnerId=`); Load more by cursor | `GET /messages` |
| `/integration/messages` (bulk reprocess card) | Preview (dry run, no key) and Reprocess (one `Idempotency-Key` per attempt) for the failed inbound interchanges in the current list, at most 200; outcome per interchange | `POST /interchanges:reprocess` |
| `/integration/messages/:id` | One message: envelope, failing rule, canonical document (masked badge without `EDI_PII_VIEW`), link to its interchange to reprocess and see the raw payload | `GET /messages/{id}` |
| `/integration/partner-sla` | Partner SLA: transactions, failure rate, 997s back, p95 997 latency, late and overdue acks per partner; 7/30/90/365-day period | `GET /partners/sla` |
| `/integration/edi/map-tester` | Dry-run the 850 map | `POST /maps:test` |
| `/integration/punchout` | Punchout cart check: a cXML PunchOutOrderMessage or OCI `NEW_ITEM-*` fields, allowed currencies, price tolerance, supplier units and reference prices; shows the requisition lines, dropped lines (EDI-0133), the total check (EDI-0134) and the approval flag. Nothing is created | `POST /punchout/returns:parse` |
| `/integration/self-billing` | Self-billing match: shipments and the customer's self-billed lines as JSON (prefilled), as-of date, wait days and tolerances; shows matched, difference and unmatched counts, the line outcomes and unbilled shipments | `POST /self-billing:match` |
| `/integration/peppol` | Peppol invoice: a UBL invoice or credit note as JSON (prefilled); shows the UBL 2.1 XML or the blocking findings (EINV-0110, EINV-0111) | `POST /peppol/invoices:build` |
| `/integration/sync` | Outbound sync: webhook and REST push subscriptions (kind, endpoint, event types, filter, status); New webhook and New REST push need `hub.subscription.write` | `GET /subscriptions` (integration hub) |
| `/integration/sync/new-webhook` | New webhook: name, https endpoint, event types (checked like the hub does), optional CESQL filter (the hub's parse error is shown on the field), optional chosen signing secret; the generated secret is shown once after creation; one `Idempotency-Key` per attempt | `POST /subscriptions` |
| `/integration/sync/new` | New REST push: event types, outbound mapping id, method, endpoint template with `{placeholders}`, legacy key path, 4xx policy, auth (basic, bearer, API key, OAuth2 client credentials; secrets are password fields, sent once, never shown again; one `Idempotency-Key` per attempt) | `POST /subscriptions` |
| `/integration/sync/:id` | Subscription settings (credentials shown only as "stored"), event filter editor (save, remove), Resume after a 410 pause, webhook only: signing secret card (last rotation, previous secret still signing until, Rotate with a grace period in hours behind a confirmation; the new secret is shown once), rest-push only: Test send: render a sample sales.order.confirmed event or also send it once | `GET /subscriptions/{id}`, `PATCH /subscriptions/{id}`, `POST /subscriptions/{id}:resume`, `POST /subscriptions/{id}:rotate`, `POST /subscriptions/{id}:test` |
| `/integration/sync/deliveries` | Delivery monitor: status filter, `?subscriptionId=`, Load more by cursor; attempts, last HTTP status, the ERP's key, next retry | `GET /deliveries` |
| `/integration/sync/dead-letters` | Dead letters with reason (HUB-0115, HUB-0117, HUB-0118) and the ERP's truncated answer; Replay one (needs `hub.subscription.write`), except HUB-0118 (the ERP already holds the record: reconcile it there) | `GET /dead-letters`, `POST /deliveries/{id}:replay` |
| `/integration/clients` | API clients: name, Keycloak client id, scopes, quota, status; Register client needs `hub.client.write` | `GET /clients` (integration hub) |
| `/integration/clients/new` | Register an API client: client id, scopes (one duty per line), requests per minute and burst (defaults 600 and 100), optional sandbox tenant, owner e-mail; one `Idempotency-Key` per attempt | `POST /clients` |
| `/integration/clients/:id` | Settings, quota form (sent with the version last read; a conflict asks to reload), usage of the last hour per minute (admitted and refused with 429), Revoke with a confirmation | `GET /clients/{id}`, `PATCH /clients/{id}`, `POST /clients/{id}:revoke`, `GET /clients/{id}/usage` |
| `/integration/catalog` | API catalog: published API and event contracts with owner, version, lifecycle and sunset; filters for kind, lifecycle and text; Publish needs `hub.catalog.write` | `GET /catalog` (integration hub) |
| `/integration/catalog/new` | Publish a contract: kind, name, version (MAJOR.MINOR.PATCH, equal to the document's `info.version`), title, owner service and the OpenAPI or AsyncAPI document as JSON (pasted or loaded from a file); one `Idempotency-Key` per attempt | `POST /catalog` |
| `/integration/catalog/:id` | Contract, operations, documentation gaps, the published document on demand, Deprecate with a sunset date at least 12 months ahead, Retire (after the sunset date) with a confirmation | `GET /catalog/{id}`, `GET /catalog/{id}/spec`, `POST /catalog/{id}:deprecate`, `POST /catalog/{id}:retire` |

The sync pages call the hub through `api/hubClient.ts` (`/api/v1/hub/...`, mapped by the gateway to `/v1/hub/...`) and are gated on `hub.delivery.read` (nav) and `hub.subscription.write` (create, test, resume, replay). The client pages are gated on `hub.delivery.read` (nav) and act on `hub.client.write` (register, quota, revoke); that duty is not seeded yet, so no nav item or route carries it. Tests: `clients.test.tsx`. Editing a subscription other than its filter, and deleting one, are not in the UI yet. Tests: `sync.test.tsx`, `webhook.test.tsx`.

The outbound document is edited as JSON, like the map tester takes raw X12: structured editors for ASN packs and invoice lines are not built, because these documents normally come from the wave-31 and wave-29 events. The slice-5 screens are dry runs over stateless routes, so they have no list pages: punchout sessions, self-billing documents and e-invoices are not stored yet. Not here yet (later slices of PSG-35): punchout session log, self-billing reconciliation report and dispute worklist, the e-invoice workspace, resend, per-row selection for bulk reprocess (the filters choose the interchanges), map designer, hub admin. Tests: `npx vitest --run src/modules/integration`.
