# Changelog

All notable changes to Depot are recorded in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project
adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0.0 any minor
release may change public APIs.

## [Unreleased]

### Changed

- The product is renamed from Passage to Depot (docs/adr/0005-rename-to-depot.md). Every identifier moves together. Go modules become `github.com/BenjaminSRussell/depot/...` and the RLS role becomes `depot_app`. Environment variables are `DEPOT_*`, HTTP headers `X-Depot-*` and `Depot-*`, CloudEvents types `dev.depot.*`, Kafka topics `depot.*` and the Keycloak realm `depot`. Charts and images are `depot-*`, the Java package is `dev.depot`, the Python package is `depot_dispatch` and the ticket prefix is `DPT-`. The service-token signing context is `depot.service-token.v1.`. Three cryptographic labels keep the former name because data at rest depends on them: `passage.fieldcrypt.v1`, `passage.fieldcrypt.mac.v1` and `passage.log.pseudonym.v1`. Dev and stage must be redeployed from scratch and their secrets re-seeded under the new paths.
- The currency on a new sales order, purchase order, goods arrival, vendor invoice, customer payment and free-text invoice follows the source record (purchase order, then vendor or customer, then legal entity) instead of a literal default, and a vendor invoice takes the legal entity's only ledger (B-26, apps/web `shell/defaults/useDefaults.ts`). `noLiteralDefaults.test.ts` keeps the six task-route forms free of a literal currency. Order type and invoice account on the new sales order move under Advanced.
- CI's web job runs `node scripts/check-bundle.mjs dist` after `npm run build` and fails when demo-only data (the demo company, the job monitor's old sample rows; listed in `src/shell/demoMarkers.json`) reaches the production bundle (B-21 AC3, #687).
- Breaking: the output guard duty names `ViewSensitivePayroll` and `ViewSensitiveWorker` are renamed to `agents.sensitive-payroll.view` and `agents.sensitive-worker.view` (DEPOT-324). A hand-set Keycloak `duties` attribute is not a supported grant and is not legal-entity scoped, so re-setting one to the new name unmasks payroll, SSN and tax-id values tenant-wide. Do not re-set it; the old value now has no effect.

### Added

- OPA tests for every agents-ts API path (DEPOT-320, follow-up to DEPOT-294): each operation of `services/agents-ts/api/openapi.yaml` is granted to its duty alone, refused to every other duty and method, and decided through Envoy on `/api/v1` and `/v1` (allowed, 403, unauthenticated) in `authz_test.rego`, `gateway_test.rego` and `deploy/scripts/test_gateway.py`. A vitest check fails when an `openapi.yaml` operation has no `policies/authz/data.json` entry. `data.json` is unchanged: every path already had its duty row.
- The output guard duties (DEPOT-324, follow-up to DEPOT-305) are seeded in `policies/authz/data.json` as the flag duties `agents.sensitive-payroll.view` and `agents.sensitive-worker.view` (renamed, see Changed); no role holds them yet, so payroll, SSN and tax-id values are masked by default in the copilot chat. The role grant is DEPOT-349, the agent run paths are DEPOT-350, and detail is in `services/agents-ts/NOT-IMPLEMENTED.md`.
- Event payload contracts for every Kafka consumer (architecture gap D6, B-05c, #666). Before, nothing compared what a consumer reads with what its producer declares and writes. A missing field went unnoticed until events failed or left an index empty.
  - **Check.** `deploy/scripts/test_event_contracts.py` runs in the new CI job `event-contracts`. It takes the consumers `test_kafka_consumers.py` finds in the code and works out what each one reads:
    - Go: the new `deploy/ci/eventfields` (its own stdlib-only module, linted in CI) type-checks each module. It follows every handler-map entry reached from a main package, through functions, variables and interface methods, to the `json.Unmarshal` of the event data: of `evt.Data`, a local copy, or a `[]byte`/`json.RawMessage` parameter it is passed in, with `any` targets bound at their call sites. A second Unmarshal of a decoded `json.RawMessage` field adds nested paths. It fails closed: any other use of the data (`json.NewDecoder`, `len`, a call it does not follow, `json.Marshal` of the whole event), a decode into a map, and a decoded `json.RawMessage`, map or `any` field that no followed decode reads are problems unless an allowlist names them with the reason. A further decode of such a field is followed directly, through a local copy or through a helper. A closure that takes the data is followed itself.
    - kafkajs: each `<Stem>Event` interface the consumer casts to, paired with its `<stem>Type(s)` constant, with interface-typed members expanded. A consumer with no such cast fails unless allowlisted (integration-hub-ts, which forwards whole events).
    - kafka-python: the data keys the consumer reads.
  - **What fails.**
    - A field not declared by the producer's AsyncAPI `send` message, or not written by every `events.New` call that writes the type (followed to the call that names the type and payload).
    - A field a producer writes that its schema does not declare.
    - A consumer group that subscribes to a topic none of its own handlers reads a type on, so a group whose handlers the analyser misses cannot pass unseen. Each group is tied to its handler maps through the `eventing.Config` named after it.
    - A producer channel that is not the topic its outbox connector routes the type to. For an aggregate-routed connector the check traces each `outbox.Enqueue` back to its `events.New`, giving (type, aggregate) pairs.
    - An `events.New` or `outbox.Enqueue` call the analyser cannot resolve in a producer of a consumed type, unless that call is listed (by its source text) with the reason; stale entries fail too.
    - The job fails, rather than skips, when Go is missing in CI, and shows the analyser's stderr. Negative tests cover each rule, with a synthetic module for each decode form.
  - **Fixes.**
    - Search decoded fields its events do not carry, through one struct shared by two types. Its handlers now decode one struct per type.
    - Three messages now declare fields their producers already wrote or can write: fulfillment `packingslip.posted` `legal_entity_id`, sales `order.confirmed` `order_number` and `legal_entity_id`, and billing `creditnote.posted` line `order_id`, `order_line_id`, `product` and `packing_slip_line_id`. The credit-note line fields come from the invoice line shape the payload shares and are not set today; the schema's `additionalProperties: false` refused them.
    - Receiving's AsyncAPI channels now name the topics outbox-receiving routes to (by aggregate type): `depot.receiving.vendorinvoice` instead of `depot.payables.invoice`, `depot.receiving.settlement` instead of `depot.payables.settlement`, and `depot.receiving.auditpolicy`, `ersvendor`, `erspriceconfirmation` and `invoiceadjustment` instead of the shared `depot.receiving.policy` and invoice channel.
    - No producer code changed. No consumer reads inventory events, so `journalEntryId` is not added.
  - **Search (ADR-0013).**
    - The new `services/search/events/asyncapi.yaml` declares the ten consumed topics as `receive` operations, each payload a `$ref` to the producer's.
    - The check ties each indexed type to an `outbox-<service>` connector that relays it to that topic: by the event-type route, or by the aggregate the producer's code enqueues that type under.
    - **Reconciliation, partial.** The new `search reconcile <report.json>` compares live index counts per type and legal entity with a source count report and lists index rows the report omits. Only this index side is built: nothing counts the source services' records to produce the report (follow-up #731).

Every Secret is an ExternalSecret on the ClusterSecretStore `depot`, one Application per service (`<service>-secrets-stage`, children of root-stage at wave -1, before the services), so a missing Vault key stops only that service; the Postgres server mounts only its own password. Database URLs URL-encode the password. New runbook `docs/ops/runbooks/database-password-rotation.md`. Keycloak's database is in the hello-ledger Postgres. Apicurio's and Temporal's databases serve TLS only too (`tls.enabled` in `deploy/postgres` and `deploy/temporal-postgres`). The Secrets every stage service reads are created in stage, except agent-runtime's `agents-provider` (listed with its reason); a test fails on any other.

- hr and party give up on the numbering service after 3 seconds (`DefaultTimeout`, a per-call deadline over connect, response and body) and say why (B-09 part b, ADR-0015). A timeout is the new `503 HCM-NUMBERING-TIMEOUT` / `PTY-NUMBERING-TIMEOUT`, which names the 3 seconds, or the caller's own deadline when that came first; every other failure stays `*-NUMBERING-UNAVAILABLE` with its cause in the detail (not configured, no signing key, unreachable, the HTTP status). Both details say nothing was saved and to retry with the same Idempotency-Key (numbering may already have issued a number). The web error catalog has the new codes.
- One authorization enforcement model on the three gateways, and an allow/deny record for every decision (architecture gaps D23 and D36, B-04, ADR-0017; FR-2.7). Before, devgateway and `depot-server` asked OPA about every request while Envoy in Kubernetes made no decision, and nothing recorded who was allowed or refused what.
  - **Envoy asks OPA.** `SecurityPolicy/depot-api-jwt` gains `extAuth`: gRPC to the new `depot-authz-opa` Deployment in `deploy/gateway/authz-opa.yaml` (OPA 1.21.2 with the Envoy plugin, digest-pinned, two replicas), with `failOpen: false`. Only the identity headers the JWT filter set and `x-request-id` are sent to it. The new `EnvoyProxy/depot-api-proxy`, the Gateway's `infrastructure.parametersRef`, moves `ext_authz` after `jwt_authn`; by default Envoy Gateway runs it first. The OPA pulls identity's signed bundle like the per-service sidecar and answers the new rule `data.authz.envoy` in `policies/authz/authz.rego`. That rule builds the policy input from the verified headers and the path the service receives (`/api` removed, or the D22 service base from `gateway_service_bases`). It calls `decision` and denies with the single-host gateways' `403 AUTH-0003` problem, or `400 GW-0400` for a path that is not canonical; any percent-encoding now makes a path non-canonical on all three gateways. When OPA cannot answer, Envoy fails closed with a bare `403` (Envoy Gateway v1.4 has no status-on-error setting), where the single-host gateways answer `503 AUTH-0503`. A NetworkPolicy admits only `depot-api`'s Envoy pods. Envoy now removes a client's `X-Request-Id` in `earlyRequestHeaders` and always generates its own. The Envoy Gateway v1.4.0 `EnvoyProxy` CRD is now vendored, so kubeconform validates it.
  - **Rollout.** The OPA needs identity's bundle (`bundle.enabled`, off in dev) and the hand-made Secret `depot-authz-opa-bundle`. Until both exist, every API request through Envoy is refused. That path did not work end to end before either (D32). The OPA is ready only when the bundle is active, its local decision-log mask is loaded and the bundle answers `data.authz.envoy`.
  - **Machine callers.** OPA grants only from identity's role assignments, so a `depot-services` client-credentials token whose duties come from Keycloak attributes is refused at Envoy unless identity holds role assignments for its service-account subject. No machine caller in this repository goes through Envoy today (ADR-0017).
  - **MCP.** `mcp.copilot.use` now grants `POST /mcp`, the path mcp-ts serves and Envoy decides on. It named `/api/v1/mcp` before, which no gateway decides on, so Envoy would have refused MCP to everyone. Every routed prefix's service base is now checked to have a duty permission under it.
  - **Single-host gateways.** devgateway and `depot-server` now use `identity.RequireOPAForGateway`. `decision` also names the duty that granted an allow (`{"allow": true, "duty": ...}`). The services keep `authz.RequireDuty` as defence in depth, and no check is loosened.

    - devgateway and `depot-server` run it end to end against `opa run policies/authz`, through the new test helper `services/identity/authztest`.
    - Envoy runs it as `gateway_test.rego` against `data.authz.envoy`, with one allowed and one refused request for each of the seven rewritten prefixes.
    - The table includes percent-encoded paths (400 everywhere) and a machine caller whose duties are only in its token (refused everywhere).
    - `deploy/scripts/test_gateway.py` `AuthzEnforcement` checks statically that every `depot-api` HTTPRoute is under the one gateway-level SecurityPolicy with `extAuth` and that no route- or listener-level SecurityPolicy overrides it. It also checks the filter order, the headers sent, the backend, the NetworkPolicy, the local decision-log mask and readiness gate, and the request-id removal. It asks the real rego (`opa eval`) for the path every generated route sends its service. The deploy CI job now installs OPA for that.
    - No live Envoy runs (#213).
    - `depot-server`'s tests move to the identity CI shard, which installs OPA. The Windows test job installs OPA too.
  - **Decision record.** Every decision writes one `authz.decision` record, schema 1, documented in the new `platform/go/README.md`. Its fields are source, tenant, subject, duty, route, outcome, reason, request id and `log_class: audit.other`.
    - The subject is pseudonymized by the new `logpseudo.Subject`, which `httpx.Serve` and both gateways now load whatever the profile says. Without a key it is `[redacted]`, never the raw id.
    - **Dedicated key.** `logpseudo` reads a new dedicated key, `DEPOT_LOG_PSEUDONYM_KEY` or `DEPOT_LOG_PSEUDONYM_KEY_FILE` (base64 of 32 bytes, used only for this MAC), before fieldcrypt's current master key. Both use the same derivation.
    - **depot-server keys.** `depot-server` reads only the dedicated key for its own records. It passes `FIELDCRYPT_*` only to the seven services that load field-encryption keys (compliance, hr, migration, party, payables, receiving and sales; a tested allow-list), and passes the pseudonym key to none, unless a service's own configuration sets it. **Upgrade note (Windows):** before, every service inherited the whole service environment. Keys set on the Depot service still reach those seven services (hr does not start without them), and no longer reach any other (`docs/ops/windows-install.md`, Secrets).
    - **Envoy record subject.** The Envoy OPA computes the same pseudonym in rego (`data.authz.log_pseudonym`, checked against Go on shared vectors) under the dedicated key from the optional Secret `depot-log-pseudonym`.
    - The route is the method and route template, never the raw path.
    - Writers: `authz.Require`, `RequireDuty` and `RequireAnyDuty` in every service; identity's `RequireOPA*` in identity and both single-host gateways, which also record their own legal-entity-selection and non-canonical-path denials; and the Envoy OPA, as `result.record` of its console decision log. Its mask, which erases the whole input, is a local policy in the OPA's ConfigMap (`data.system.log.mask`), not part of identity's bundle, so an older or broken bundle cannot turn it off. A test runs OPA against a bundle without the mask rule and finds nothing raw logged.

    - The whole-log pseudonymizer passes the record's subject through unchanged, because `logpseudo.SubjectAttr` marks it. A string that merely looks like a pseudonym is still pseudonymized.
  - **Metric and alert.** `depot_authz_denied_total{source,duty,reason}` is exported on every service's `/metrics` through the new `httpx.RegisterMetrics`. It has no user or tenant label. A new Prometheus alert `DepotAuthzDenySpike` in the observability chart fires above 0.5 denials/s per source and reason when that is more than 5 times the previous hour.

    - `DepotAuthzEnvoyCheckErrors` alerts when Envoy cannot get an answer from OPA, and `DepotAuthzOPAUnavailable` when no OPA replica is available. That alert is on by default and off in dev (`authz.opaUnavailableAlert`), where identity serves no bundle.

They used to be a ConfigMap that no Prometheus loads, so none of them could fire. `deploy/scripts/test_argocd_apps.py` checks that every alert is in a rule the dev Prometheus selects, and CI runs `promtool check rules` on the rendered rules (`deploy/scripts/prometheus_rules.py`).

    - Secret `depot-log-pseudonym` is not yet wired into the service charts, so most services still write `[redacted]`. Until it is, it must hold fieldcrypt's current key, so the Envoy record and the fieldcrypt-keyed services agree on a user's pseudonym.

- CDC-fed audit trail with the `depot.ctx` actor and trace, change-chain verification and a daily anchor (architecture gap D3 part a, B-07a, #669; FR-5.10, FR-5.11, AUD-API-4). Changes to audited master-data tables now reach the audit hash chain from the owning service's database rather than over HTTP. A new connector type, `audit-cdc-<service>` in `deploy/kafka/connect.yaml`, is separate from the outbox relays and reuses the service's CDC role. It captures the tables of the service's publication `depot_audit_<service>` and the service's `depot.ctx` logical-decoding messages into one single-partition topic, `depot.cdc.<service>`. The pilot is party's vendor bank accounts: party migration `0021` sets REPLICA IDENTITY FULL, publishes the table and grants SELECT. The sealed account and routing numbers are never written to Kafka: their ciphertext is in the WAL and reaches Kafka Connect, which drops it (`column.exclude.list`), and the CDC role's SELECT leaves those columns out. Party's add-bank-account path writes `depot.ctx`. The new `platform/go/auditctx` package has `WithAuditedTx` and `Emit`. Together they write `pg_logical_emit_message(true, 'depot.ctx', …)` in the transaction that changes an audited table. The message carries the actor taken from the verified principal: a person; a service; or a service or agent acting for a user, with `onBehalfOf`. It also carries the reason from the new `X-Depot-Reason` header, which `httpx.NewRouter` now captures for every service, the W3C trace id (else the request id) and a per-transaction `changeSetId`. `audit cdc-consume` (chart `consumer`, KafkaUser `deploy/kafka/audit-consumer.yaml`, service principal `audit-cdc`) records one chain row per changed field of the table's allow-list. Each row carries the old and new value, the entity, the record id, the legal entity, the source service, and the actor, reason and trace of its transaction's message. A change without a message is recorded as `actorKind` `system`, user `system:<service>`, flag `unattributed`. The consumer uses the platform `eventing` consumer through its new `Config.Decode` hook, and the inbox makes it idempotent by CDC position. `GET /v1/audit/records:verify` (new duty `audit.verify`) verifies a tenant's change chain or a seq range of it. It reports the first break (`hash-mismatch`, `link-mismatch`, `anchor-mismatch`) and counts rows from before B-06 apart rather than as tampering: legacy-precision rows (their sub-microsecond time recovered) and legacy forks. The `audit chain-nightly <tenant-id>...` CronJob (chart `chainNightly`, service principal `audit-anchor`) verifies every listed tenant nightly. It stores the day's chain head in the append-only `audit_anchor` table (one per tenant per UTC day), logs it, and fails on a break (runbook `docs/ops/runbooks/audit-chain-verify-failure.md`). Audit migrations `0009` and `0010` add `legal_entity_id`, `source` and `flag` to `audit_entry`, covered by a v3 hash payload. They add a restrictive legal-entity policy on `audit_entry` and `alert_inbox` that admits NULL for tenant-level entries (allowlisted), plus `consumer_inbox`, `cdc_tx_context` and `audit_anchor`. Changes recorded over HTTP are filed under the one legal entity of the service token. `deploy/scripts/test_argocd_apps.py` tells outbox relays and audit CDC connectors apart. It gains `test_audit_cdc_connectors_match_their_tables_and_the_consumer`, which checks each audit connector against the service's migrations, P3 exclusions, ACLs, the consumer's KafkaUser and the consumer's table registry. Adding a table is wiring only (`services/audit/internal/cdc/tables.go`). Review fixes:
  - **The `depot.ctx` message is signed.** Any session on the database can emit one, so `Emit` signs it with the service's ADR-0010 Ed25519 key (`tenant.ServiceSigner.SignDetached`, domain `depot.audit-ctx.v1.`). The signature covers the tenant, `txid_current()` and the body. The consumer verifies it against the service-token key registry (`DEPOT_SERVICE_PUBLIC_KEYS`) and requires the issuer to be the source service and the signed txid to be the change's own. An unsigned, unknown-key, altered or replayed message records its changes as `system` with the new flag `unattributed-bad-signature`. Party now calls `auditctx.ConfigureSigner` at start.
  - **Joining a message to a change** also requires a commit time within one hour, so a reused transaction id cannot attach an old message. The consumer purges messages older than seven days itself.
  - **`:verify` changes:**
    - It needs tenant-wide authority (AUD-0009).
    - It walks at most 100,000 rows per request, with `complete`, `nextFromSeq` and `startPrevHash` for paging.
    - It names a `fork`.
    - It counts legacy rows with a `|` in a field as `legacyAmbiguous`.
  - **Anchors** are written only through the SECURITY DEFINER function `audit_anchor_record`, which takes the head hash from the chain and accepts only today or yesterday. `depot_app` lost INSERT on `audit_anchor`.
  - **The connector** is created `state: stopped` until the consumer is enabled. It sends a table-less heartbeat, and its topic is a declared KafkaTopic with one partition and 30 days' retention.
  - **Smaller fixes:** party 0021 sets a lock timeout, and the chart's `consumer.kafka.dlqTopic` is used.
  - **The trace id is client input**, and the docs now say so.

  Re-review fixes:
  - **Blocker.** `audit_anchor_record` (migration 0011) captured its `search_path` FROM CURRENT, which leaves `pg_temp` out, and PostgreSQL then searches `pg_temp` first. `depot_app` could shadow `audit_entry` with a temp table, or with a temp view that calls a temp function, and run code as the owner. Migration 0013 replaces the function: its `search_path` is `pg_catalog`, then the schema, then `pg_temp`; its body is schema-qualified; EXECUTE is revoked from PUBLIC and granted only to `depot_app`. It now reads the head itself under the append lock and refuses a seq that is not the head (the nightly job walks again). A test shadows both tables and the view as `depot_app` and checks that they are ignored.
  - **rlscheck** now fails any SECURITY DEFINER function whose `search_path` is unset or does not end with `pg_temp`. No other service had one, and none is exempted.

- Quality holds now hold across every movement kind together (#33, Wave 33 AC2). Inventory's issue claims

  both passed. Claims of every kind now count together, and the new optional `issueRef` (the document line the units
  are issued for: `SALES_LINE:<order line id>` or `PRODUCTION_ORDER:<order id>:<item id>`) groups claims that are
  successive steps of the same units. A pick and the ship of what it picked count once (the largest per-kind total of
  the ref). Fulfillment's packing-slip post and production consumption send their ref, and a warehouse pick sends the
  work line's `issueRef` attribute. Inventory's own issues are weighed against the outstanding claims too: journals
  other than counts, status steps, transfers and blockings. A sales DELIVERED booking settles its order line's
  claims, so stock issued through inventory and claimed before is no longer counted twice. A claim may not leave
  free stock below zero while anything is held, so a hold placed after a pick also stops the ship of the staged units
  until the usage decision. Inventory migrations 0038 and 0039 add `inventory_issue_claim.issue_ref` and the `ISSUED`
  rows (NOT VALID checks, validated apart). Property test: `TestHoldProperty_MixedMovementsNeverReachHeldStock`.

  settles only the claims of that line's ref, once and net of what left the warehouse; claims without a ref and claims of other
  refs are never settled by an issue, so one line's delivery cannot release another line's pick and move held stock. Journals,
  status steps and registrations settle nothing, and `transactions:apply` takes no `issueRef` (refused). Settlement keys start
  `issued:` and `ClaimIssue` refuses a caller key that does.
  Production consumption claims stay until released (production books none in inventory yet). Sales and inventory tests
  follow a posted slip's `:record-progress` call to the event and the booking.

### Security

- Kubernetes: every service now refuses network connections except from the gateway, the services that call it and Prometheus (D1, ADR-0006 rule 6, B-01a, #660). Services believe the `X-Depot-*` identity headers they receive, and before this change only 13 of 70 charts had a NetworkPolicy (some of which let every pod in the namespace in) and no namespace denied traffic by default, so any pod in `hello-ledger` could call a service as any user. Now every service chart renders `<release>-ingress` (template `templates/networkpolicy-ingress.yaml`, the same in every chart): the API port admits only the Envoy pods of Gateway `depot-api` (and of `depot-portals`, `depot-region` or `depot-edge` where an HTTPRoute sends traffic to the service) and the specific services that call it; the metrics port admits only Prometheus. The list of callers is generated by `deploy/scripts/gen_networkpolicies.py` from the `*_URL` peer clients each chart configures, cross-checked against the service grant table (`policies/authz/data.json`): a grant with no client is admitted only when the script lists it with a reason (none today; transport's unused grant to carrier-gateway is listed as not admitted). The callers are written into the chart's `ingressPolicy` values; rerun the script after changing a client, a grant or an HTTPRoute (`make -C deploy test-argocd` fails until you do, and renders every dev and stage chart to check the policy). The namespaces `hello-ledger`, `batch` and `metadata` also get a default-deny ingress policy (ApplicationSet `namespace-default-deny` in dev and stage; in prod for `hello-ledger`). iot-edge opens no port and admits nothing. Three charts now set the peer URLs their code already reads, so the generated policy admits them: receivables `ledgerUrl`, `billingUrl`, `taxUrl` (LEDGER_URL, BILLING_URL, TAX_URL), the migration factory `ledger.url` (LEDGER_URL) and workflow `budgetingUrl` (BUDGETING_BASE_URL). `global.regionFenceUrl` must now point at Gateway `depot-region` (`https://region.<env>.depot.dev/healthz/region`): every chart refuses to render with the ops Service URL, because a network rule cannot limit callers to `/healthz/region` and would open the whole operator API. The four Python services (configurator, forecast, prediction, scheduler-opt) serve `/metrics` on their API port, so Prometheus reaches that port too (an exception recorded in ADR-0006). The old per-chart ingress rules that admitted the whole namespace (fx, org, mcp-gateway) or kept the API open (edi, receivables) are gone; the AS2, payment webhook and OPA bundle ports keep their own policies, and the portals, carrier-gateway, integration-hub and migration keep their egress policies. Removed values: `networkPolicy.apiFrom` (edi, receivables), `networkPolicy.ingressFrom`/`ingressNamespaces`/`metricsFrom` (fx), `networkPolicy.ingressNamespaces`/`metricsNamespace` (org, mcp-gateway, agent-runtime), `networkPolicy.gatewayNamespaces`/`gatewayPodLabels`/`allowSameNamespace`/`metricsNamespaces` (identity), `networkPolicy.workflowPodLabels`/`agentsPodLabels` (agent-runtime, workflow), `networkPolicy.callers` (carrier-gateway), `networkPolicy.edgeNamespace` (portals), `networkPolicy.gatewayNamespace`/`metricsNamespace` (integration-hub). **Known weakness:** a peer is recognized by its pod label `app.kubernetes.io/name`, which any workload in the namespace can set, so a pod labelled as ledger gets every access ledger has. Until an admission policy pins those labels to each chart's ServiceAccount and image, only trusted parties may create pods in these namespaces, or `DEPOT_GATEWAY_SECRET` must be set as well (ADR-0006 rule 6). **Rollout:** a pod in these namespaces that no NetworkPolicy selects (a database, a tool) accepts no connection once the default deny syncs. The policies only take effect on a CNI that enforces NetworkPolicy (Calico, Cilium, Azure NPM; k3s enforces it with its built-in controller; plain flannel does not). Prometheus must run in namespace `observability` with label `app.kubernetes.io/name: prometheus`, and Envoy Gateway's proxies in `envoy-gateway-system`, or the values must say otherwise. To verify in a cluster: `kubectl -n hello-ledger get networkpolicy` lists `default-deny-ingress` and one `<release>-ingress` per service; `kubectl -n hello-ledger run probe --rm -it --restart=Never --image=curlimages/curl -- curl -m 5 -s -o /dev/null -w '%{http_code}' http://ledger:8080/healthz` times out (a pod that is not a peer), while the same request through the gateway answers. Still open: the forged-header integration test on a live cluster (#213) and moving the header-forwarding peer calls to service tokens (B-01 part b).
- Kernel: a legal-entity selection is refused without an `le` claim; tenant administrators are unaffected (D33 part a, ADR-0006 rule 4, B-03a). Before, when the gateway-asserted claim `X-Depot-Legal-Entity` (the token's `le`) was empty, `platform/go/tenant` took the shell's `X-Depot-LegalEntity` selection as the request's scope, so only the gateways kept a caller from choosing any legal entity. Now the selection can only narrow the claim. A request with a selection and no claim is refused with `403 AUTH-0003`. The one exception is a tenant administrator, a principal with the `tenant.administer` duty and no claim (the same test as `tenant.IsTenantAdmin`): that principal is entitled to every legal entity of the tenant, so it may still pick one as before. When the claim is a comma list (the kernel accepts up to 100), a selection of one or more entities from that list narrows the scope to them; a selection naming any entity outside the list is refused with `403 AUTH-0003`. A selection different from a single claim was a `400 COM-0001` before, and is now also `403 AUTH-0003`. A malformed header is still `400 COM-0001`, and a request without a selection behaves as before. A refusal is logged as a warning. What Envoy forwards is unchanged: it still strips the selection. devgateway and `depot-server` already refuse with 403 any selection that is not equal to the claim, tenant administrators included, so they are stricter than the kernel until B-03c. **Release order (RR-01):** this change must ship before, or in the same release as, any change that makes Envoy forward the selection header, which is planned in B-03c only. integration-hub-ts, which reads the caller's legal entity for the subscription test send itself (`legalEntityFromHeaders`) instead of through the kernel middleware, applies the same rule: a selection without a claim is `403 HUB-0403` unless the caller holds `tenant.administer`, a selection outside the claim is `403 HUB-0403` (the two refusals have different details), and a malformed, all-whitespace or repeated header is `400 HUB-0400`. Before, it took the selection whenever the claim was missing.
- OPA: a role assignment scoped to a legal entity grants its duties only for requests in that legal entity (D33 part b, ADR-0006 rule 4, B-03b, FR-2.6, FR-2.9, FR-6.10). Before, identity's policy bundle left legal-entity-scoped assignments out, so a per-company role granted nothing where OPA decides (identity's administrative and SCIM routes, devgateway, `depot-server`). The bundle now carries them in a new root, `scoped_assignments[tenant][subject][legal_entity]`, and `authz.rego` grants a scoped duty only when every legal entity in `input.subject.legal_entity_id` carries it: a role scoped to company A grants in A and nothing in B, in A and B together, or on a request with no legal entity. A *tenant-level* duty (`"tenant_level": true` in `policies/authz/data.json`: every `identity.*`, `audit.*` and operator duty, SCIM provisioning, platform administration, routes that run only in scope `*`, tenant-wide structure and integration channels; the table is in `policies/authz/README.md`) is never granted by a scoped assignment: the rule skips it, identity refuses to create one with `422 IDN-ROLE-TENANT-LEVEL`, and the bundle compiler drops any stored one, as it drops a scoped assignment whose legal entity is no longer active (identity migration 0019). Tenant-wide assignments, tenant administrators and operator-only duties are unchanged. `RequireOPA` always takes the request's legal entity from the verified token's `le` claim, a JSON string only; the principal, and so the database scope of identity's routes, is unchanged. The `pv` (policy bundle version) claim is not issued, a decision recorded in ADR-0006 rule 5.
- Shop floor: time and pay data is scoped to the legal entity that employs the worker (D17, B-03b, FR-2.4). Before, every shop floor table was tenant-wide, so a caller in company A could read and write company B's time registrations, calculated days, pay lines and payroll exports. Migration `0039_worker_legal_entity.sql` adds `worker.legal_entity_id` and `pay_export_batch.legal_entity_id` with restrictive policies, and `time_registration`, `worker_day`, `pay_line`, `registration_correction`, `worker_cost_rate` and `pay_export_line` follow the worker's legal entity. A new worker belongs to the caller's legal entity, or to `legalEntityId` within the caller's scope; a payroll export is one legal entity's. **Existing workers have no legal entity and are visible only to all-entity reads until a tenant administrator assigns one: run the backfill in the same deploy window** (`docs/runbooks/delivery/shopfloor-legal-entity-backfill.md`, dry run first) with the new bulk route `POST /v1/shopfloor/workers:assign-legal-entity` (`allUnassigned`, at most 1,000 workers per call with a `remaining` count, or up to 1,000 `workerIds`; `dryRun` writes nothing), or per worker with `POST /v1/shopfloor/workers/{id}:assign-legal-entity`. Both confirm the legal entity with identity first, through the new service-only `GET /v1/identity/legal-entities/{id}` (duty `identity.legal-entity.lookup`, granted to shopfloor; chart values `identityUrl` and `serviceIdentity`): an unknown or inactive legal entity is `422 SF-0201`, identity not answering or not configured `503 SF-0202`, and nothing is written. Both need no legal-entity claim, `tenant.administer` and `shopfloor.setup.maintain`, publish `worker.assigned` with the legal entity and the administrator, and also give old export batches whose lines all belong to the legal entity's workers that legal entity. A wrong legal entity can be corrected while the worker has no time or pay; after that it never changes (SF-0200). Exported lines follow their batch (migration 0041), a new exported line must also belong to a pay line of the caller's legal entity (0042), and an index serves the worker lookups of the policies (0040). The effective-permissions report applies the same exclusions as the bundle (scoped tenant-level duties, inactive legal entities). The sweeper's auto clock-out, the production consumer and the auto clock-out route called with a service token still act on every legal entity of the tenant, through an in-process context marker rather than the actor's name. The other tables of the services D17 named (shopfloor, scheduling, mobile, fx, integration-hub-ts, agents-ts; audit follows in B-07) have a recorded reason in `platform/go/rlsexempt`, and `tools/rlscheck` now fails on a table of these services with neither a legal-entity policy nor a reason. Nine tables have an interim reason, tracked in #725 (mobile's sessions and offline queue, integration-hub-ts's delivery log, agents-ts's run log): those rows are readable across legal entities by the holders of the services' supervisor and admin duties until they record a legal entity.
- Audit: a change is recorded only by a service the audit service verified itself, under that service's identity, never under a name the request supplies (B-06, AUD-API-1, FR-5.10). Before, `POST /v1/audit/changes` took the actor from the body's `userId`, or from identity headers that any workload in the cluster could set, so a caller could record a change in another person's name. Now the route accepts only a signed service token; a call with identity headers alone is refused with AUD-0007, and a body `userId` with AUD-0002, as `POST /v1/audit/reads` already refused it. What is now guaranteed for each new change: `userId` is `service:<name>` of the verified caller; `actorKind` is `service` (or `agent` for the agent runtime); and `onBehalfOf` is the user that the calling service put in its signed token, which the body may repeat but never change (AUD-0006). Changes made by people directly will reach the trail through CDC (B-07). Changes also carry `reason`, `changeSetId`, `eventType`, `eventId` and `workflowInstanceId` (migrations 0005 and 0006: new columns, with checks added without a long table lock). The new fields are on the hash chain, whose encoding is now documented for outside verifiers (services/audit/README.md). Rows recorded earlier keep the hashes they were written with, and none is rewritten. But a row written before this fix whose time had a sub-microsecond part cannot be re-verified from the database. Two existing faults in the chain are also fixed. Concurrent changes for one tenant could fork the chain; appends are now serialised per tenant. Rolling audit back stalls signature records until audit is rolled forward; none are lost. While old audit replicas still run they take no chain lock and still accept identity headers, so roll audit for this release without old and new replicas overlapping: the audit chart's new `strategy` value, set to `{ type: Recreate }` for this release only (services/audit/README.md).

### Upgrade notes / operator actions

There is no earlier release, so this is a first install rather than an upgrade. Before any
environment runs 0.1.0:

1. **Protect `main` before prod.** A repo admin must enable branch protection on `main`
   (required review plus code-owner review) before the prod cluster is registered in Argo CD.
   Until then any push to `main` auto-deploys prod (`docs/runbooks/delivery/deploy-local.md`).
2. **Build, sign and pin images.** Once Actions billing is restored, re-run CI on the tag, then
   build every service image and sign it with cosign. Replace each placeholder digest in
   `deploy/envs/{dev,stage,prod}/apps/*.yaml` with the real digest. The Kyverno admission
   policy (#170, #172) rejects unsigned or tag-referenced images.
3. **External Secrets.** The charts read their Secrets through External Secrets Operator from a
   `ClusterSecretStore` named `depot` (the `storeName` default in `deploy/postgres` and the
   batch chart; also `deploy/envs/dev/kafka-secrets`). Install ESO and create that store,
   backed by Vault, before syncing.
4. **Apply each service's migrations in filename order** (`services/<svc>/migrations`). Pay
   particular attention to these:

     `identity/0006_operator_single_row.sql`, `identity/0007_scim.sql`.

    `IDENTITY_SCIM_AUDIENCE` and `IDENTITY_OPA_URL` are all set. Assign the duty `Provision
    users via SCIM` to the IdP's service account.
13. **Receiving `PARTY_URL`** (#354). Receiving reads vendor groups from party through
    `PARTY_URL`. The chart sets it from `serviceUrls.party`, defaulting to
    `http://party.<namespace>.svc:8080`, so set `serviceUrls.party` wherever party runs
    elsewhere. With `PARTY_URL` empty, `vendor_group_id` is never sent and payables' per-group
    aging gets no group.
14. **`RECEIVING_ALLOW_LEGACY_PO_LINE` is for dev only.** Chart value `allowLegacyPoLine`
    defaults to false. When it is set, receiving trusts client-sent `poLineId`,
    `orderedRemaining` and `unitPrice` instead of resolving `poLineNo` against the purchase
    order. Never set it in stage or prod; it is removed in #340.

### Known limitations

- **No published artifacts.** No images, charts, SBOMs or signatures exist for 0.1.0, and the
  digests in `deploy/envs` are placeholders. CI did not run on the release commit because
  Actions is billing-blocked.
- **Per-service gaps.** Each service's `NOT-IMPLEMENTED.md` lists what is missing. Many slices
  are partial implementations of their wave's functional requirements.
- **Identity is incomplete.** The Keycloak realm and push (#80), OIDC/SAML federation and MFA,
  OPA bundle build and distribution, and gateway host-to-tenant mapping (#213) are not
  implemented. mTLS between pods is a follow-up to the service tokens.
- **No live-cluster proof.** Nothing has been proved on a live cluster: Actions runs, the
  gateway, the CDC relay, the EBICS bank sandbox, or the repository admin steps. All of these
  are tracked in #213.
- **Wave proof criteria are partly open.** The proofs that landed in code are Wave 7 (#352),
  Wave 12 AC-12.4 (#273), Wave 13 (two of four, #350), Wave 14 (AC2 to AC4, AC1 partial, #351),
  Wave 15 AC1 (#344), Wave 20 (AC-20.1, 20.3 and 20.4, #347), Wave 23 (#261), Wave 31 (AC1 to
  AC4, #348), Wave 36 (AC2 and AC4, AC3 partial, #346), Wave 42 AC2 (#258) and the interim Wave
  40 fixture (#345). Human steps are still open: accountant workbooks and sign-offs, recorded
  walkthroughs, and every phase-exit sign-off.
- **Wave 36 AC1 is not met.** On the adversarial 1,000-line reconciliation fixture, 78.0% of
  all lines auto-match correctly (91.8% of the lines that have a book counterpart, 0 wrong),
  against the 95% bar (#346).
- **Transitional umbrella grants.** The service grant tables keep `ledger.journal.post`,
  `ledger.journal.read` and `numbering.write` for this one release, until #341 removes them.
- **Tax is not deployable yet.** The tax service has no Helm chart, Dockerfile or store (slice
  B in `services/tax/NOT-IMPLEMENTED.md`). Tax does not verify service tokens yet, so the
  seeded payables to tax grant is not exercised.
- **Party does not verify service tokens yet.** No service-token verifier, public keys or
  replay table are configured for party. A receiving build with a signing key therefore signs
  its vendor lookup (#354), party rejects it, and every posted invoice goes out without
  `vendor_group_id`; watch `receiving_vendor_group_lookups_failed_total`. The lookup only works
  where receiving runs without a signing key and forwards the user's headers. Payables' vendor
  bank reveal (#352) is not callable as a service for the same reason.
- **Known vulnerability.** `apps/web` depends on `zod` 3.23.8 in production, which is affected
  by the high-severity advisory GHSA-mrhx-c7xc-m3w5 (CVE-2023-54404: memory exhaustion when
  validating oversized constrained collections). It is fixed in zod 4.6.6+, but that is a major
  version bump, tracked in #355. The code runs client-side, in API response validation in the
  browser.
- **Go and Python dependencies were not audited.** No `govulncheck` or `pip-audit` run was made
  for this release. Only the npm advisory above was checked.

  recording, #75).
