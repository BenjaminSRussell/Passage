# Not implemented in PSG-14 slice A

Slice A ships period control, the allocation, year-end and checklist engines, the `:check` endpoint and the service skeleton. Slice B of the same ticket carries the rest; no other ticket owns it.

| Deliverable or AC | Status | Reason |
|---|---|---|
| AC1 / Deliverable 1: period control enforced at the posting API | partial | decision logic, `FOR SHARE` read, `:check` and the resolver ship, and `internal/api/period_contract_test.go` proves through the real routes that a closed period rejects (check) or reports closed (resolve) for every source system the ledger, payables, receiving, assets, eam and production send, and that only the closed module and unmapped sources are rejected when one module is closed. The ledger-side half (`services/ledger/internal/store/closed_period_test.go`) proves its own posting paths reject; a single test that drives a ledger posting into a closed close-service period needs the ledger and close in one harness (ledger code is out of this lane). | AC2 / Deliverable 3: allocation engine | partial | fixed, basis and reciprocal computation ship with fixtures; allocation rule persistence, run, post and reversal API are slice B and need the ledger |
| AC3 / Deliverable 5: year-end close | partial | `POST /v1/close/year-end-runs` derives balances from the ledger trial balance, classes from the ledger chart and dates from close's fiscal periods (which must be contiguous and cover 1 January to 31 December; nothing numeric comes from the request), stores the run with proposals and the journal id, posts the closing entry (profit and loss to retained earnings, dimensions on the ledger lines), supports re-run through `supersedesRunId` (reverses the prior closing entry) and emits `dev.passage.close.yearend.completed.v1`. No opening journal is posted: the ledger's balances are cumulative from inception (no period 0, no opening flag), so an opening entry would double every balance sheet account; the opening proposal is stored on the run as a verification artifact. A run is `abandoned` (freeing the year) only when the ledger gave a definite refusal (400, 404, 422) or the request failed validation, on the call that first sent anything to the ledger; 401, 403, 429, 5xx, transport errors and conflicts leave it pending. The proposals are frozen in the store, with the run's dispatched mark, in a committed transaction before the first ledger write (the reversal of a re-run, or the closing entry), and a retry resends them verbatim under the same idempotency keys, so a closing entry the ledger accepted but never answered is replayed and recorded, never re-derived; a run whose earlier attempt may have been accepted and is then refused stays pending for an operator. A repeat of a completed request returns the stored run before any precondition is re-read. Ledger handoffs: the chart read uses `ledger.account.lookup` (#434, granted to close, seeded in `data.json`); the ledger has no allowed-group forwarding for an on-hold period, so close holds the flag duty `ledger.period.postclosed` in its grant to the ledger (the only service that does), signed only on the closing entry and the reversals of a re-run, which also makes a closed last period postable (a permanently closed one is refused up front, and the last period must have an `all` row closed or on hold). The ledger cannot restrict `postclosed` by source, so any future close posting path (accruals, allocations) must not set `PostClosed` by default. Fiscal years are calendar years. Not built: attaching `close.yearend.run` and `close.yearend.read` to a role (the duties are seeded and unattached, follow-up), and the cross-service contract test against the real ledger posting API (AC1), which this tree proves per service |
