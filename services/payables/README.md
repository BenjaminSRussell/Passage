# payables

Wave 19 deployable: accounts payable settlement and payments. This slice ships the settlement engine and a stateless preview endpoint. One Go module, one image (`payables`). Deferred deliverables are listed in `NOT-IMPLEMENTED.md`.

## Run and test

```
cd services/payables
go vet ./... && go test ./...
DATABASE_URL=postgres://... go run ./cmd/payables
```

## Test data

`testdata/xsd/` holds the official pain.001.001.09 and pain.002.001.10 schemas, vendored verbatim (`SOURCE.md` records origin, date and sha256; never edit them). `testdata/pain001/` holds one JSON input and one `.golden.xml` per bank profile; `testdata/pain002/` holds hand-written status reports. Regenerate the pain.001 goldens with `go test ./internal/domain -run Golden -update`; never edit a golden by hand. The XSD contract tests and the golden API tests need `xmllint` (libxml2-utils) on `PATH` and skip with an explicit message when it is absent.

## API

`POST /v1/payables/settlements:preview` (duty `settlement.read`), `GET /healthz`, `GET /readyz` (database ping, 503 when down), `GET /metrics` on the admin port. Contract: `api/openapi.yaml`.

`POST /v1/payables/payment-files:preview` (duty `payment-file.preview`) builds a pain.001.001.09 file from a JSON request (same shape as `testdata/pain001/*.json`; `created` defaults to the server clock; at most 2000 payments; `method.type` is limited to `TRANSFER` and `WIRE`, the only methods that render as pain.001, while bank profiles also accept `ACH`, `CHECK` and `CARD`), validates it against the vendored XSD and returns `content`, a `summary` (`paymentCount`, `controlSum`, `sha256`) and `validation`. `POST /v1/payables/payments/status:parse` (duty `payment-status.parse`) parses a pain.002.001.10 report (`content`) against the caller-supplied `messages` and `payments` into outcomes and unknown references. Both are stateless and persist nothing; the status parse does not replace the PRD's stateful `POST /payments/status:ingest`.

XSD validation runs `xmllint` (libxml2-utils) as a subprocess with `--nonet`, a minimal environment, a 10 second timeout and at most 3 concurrent runs. Only xmllint exit code 3 counts as an invalid document; any other failure is a 500. The service validates a known-good file at startup and refuses to start without `xmllint` on `PATH`; the Docker image is distroless (`distroless/cc-debian12:nonroot`) and carries `xmllint` plus its shared libraries copied from a digest-pinned `debian:12-slim` stage.

The preview settles one credit against open invoices per PRD FR-19.2: priority order, cash discount (pro-rated on partial settlement), realized FX gain or loss, write-off within the limit, and a balanced journal. Amounts, rates and percentages are decimal strings; rates come from the request until the wave 12 rate lookup exists. A cross-currency credit settles in the accounting currency, so its FX difference is zero by construction.

## Vendor aging and AP control reconciliation

`GET /v1/payables/aging` (duty `aging.read`) buckets open items (`open_amount`) by days past due at `as_of` (CURRENT, 1-30, 31-60, 61-90, 91-180, OVER-180) per currency, and per vendor with `group_by=vendor`. `GET /v1/payables/aging:reconcile` (duty `aging.reconcile`, required `ledger` query parameter) compares total open AP per currency with the AP control account in the ledger (credits minus debits from `GET /v1/ledger/balances` through the period of `as_of`) and returns the difference and a `reconciled` flag.

`group_by=vendorGroup` on `aging:reconcile` adds `vendorGroups`: per currency and vendor group code, the open AP of the subledger against the AP control balance of the ledger lines carrying that code as the `VENDGRP` dimension (#421, see below; `UNASSIGNED` last). The vendor group is stored on `ap_open_item.vendor_group_id` (migration 0006, nullable) from the optional `vendor_group_id` of `invoice.posted`; a vendor has one group in the party master (`party.vendor.vendor_group_id`, whose posting profile selects the control account), so no multi-group choice is made here (purchasing's multi-group memberships are pricing-only). Rows created before the migration, or from events without the field, are `UNASSIGNED`; redelivering the event with a group fills a still-empty group and never overwrites an assigned one. The aging report rejects `group_by=vendorGroup`.

Per-group control comparison (#421): receiving puts the party vendor group's short `vendor_group_code` on `invoice.posted` and posts it as the ledger dimension `VENDGRP` on the vendor-control credit; the consumer stores it on `ap_open_item.vendor_group_code` (migration 0014, nullable; a redelivery fills a missing code, never overwrites one). The payment run journal splits each vendor's control-account debit per item code and posts the same `VENDGRP` value, so a group's ledger balance falls with its own payments. `aging:reconcile?group_by=vendorGroup` reads `GET /v1/ledger/balances?group_by=VENDGRP` for the control account (credits minus debits per dimension value; a blank value is `UNASSIGNED`) and returns, per currency and code, the subledger total, ledger balance, difference and `reconciled`, plus `vendorGroupsReconciled` and `vendorGroupDimension`. A code with a ledger balance but no open items is listed with a zero subledger. A ledger that does not define `VENDGRP` (400) gives uncomparable lines with a reason; foreign-currency items make the lines uncomparable like the currency lines. `AP_VENDOR_GROUP_DIMENSION` (default `VENDGRP`, `-` switches it off) names the attribute. Items consumed before the code existed have no code and compare with the untagged ledger lines (`UNASSIGNED`). An item whose code was filled by a redelivery while its ledger line was posted without `VENDGRP` shows as a difference in its group, and the opposite in `UNASSIGNED`, until the ledger lines are realigned (ledger dimension realignment). The run journal names the attribute in `optionalDimensions`, so a ledger that does not define it drops the tags and posts the run as before; the per-group comparison starts once the ledger adds it (`PATCH /v1/ledger/ledgers/{id}` with `addDimensionAttributes: ["VENDGRP"]`). Because the split follows the item codes, a retry can differ from an earlier attempt that the ledger committed; the ledger then answers 409 `LEDGER_IDEMPOTENCY_CONFLICT` and the run records the entry it finds for the run document (lines compared as totals per account and side). A malformed `AP_VENDOR_GROUP_DIMENSION` stops the service at start.

Configuration: `AP_CONTROL_ACCOUNT` (default `2000`) and `LEDGER_URL` (unset: reconcile answers 503) and `LEDGER_TIMEOUT` (Go duration, default 3s). The ledger call forwards the caller's tenant, legal-entity, user and duty headers, so the caller needs `ledger.balance.read` and `ledger.journal.read` (a signed call carries only `ledger.balance.read` for the balance and `ledger.ledger.lookup` for the ledger fetch) (the ledger is fetched to confirm it belongs to the legal entity; a ledger 403 is returned as 403); a service identity (#226) will replace the forwarding. A ledger reports one currency in the accounting currency and includes translated foreign invoices, so other currencies are listed unreconciled and, while foreign-currency items are open, the ledger-currency line is marked `comparable: false` (reason `foreign-currency items require translation`) and the overall result is not reconciled. Reconcile at a period end: the ledger side is cumulative to the period, the open-item side is the current balance.

## Open-item API, FX valuation and payment proposals

`GET /v1/payables/open-items` and `GET /v1/payables/open-items/{id}` (duty `open-item.read`) read the open-item store. The list filters by `vendor`, `due_from`, `due_to`, `currency` and `status`, is ordered by due date then id and pages with `limit` (1 to 200, default 50) and the opaque `cursor` returned as `nextCursor`. Every request names its legal entity (`legal_entity` or the caller's single legal-entity scope); an unscoped caller without `legal_entity` gets 400, and an entity outside the caller's scope gets 403. With `value_in=USD` each item carries a `valuation` (open amount times the spot rate of today, rounded to the currency's minor unit).

Rates come from `GET /v1/fx/rates` of the fx service (`internal/fx`, same adapter shape as `internal/ledger`). With a service signing key (`PASSAGE_SERVICE_SIGNING_KEY[_FILE]`) the call carries a signed service token holding only `fx.rate.lookup` for the request's legal entity, so the caller needs no fx duty (#305); without a key it forwards the caller's headers and the caller needs `fx.rate.view`. A pair without a rate is a 422 (`PAY-0002`), a caller fx refuses is a 403, anything else is a 502.

`POST /v1/payables/payment-proposals` (duty `payment-proposal.write`) builds a payment proposal for a legal entity:

- Selection: open items with `due_date <= dueBy` (default `runDate`), status OPEN or PARTIALLY_SETTLED, not on payment hold (`ap_open_item.payment_hold`), vendor not in `ap_vendor_block`, and not already on a proposal. At most 5000 items; lower `dueBy` otherwise.
- Cash discount: `runDate` is the payment date and must not be earlier than today (UTC), so a backdated date cannot revive an expired discount; replaying an existing run stays allowed. Taken when `runDate <= discount_date`, the item is still OPEN (a partly settled item pays its full remaining amount) and the discount is below the open amount. `pay = open_amount - discount`.
- Grouping: per vendor, currency and payment method (`paymentMethod`, overridden per vendor by `vendorPaymentMethods`). Every group and line is valued in `legalEntityCurrency` at the spot rate of `runDate` (today when `runDate` is in the future); each line is rounded to the currency's minor unit before summing.
- Persistence: `ap_payment_proposal`, `ap_payment_proposal_group`, `ap_payment_proposal_line`, status DRAFT. A line keeps the item version it was selected at and the insert re-checks version, open amount, hold and vendor block, so an item that changed in between fails the whole proposal with 409 and nothing is written. An item can sit on one live proposal only (partial unique index over lines with `reserved`); `POST /v1/payables/payment-proposals/{id}:cancel` (duty `payment-proposal.write`, DRAFT only, audited in `cancelled_by`/`cancelled_at`) releases the lines while keeping them for audit, and releasing on execution is part of #102. A run with nothing due is a 422 and stores nothing.
- Idempotency: unique per (legal entity, `runDate`, `runId`). Repeating the identical request returns the stored proposal (200, `Idempotent-Replayed: true`) without selecting or valuing again; the same key with a different request is 409 `AP-PRP-001`.

`GET /v1/payables/payment-proposals` (duty `payment-proposal.read`) lists a legal entity's proposals without lines, newest run date first, filtered by `status`, `run_from` and `run_to`, with the same `limit` and `cursor` keyset paging as the open-item list. `GET /v1/payables/payment-proposals/{id}` (same duty) returns the proposal with groups and lines. `POST /v1/payables/payment-proposals/{id}:approve` (duty `payment-proposal.approve`) moves a DRAFT to APPROVED and requires a different user than the creator (`AP-PRP-003`); the table also carries a check constraint so no code path can store a self-approval. Approval locks each line's open item and re-checks version, open amount, hold, vendor block and status; a changed line is a 409 `AP-PRP-001` naming the items, and a run date before today (UTC) is a 409 `AP-PRP-004`, so an expired discount can never be approved. Creator and approver both need an identified user. The application role may update only the status and the approval and cancellation columns of a proposal, and a trigger allows only the transitions DRAFT to APPROVED or CANCELLED, APPROVED to EXECUTING, and EXECUTING to EXECUTED or FAILED (migration 0007), and a line is released only by cancelling or failing its proposal.

The employee-vendor register (#472) maps an HR worker to the party vendor that pays their expense reimbursements: `PUT /v1/payables/employee-vendors/{workerId}` (body `{vendorId, legalEntityId?}`, duty `employee-vendor.maintain`, an identified user) checks the vendor against the party vendor master, stores the mapping once per legal entity (`ap_employee_vendor`; the same vendor again is a 200 replay, another is 409 `AP-EMP-002`) and, in the same transaction, moves the worker's OPEN items still waiting for a payee to the vendor (bumping their version, as a payee change). `HandleExpenseReportApproved` creates the report's open item for the mapped vendor with the worker in `payee_worker_id` (also on the `openitem.*` events and `payeeWorkerId` on the item), or for the worker id with `payee_unverified` when none is registered; both calls take the same per-worker advisory lock, so an item created during a registration is never left behind. Expense publishes `report.approved` only after the report's liability (Dr expense, Cr AP control) is in the general ledger, so the run's AP control debit has its credit. With bank bindings on, proposal creation leaves unverified items out without calling party, stores them with the proposal (`excludedItems`, returned on the 201, the replay and GET) and counts each item once per process in `payables_payee_unverified_excluded_total`.

`GET /v1/payables/vendor-blocks` (duty `vendor-block.manage` or `open-item.read`; `legal_entity`, optional `vendor`) lists the blocks of a legal entity with reason, `blocked_by` and the time of the first block, at most 500. Payment holds and vendor blocks are written by `POST /v1/payables/open-items/{id}:hold` and `:release` (duty `payment-hold.manage`) and `POST /v1/payables/vendors/{id}:block` (body `{reason}`) and `:unblock` (duty `vendor-block.manage`). A vendor block is per legal entity (`ap_vendor_block` primary key tenant, legal entity, vendor; migration 0010 expanded old tenant-wide rows to one row per legal entity that has open items for the vendor, and drops blocks of vendors without open items): `legalEntityId` defaults to the caller's scope, an entity outside it is a 403, and a block in one entity never excludes another entity's items. A hold respects the caller's legal-entity scope (outside it the item is a 404), takes an optional `reason`, is stored with `payment_held_by`, and is refused with 409 `AP-OPN-001` on a SETTLED or REVERSED item. Each call needs an identified user, writes a structured `audit:` log line with the actor and, in the same transaction, an outbox event carrying the actor (`openitem.held/released`, `vendor.blocked/unblocked`); a hold that does not change emits nothing, counts nothing and logs no audit line, and unblocking a vendor that is not blocked is a 404. Neither a hold nor a block bumps the item version (the version moves only with the open amount); a held or blocked item is refused at approval and at run start because both re-read `payment_hold` and `ap_vendor_block`, and a hold that is released again leaves the proposal valid. Audit of every reader of `ap_open_item.version` (#317): proposal creation (`insertGroups`) and `verifyLines` compare `version` and test `payment_hold` and `ap_vendor_block` separately, so neither relies on a hold bumping the version; `settleTx` (and so `:settle`) uses it only as the optimistic lock on the amount and deliberately ignores a hold placed after the journal posted; the version is not in the `payables.openitem.*` event payloads and nothing outside this service reads it (the web app and workflow-ts never call the open-item routes). No consumer breaks. The approved proposal is the input of the payment run below; withholding tax is not applied.

Outbox events (same transaction as the change, subject and aggregate = the proposal id): `payables.paymentproposal.created/approved/cancelled.v1` with the actor, run date, run id and, on created, the valued total; cancel is the rejection path of the approval flow, there is no separate reject state. The vendor group of an open item that was created without one is assigned when the same `invoice.posted` is redelivered with it, emitting `payables.openitem.grouped.v1` once; concurrent redeliveries re-read the winner instead of failing. See `events/asyncapi.yaml`.

Metrics: `payables_payment_proposals_total{outcome}` (created, replayed, approved, self_approval_refused, cancelled), `payables_payment_holds_total{outcome}` (held, released, vendor_blocked, vendor_unblocked) and `payables_fx_rate_faults_total`.

## Payment runs (#102)

An APPROVED proposal is executed by a payment run, orchestrated by the Temporal `paymentRunWorkflow` in `services/workflow-ts` (retries, crash recovery) over idempotent payables endpoints. Duties: `payment-run.execute` (start, the step endpoints and `GET .../{id}/file`; separate from `payment-proposal.approve`) and `payment-run.read` (`GET /v1/payables/payment-runs/{id}`). Every call names a legal entity (fail-closed scope) and every table has tenant and legal-entity RLS.

Who decides what a run pays and where:

- Payee bank details are not part of a proposal and are never stored: `:generate-file` reveals them from the party vendor master (`GET /v1/party/vendors/{id}/bank-accounts:reveal`, service token `aud party`, only duty `party.vendor-bank.reveal`, one call per vendor) and builds the pain.001 from them; the sealed pain.001 file is the only copy. The vendor's single account in the group currency is used (holder, account number as IBAN when valid else other id, routing number, bank country as the creditor country; party carries no BIC or postal address yet, so structured-address bank profiles refuse with a clear error). An unknown vendor, no account in the currency, several accounts, or a missing holder/country is a terminal 422 `AP-RUN-017` naming the vendor; party unreachable is a retryable 502 `COM-0502` (`payables_payment_run_party_faults_total`). The account is bound at approval: `:approve` reveals each group's account, stores only the party account id, a keyed fingerprint (fieldcrypt `MAC` per tenant over the length-prefixed account number, routing number, holder and bank country, with the fieldcrypt key id used, so rotation keeps matching; no field keys means approval answers 503 and nothing is bound) and the last four digits on the group (set once, trigger-enforced; the approval response shows `bankAccountId` and `bankLast4`), and `:generate-file` re-fetches and refuses with `AP-RUN-017` when the id or fingerprint differs or was never bound (bank changed after approval: create and approve a new proposal). With payment runs enabled, approval answers 503 `COM-0503` when party (or the field keys) is not configured, so no unpayable approved proposal exists. A party refusal (400, 401, 403, missing signing key or scope) is a terminal 422 `AP-RUN-013` so the workflow stops instead of retrying; a tax refusal on a proposal is a 500 `COM-0500` (not a workflow step). Only transport errors and 5xx/408/429 are the retryable 502. Approval takes the per-vendor/currency/year advisory lock for every group, tracked or not. A creator's self-approval attempt reveals nothing. `creditors` on a proposal is now an unknown field (400). Migration 0012 drops `ap_payment_proposal_payee`.
- Withholding: a proposal request may carry `withholdingCodes` (vendor id to code). The codes (jurisdiction, income type, effective-dated rates, optional threshold, in the tax service's `codes` shape) and the `withholdingAccount` live in the legal entity's posting profile (`withholdingCodes`, `withholdingAccount`), so a creator picks among configured codes but cannot define rates; a stored per-vendor setting is a follow-up. Per line the tax service is called (`POST /v1/tax/withholding/calculate`, signed token, only duty `tax.withholding.calculate`) with the line's pay amount and `paid_to_date` = the vendor's year-to-date `pay_amount` in that currency over APPROVED, EXECUTING and EXECUTED proposals plus earlier lines of this proposal (drafts are not counted, so each group stores the external base it used and `:approve` recomputes it under a per-vendor advisory lock: if another proposal for the vendor was approved meanwhile the approval is a 409 `AP-PRP-001` and a new proposal is needed). `withheld` and `withholdingCode` are stored per line, `withheld` per group, `net` and `valued` are net of tax, `totalWithheld` and the `total_withheld` created-event field report the total per group currency (a map, never summed across currencies). The run pays the net, credits the withholding account in the journal (needs `withholdingAccount`, else 422 `AP-RUN-013`) and settles the item in full. Unknown code or a tax rule refusal is 422 `AP-PRP-006`; tax unreachable is a retryable 502; `TAX_URL` unset is a 503 for proposals with codes. Config: `PARTY_URL`/`PARTY_TIMEOUT` and `TAX_URL`/`TAX_TIMEOUT`, both requiring the service signing key.
- The ledger, the bank, control and discount accounts and the paying bank account come from the legal entity's posting profile (`PAYABLES_POSTING_PROFILES`), never from a request. The profile is snapshotted onto the run at start (accounts in columns, the paying bank file settings sealed with fieldcrypt) and every later step uses the snapshot. The generated pain.001 is also stored sealed (tenant, run id and field bound), because it carries the payees' full account numbers.
- The executor must be neither the creator nor the approver of the proposal, compared case- and whitespace-insensitively, at start (API 403 `AP-PRP-003` and a trigger on `ap_payment_run`) and on every step and `GET .../file`. `GET .../file` carries full bank details, so it needs the execute duty and every read logs `audit: payment file read` and counts in `payables_payment_file_reads_total`.
- Only groups in the legal-entity currency run, TRANSFER or WIRE only; foreign-currency groups are a 422 until realized FX gain or loss is built.

Steps:

- `POST /v1/payables/payment-runs` `{legalEntityId, proposalId}` starts the run: idempotent per (legal entity, proposal) with `Idempotent-Replayed` on 200 (also after the run date; a new start needs `runDate >= today`, else 409 `AP-PRP-004`). It locks the proposal, moves APPROVED to EXECUTING and re-verifies every line. A changed line (hold, vendor block, version, amount) makes the run FAILED, the proposal FAILED and releases its lines in the same transaction.
- `:generate-file` re-verifies the lines (a hold placed since start is a 409 `AP-RUN-015`, and the workflow then fails the run before any journal), builds one pain.001.001.09 payment per group (end-to-end id `P-<group id>`, remittance = the invoice numbers), validates the XSD and stores the file, its sha256 and one `ap_payment` row per group (a group is paid once, ever). Terminal 422 on a bank or XSD failure.
- `:post-journal` first records `journal_requested_at` under the run lock, then calls the ledger through `POST /v1/ledger/journal-entries` with `Idempotency-Key: payables:payment-run:<run id>` and a service token carrying only `ledger.entry.post` for the run's legal entity: debit the control account per group at gross valued amounts, credit the bank account the paid valued total and the discount account the difference. A reply lost after the ledger committed is replayed by the ledger's idempotency; a 409 `LEDGER_IDEMPOTENCY_IN_PROGRESS` (a slow first post still running) is a retryable 502, never a failure. Only a ledger 400 or 422 is a definitive business rejection, and before recording it payables looks the run's entry up by document id (`GET /v1/ledger/journal-lines?ledger=&documentId=<run id>&limit=1`, token duty `ledger.entry.lookup`): an entry found there is the journal (a ledger deploy that tightened validation between attempts cannot reject a post that already committed) and is recorded as posted; a failed lookup is a retryable 502 that records nothing; with no entry the rejection is recorded (`journal_rejected_at`), answers 422 `AP-RUN-014`, and the journal can never be requested again. Every other answer (401, 403, 404, 408, 429, a 409 of either kind, 5xx, a transport error) is a retryable 502 that records nothing, because the first post may have committed with its reply lost. Posting needs a signed ledger client: with `LEDGER_URL` but no signing key payment runs are disabled at startup with a warning.
- `:fail` (reason required, at most 500 bytes) marks run and proposal FAILED and releases the lines. It is refused (409 `AP-RUN-011`) once the journal was requested, unless the ledger definitively rejected it and nothing posted; the proposal and run triggers enforce the same, and the journal columns cannot be cleared once set. `journal_rejected_at` is frozen the same way (migration 0008): it can be set only while `journal_requested_at` is set and `journal_posted_at` is not, a check constraint requires a requested journal, and the application role cannot clear or move it, so it cannot be used to unlock `:fail`. The executor check (neither creator nor approver) also applies to a replayed start: a creator or approver replaying the start gets 403 `AP-PRP-003`, not the run. Each step's executor check reads only the proposal's creator and approver, never the encrypted payee details; a proposal read, file or payee call without field keys is a 503 `COM-0503`.
- `:settle` settles every unsettled proposal line in one transaction (open amount reduced, PARTIALLY_SETTLED or SETTLED, version bumped, `payables.openitem.settled` event with the run id as settlement id). `:complete` marks the run COMPLETED and the proposal EXECUTED.

A proposal carries `paymentRunId` once a run starts from it (derived from `ap_payment_run.proposal_id`, at most one run per proposal), so an EXECUTING, EXECUTED or FAILED proposal links back to its run.

Remittance advice (#528): `GET /v1/payables/payment-runs/{id}/remittances/{vendorId}` (duty `payment-run.read`) lists, for a COMPLETED run, each payment to the vendor and the invoices it settled (invoice number and date, open amount, discount taken, tax withheld, amount paid); the lines of a payment add up to its amount. It carries no bank details. A run that is not completed is a 409 `AP-RUN-018`, a vendor the run did not pay a 404. `?format=csv` answers the same as a CSV download (formula-like cells prefixed with an apostrophe). This service renders no PDF: the web app builds one per payment from the JSON and sends it to the print service's `POST /print/v1/documents:render` as document type `REMITTANCE_ADVICE`. The print service accepts purchase orders, customer invoices and packing slips only, so that call is refused with `PRN-0008` until the print service adds the type; the CSV does not depend on it.

Each step locks the run row, so concurrent duplicates serialise; a step already done returns the run unchanged. Steps must run in order (409 `AP-RUN-012`). The workflow retries `generate-file` five times and then fails the run; `post-journal`, `settle` and `complete` retry for 24 hours while the failure is retryable (a payables 401 or authorization 403 is retryable, a business 403 is not). When those retries end after the journal was requested the workflow counts `passage_payment_run_stuck` (Temporal SDK metric) and fails visibly. The workflow authenticates with a short-lived Ed25519 service token (#303) whose only duty is `payment-run.execute` and whose actor is the user who started the run.

Metrics: `payables_payment_runs_total{outcome}` (started, replayed, completed, failed), `payables_payment_run_ledger_faults_total`, `payables_payment_file_reads_total` and `payables_payment_run_stuck_total`.

Alert: page on `increase(payables_payment_run_stuck_total[5m]) > 0`. It counts a settle step that found an open item changed after the journal posted: the money is posted and nothing is settled, the run stays RUNNING and the structured error log `payment run stuck` carries the run id. Resolve by hand: inspect the named item, then either reverse the journal in the ledger (the run cannot do that yet) or settle the item against the run, and complete the run.

Opening items (#49): `POST /v1/payables/opening-batches` (duty `opening-item.import`, service-only, granted to `migration-factory`) loads a cutover batch of open vendor items for one legal entity, all or nothing: per-row validation, vendors checked against the party vendor master, integer minor units, and a declared total per currency that must match. A batch is idempotent per `batchKey` (replay 200, other content 409) and an item per `reference` per legal entity (`ap_open_item.opening_batch_id`, `opening_reference`). Items are ordinary OPEN items, listed and payable in proposals, and post nothing to the ledger (the GL opening journal carries the AP control balance); no `openitem.created` event is emitted for them. `GET /v1/payables/opening-batches` (duty `opening-item.import.read`) reads back each batch's item count and totals from the stored items.
