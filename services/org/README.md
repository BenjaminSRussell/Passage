# org

Organization service for Passage (wave 6). Slice 1 ships legal entities, the pure hierarchy as-of logic and unit-of-measure conversion. Create also writes `dev.passage.org.legalentity.created.v1` to the `outbox` table in the same transaction (an Idempotency-Key replay writes none), and PATCH writes `dev.passage.org.legalentity.updated.v1` with `{id, changed_fields, version}` in the same transaction when a value changed; operating units write `dev.passage.org.operatingunit.created.v1` on create and `dev.passage.org.operatingunit.updated.v1` on a version bump the same way; sites, which are legal-entity-scoped, write `dev.passage.org.site.created.v1` and `dev.passage.org.site.updated.v1` the same way; warehouses, which take their legal entity from their site, write `dev.passage.org.warehouse.created.v1` and `dev.passage.org.warehouse.updated.v1` the same way; locations, which take their legal entity from their warehouse, write `dev.passage.org.location.created.v1` on create; postal addresses write `dev.passage.org.address.changed.v1` on create, take their region and postal-code rules from the seeded `country` rows, and go through a geocoder that is a null adapter until a real one is configured; an address PATCH closes the current version, inserts the next and emits `address.changed` for it, and documents read a version by id; a site cannot be deactivated while an active warehouse references it; events are declared in `events/asyncapi.yaml`. Everything else is listed in `NOT-IMPLEMENTED.md`.

Run: `DATABASE_URL=postgres://... MIGRATE_ON_START=true go run ./cmd/org`. Test: `go vet ./... && go test ./...`; store tests need `PASSAGE_TEST_DATABASE_URL` (role without BYPASSRLS).

## Reference data

Countries, currencies, regions and languages are platform-owned rows under the `sys` tenant (`00000000-0000-0000-0000-000000000000`): every tenant can read them, no tenant can insert, update or delete them. The data lives in `migrations/reference/countries.csv`, `currencies.csv`, `regions.csv` and `languages.csv`, embedded as `migrations.Reference`, and `store.SeedReference` loads it after the migrations when `MIGRATE_ON_START=true`. Regions cover US, CA, IN and MX as full ISO 3166-2 codes (`US-CA`). A malformed row fails the whole file with `<file> line <n>: <reason>`; re-running the seed changes nothing. Tenants never edit the `sys` rows: `PATCH /v1/org/{collection}/{code}` deactivates or reactivates a row for the calling tenant only, by writing `reference_status`, and every read returns the tenant's effective status.

Units of measure and their conversions are seeded the same way from `migrations/reference/units.csv` (59 units) and `uom-conversions.csv` (49 conversions) into `unit_of_measure` and `uom_conversion`. Units fall in twelve classes: the eight of FR-6.8 (`quantity`, `each`, `mass`, `length`, `volume`, `area`, `time`, `temperature`) plus `energy`, `pressure`, `power` and `speed`, which the AC-6.3 fixture needs. A conversion is stored once per unordered pair (a unique index on the sorted codes), and the inverse is computed. `store.SeedConversions` checks both files together before any write: unknown unit, two classes in one pair and a reversed duplicate fail with `uom-conversions.csv line <n>: <reason>`. `GET /v1/org/uom/convert` reads the persisted set per request through `store.ConversionGraph` (the caller's visible, active units and their conversions, at most two hops inside one class) and returns `quantity` rounded to 12 decimals plus `displayQuantity` rounded to the target unit's `decimal_precision` (BR-6.8); an unknown or inactive unit returns `ORG-UOM-NO-PATH`. The unit routes list and read units (`GET /v1/org/uom/units`, `…/{code}`; codes are case-sensitive), add a tenant-owned custom unit (`POST`, code `^[A-Za-z0-9/%]{1,10}$`, precision 0 to 6, optional `Idempotency-Key`) and deactivate or reactivate any unit for the calling tenant (`PATCH …/{code}`). Unit status for platform and tenant units lives in `reference_status` with kind `uom`, so a platform unit deactivated by one tenant stays active for the others; units are never deleted. `GET /v1/org/uom/conversions` is the Unit conversions report: every platform and tenant conversion visible to the caller with `inverseFactor`, `inverseOffset` (`1/factor` and `-offset/factor`, rounded to 12 decimals for display only, never stored; BR-6.8), `roundTrip` (converting 1 there and back equals 1 at 12 decimals), `system`, a `status` that is `inactive` when either unit is inactive for the caller, and the filters `class`, `unit` (either side, case-sensitive) and `status`. `POST /v1/org/uom/conversions` adds a tenant-owned conversion (`fromCode`, `toCode`, `factor` greater than 0, optional `offset`, at most 16 integer digits and 12 decimals, optional `Idempotency-Key`): both units must exist and be active and share a class, and the unordered pair must not already be converted by a platform or tenant row; `convert` uses the new row at once, and it is invisible to other tenants. Conversions are deactivated through their units, never deleted.

## Fiscal calendars

`domain.GenerateYear` builds the periods of one fiscal year for the patterns `calendar`, `4-4-5`, `4-5-4`, `5-4-4`, `13-period` and `custom`, with optional opening, closing and special (adjustment) periods, and `domain.ProveContiguous` proves they tile the year (`ORG-CAL-GAP`, `ORG-CAL-OVERLAP`, `ORG-CAL-PATTERN`). A year is labelled by the calendar year of its nominal start. Week-based years end on the last day of the week nearest to the nominal year end (the NRF retail-calendar rule), so they have 364 or 371 days and the 371-day year puts its extra week in the last period (`week53`). The golden CSVs are in `testdata/fiscal-patterns/`. 

Teams are tenant-level and persisted in `team_type` and `team` (migration 0021). `POST /v1/org/team-types` (duty `org.operating-unit.write`, `Idempotency-Key`) creates a team type that states which member kinds, user or party, its teams may hold; a replay returns the stored row with 201 and is not counted, and a key reused with another body is 422 `idempotency_key_reuse`. `POST /v1/org/teams` (same duty, `Idempotency-Key`) creates a team of a team type with an optional active operating unit and an inclusive `effectiveFrom` to `effectiveTo` date range; `GET /v1/org/teams` lists teams in code order with `teamTypeId`, `operatingUnitId`, `status` and `asOf` filters, and `GET /v1/org/teams/{id}` reads one. A tenant holds at most 5,000 teams. `domain.TeamInForce` is the in-force rule shared with the `asOf` filter. Team members are persisted in `team_member` (migration 0022). `POST /v1/org/teams/{id}/members` (duty `org.operating-unit.write`, `Idempotency-Key`) adds a manual member of kind user or party with a role of member or lead and an inclusive `validFrom` to `validTo` range; the kind must be allowed by the team type, and BR-6.12 (`domain.MemberRangeViolation`) refuses an ended team (`ORG-TEAM-EXPIRED`) and a validity outside the team's range (`ORG-TEAM-MEMBER-RANGE`; a bounded team needs a bounded `validTo`). A team holds at most 2,000 members in force (`ORG-TEAM-MEMBER-LIMIT`). `GET /v1/org/teams/{id}/members` lists them in insertion order with `asOf`, `memberKind` and `memberRole` filters. An add writes `dev.passage.org.teammembership.changed.v1` (`team_id`, `added`, an empty `removed`, `as_of`) in the same transaction; the type collapses `org.team.membership.changed` because the kernel allows three segments. `PATCH /v1/org/teams/{id}` (duty `org.operating-unit.write`, body `version` required, optional `name`, `description`, `operatingUnitId`, `effectiveTo` and `status`; `""` clears `description`, `operatingUnitId` and `effectiveTo`) is the optimistic-version update: a stale version is 409 `ORG-VERSION-CONFLICT`, a patch that changes nothing returns the stored team with the same version, and `code`, `teamTypeId` and `effectiveFrom` are not patchable, so a body carrying any of them is 400 `COM-0001`. `status` `inactive` deactivates a team and `active` reactivates it; adding a member to an inactive team is 422 `ORG-TEAM-INACTIVE` (a replay of an earlier add still returns the stored row), while ending and removing members stay allowed so an administrator can clean the team up. Setting or moving `effectiveTo` earlier is refused with 422 `ORG-TEAM-MEMBER-RANGE` on `effectiveTo` while members are valid after it ("N members are valid after {date}; end them first."), and an `effectiveTo` before `effectiveFrom` is 400 `COM-0001`. `POST /v1/org/teams/{id}/members/{memberId}:end` (body `validTo`, `{memberId}` is the member row id) can only shorten or close a member's validity: a `validTo` before `validFrom` or after the current end is 422 `ORG-TEAM-MEMBER-RANGE` and re-sending the current end changes nothing. `DELETE /v1/org/teams/{id}/members/{memberId}` (204) deletes a manual member entered in error; a rule-sourced row is 422 `ORG-TEAM-MEMBER-RULE-SOURCED`. Both write `dev.passage.org.teammembership.changed.v1` with an empty `added` and the member in `removed`; `as_of` is the day after `validTo` for an end (the first day the member is no longer in force), the row's `validFrom` for a removal, and `validFrom` for an add. `GET /v1/org/teams?memberId=` lists the teams that have a member row for that id, once each, and with `asOf` only teams where that member row is in force on the date. Membership rules (job ORG-J5) and the BR-6.12 stewardship reassignment on deactivation are not built.

Calendars are tenant-level and persisted in `fiscal_calendar` and `fiscal_period`. `POST /v1/org/fiscal-calendars` (duty `org.fiscal-calendar.write`, `Idempotency-Key`) creates one with the defaults `startMonth` 1, `weekStart` `monday`, `openingClosing` true and `specialPeriods` 0; `GET /v1/org/fiscal-calendars/{id}` reads it. `POST /v1/org/fiscal-calendars/{id}:generate` with `{fiscalYear, force?, periods?}` writes the year's periods and emits `fiscalcalendar.generated` (201, `generated` true). Calling it again for the same calendar and year is a replay: 200, `generated` false, the stored periods, no write and no event. `force` replaces the rows and emits a second event, but first asks the `PostingChecker`: postings answer 409 `ORG-CAL-LOCKED`, a checker failure answers 503 `COM-0503`. Until the ledger exists the checker reports no postings. `periods` is required for a `custom` calendar and rejected for any other pattern (`ORG-CAL-PATTERN`). `GET /v1/org/fiscal-calendars/{id}/periods?fiscalYear=` returns the periods in order 0, operating, adjustment, 99. `GET /v1/org/fiscal-calendars` lists the calendars in code order (`status`, `pattern`, `limit`, `cursor`); every calendar carries `generatedYears`, the ascending fiscal years that have periods, so a picker can tell which calendars a legal entity may use (an empty array when none). `PATCH /v1/org/fiscal-calendars/{id}` (duty `org.fiscal-calendar.write`, not for legal-entity-scoped callers) takes `version` and optional `name` and `status`; `code`, `pattern`, `startMonth`, `weekStart`, `openingClosing` and `specialPeriods` shape the generated years and are immutable, so a body carrying one is 400 `COM-0001`. Setting `status` `inactive` while active legal entities are assigned to the calendar is 409 `ORG-CAL-IN-USE`; generating a year that does not exist yet on an inactive calendar is 422 `ORG-CAL-INACTIVE`, while a replay of an existing year still answers 200. A legal entity is assigned a calendar through `PATCH /v1/org/legal-entities/{id}` with `fiscalCalendarId` (`""` clears): the calendar must be active and have at least one generated year, otherwise 422 `ORG-LE-CALENDAR-INVALID`.

A site follows its legal entity's calendar unless it carries its own: `POST /v1/org/sites` and `PATCH /v1/org/sites/{id}` take an optional `fiscalCalendarId` (`""` clears it on PATCH) under the same rule, otherwise 422 `ORG-SITE-CALENDAR-INVALID`, and a change is reported as `fiscal_calendar_id` in `site.updated` `changed_fields`. `GET /v1/org/legal-entities/{id}/fiscal-period?date=YYYY-MM-DD` and `GET /v1/org/sites/{id}/fiscal-period?date=YYYY-MM-DD` (duty `org.read`) return the period containing the date as `{legalEntityId, calendarId, source, period}` (the site route adds `siteId`), where `source` is `site` when the site has its own calendar and `legalEntity` otherwise. Only `operating` periods are returned: opening period 0 and closing period 99 are single days that overlap the first and last operating period, and adjustment periods are not posting dates, so 1 January resolves to period 1 and 31 December to the last operating period (12 or 13, `week53` on a 53-week year). The lookup filters by period type, not number, so 12- and 13-period calendars behave alike. An inactive calendar still resolves, because postings into historic periods must still map. A date in a year that is not generated is 404 `ORG-CAL-PERIOD-NOT-FOUND`, no calendar on the entity (or on the site and its entity) is 422 `ORG-LE-NO-CALENDAR`, and a missing or malformed `date` is 400 `COM-0001`. The reads write no event. Deactivating a calendar is refused with `ORG-CAL-IN-USE` while active sites hold it too: "Fiscal calendar {code} is assigned to N active legal entities and M active sites."

## Default warehouse

`POST /v1/org/sites` can carry `defaultWarehouse` (`code` and `name` validated like `POST /v1/org/warehouses`, field errors under `defaultWarehouse.*`). The site, the warehouse (same legal entity, `type` defaulting to `standard`, `timeZone` to the site's) and `site.default_warehouse_id` are written in one transaction, with `site.created` (carrying `default_warehouse_id`) then `warehouse.created` in the outbox; a duplicate warehouse code rolls everything back with 409 `ORG-WH-CODE-DUPLICATE`, and an Idempotency-Key replay returns the original site and writes nothing. `PATCH /v1/org/sites/{id}` re-points the default with `defaultWarehouseId` (an active warehouse of that site, otherwise 422 `ORG-SITE-DEFAULT-WAREHOUSE-INVALID`; `""` clears it) and reports `default_warehouse_id` in `site.updated` `changed_fields`. While a warehouse is its site's default, `PATCH /v1/org/warehouses/{id}` refuses `status` inactive and a different `siteId` with 422 `ORG-WH-IS-DEFAULT`; clear or re-point the default first. `org_site_default_warehouses_total` counts sites created with a default warehouse; replays are not counted.

## Hierarchies

Hierarchies are tenant-level configuration, scoped by tenant only. `POST /v1/org/hierarchy-types` creates a type with its purposes. `POST /v1/org/hierarchy-types/{id}/versions` opens a draft version; a type has at most one open draft (`ORG-HIER-DRAFT-EXISTS`), and the draft starts as a copy of the type's latest published version, or empty when none exists. `PUT /v1/org/hierarchy-versions/{id}/nodes` replaces the draft's whole node set under the optimistic `version` lock; published versions are immutable.

Every node set is checked structurally before it is stored: at most 50,000 nodes, each org unit once, known parents, no cycle, exactly one root and at most 15 levels. `POST /v1/org/hierarchy-versions/{id}:publish` (body `version`, `effectiveFrom`, optional `reason`; `Idempotency-Key`) publishes a draft. The version must come after the type's latest published version (`ORG-HIER-OVERLAP`), which is superseded with its range closed at `effectiveFrom`; the stored node set is re-validated, and the closure table (one row per ancestor-descendant pair, no self pairs) is written in the same transaction as the `dev.passage.org.hierarchyversion.activated.v1` event. A publish with `effectiveFrom` before today (UTC) is backdated: it needs the `org.hierarchy.backdate` duty, a type with `backdateAllowed` and a `reason` of 10 to 500 characters, or it is refused with `ORG-HIER-BACKDATE-DUTY` before any state changes. `GET /v1/org/hierarchy-types/{id}/as-of?date=&node=` returns the node's parent, ancestors and descendants in the non-draft version in force on that date; superseded versions answer for dates inside their closed range.

## Web module

`apps/web/src/modules/org/` (id `org`, title Organization) serves `/org`, `/org/legal-entities`, `/org/operating-units`, `/org/sites` and `/org/warehouses`. `LegalEntityProvider` loads the active legal entities once, restores the choice stored under `localStorage` key `passage.org.legalEntity` while it still names an active entity, and offers the read-only `ALL` scope only with the duty `org.switcher.all_scope`. `LegalEntitySwitcher` (label "Legal entity") sits in the module header. Every request goes through `orgFetch`, which sends `X-Passage-LegalEntity: <id>` for one entity, or `X-Passage-LegalEntity-Scope: ALL` on GET for `ALL` and never on a write; the list pages also pass `legalEntityId` as a filter and drop responses from a superseded scope.

## Address search and history

`GET /v1/org/addresses?q=` matches the text as a literal, case-insensitive substring of the formatted address (`%`, `_` and `\` match themselves), served by the `postal_address_formatted_trgm` GIN trigram index from migration 0026, which creates the `pg_trgm` extension. `q` is trimmed and must be 3 to 100 characters; with `q` the owner filter is optional, but `ownerType` and `ownerId` come as a pair. Only current versions are searched. `GET /v1/org/addresses/{id}?asOf=` returns the version in force on that date (`validFrom` on or before it, `validTo` after it), a date before the first version is 404, and purposes are always the address's current purposes. `GET /v1/org/addresses/{id}/versions` lists every version newest first.

## Name translations

Legal entities, operating units, sites and warehouses can carry a translated name per language tag (`fr`, `fr-CA`), stored in `org_unit_translation` (primary key tenant, owner type, owner id, language). Routes exist for each owner collection (`legal-entities`, `operating-units`, `sites`, `warehouses`) and take the owner's write duty (legal entities `org.legal-entity.write`, operating units `org.operating-unit.write`, sites and warehouses `org.site.write`).

- The primary subtag of the language must be an active row of `language` for the tenant, else 422 `ORG-TRANSLATION-LANGUAGE-INVALID`. The check runs on write only, so a language deactivated later still resolves.
- `GET …/{id}/name?language=fr-CA` resolves the name: the exact tag, then its primary subtag (`fr`), then the base name. `source` is `translation` or `base`; `language` names the tag that matched and is absent for the base name. A region-only translation (`fr-CA`) is never used for a plain `fr` request.
- An inactive owner still accepts and serves translations, because documents for history keep printing its name.
- Names are trimmed and capped at 120 characters (counted in runes), the same as base names; the PRD's text(100) is a recorded deviation.
- A PUT that creates returns 201, one that replaces returns 200, and an identical repeat returns 200 and changes nothing.
- No outbox event is emitted: PRD §1.6.5 lists none for translations, so consumers read the name route.
- Owners outside the caller's tenant or legal-entity scope answer with the owner's own 404. Operating units carry no legal entity, so scoped callers can maintain their translations.
