# receiving

Wave 18 deployable: receiving, product receipts and three-way match. One Go module, one image (`receiving`). Delivered so far: the pure domain, the policy tester endpoint, the Postgres receipt store, and the HTTP surface for arrivals, direct receipts, registration, posting, correction, cancellation, receipt and GR/IR inquiry and vendor invoice posting, subsequent debits and credits, invoicing plan settlement and consignment settlement, with `receipt.posted`, `receipt.corrected`, `invoice.posted`, `invoice.adjusted` and `settlement.posted` written to the outbox in the same transaction (`events/asyncapi.yaml`). Deliverables 2 to 7 and the one-time payee invoice are open; see `NOT-IMPLEMENTED.md`.

## Run and test

```
cd services/receiving
go vet ./... && go test ./...
DATABASE_URL=postgres://... MIGRATE_ON_START=true go run ./cmd/receiving
```

Store tests run only when `PASSAGE_TEST_DATABASE_URL` is set, against a role without BYPASSRLS. API tests use `internal/store/memstore`, which a parity test checks against Postgres.

## Behaviour notes

- Over-delivery and tolerance percentages are percent values (2.0 means 2 percent).
- Line currency differing from the PO currency yields `PRICE_VARIANCE` with `currencyMismatch: true`.
- The header status is the worst line status; `TOTAL_VARIANCE` outranks all line statuses. Postings are produced only when the header is `MATCHED`.
- GR/IR clearing is pro-rata at the receipt-side amount; the final invoiced quantity clears the exact remainder, so a fully invoiced line leaves 0.00.
- Receipt numbers are `RCV-%08d`, allocated per tenant; a failed arrival or direct receipt burns no number.
- Posting idempotency keys: `post:receiving:productreceipt:<id>:receipt`, `post:receiving:productreceipt:<id>:correction:<seq>`, `post:receiving:productreceipt:<id>:cancel`, `post:receiving:vendorinvoice:<id>:invoice`. The invoice id derives from tenant, vendor and invoice number, so a retry after a failed commit reuses the ledger key.
- Every ledger post is first recorded in `receiving_pending_posting` (key, journal, hash) in its own committed transaction and marked done in the main one. While a posting is unfinished, any other ledger-posting command for the same receipt or invoice, or the same key with a different body, returns RCV-IDM-001; repeating the original request completes it. A definite ledger rejection (closed period) releases the row. `LEDGER_IDEMPOTENCY_CONFLICT` from the ledger also maps to RCV-IDM-001.
- Money and quantities are accepted as JSON numbers or as decimal strings (`"2.50"`); strings are validated as plain decimals.
- `:correct` and `:cancel` take an optional `postingDate` (default the receipt date, never earlier). When a correction brings a line to its invoiced quantity the amount becomes the cleared amount, so no rounding residual is left on the closed GR/IR item.
- A correction changes quantities on a POSTED receipt and leaves it POSTED; it cannot go below the invoiced quantity or to zero, and serial-tracked lines are refused. Cancelling a POSTED receipt reverses the ledger entry and closes its GR/IR items at zero; a cancelled receipt keeps its packing slip.
- Subsequent debit and credit (`invoice-adjustments:post`) is value only: it references lines of a posted invoice, never changes GR/IR items or quantities, and posts to the difference account that line used (inventory, or PPV for a `standardCost` line) against vendor control. GR/IR is not touched because the invoice already cleared it by quantity at the receipt value; only the price difference is adjusted. A credit may not exceed invoiced amount + earlier debits - earlier credits on the line (`AP-CRD-001`), counted across the lines of the request and serialised per original invoice. The ledger key is `post:receiving:invoiceadjustment:<id>`, so a retry as the other kind meets the first posting instead of posting a second one; the id derives from tenant, original invoice and document number, which is unique per invoice ignoring case.
- Invoicing plan settlement (`plan-settlements:run`) takes one purchase order, reads its plans from purchasing and settles OPEN rows due on or before `postingDate` as Dr GR/IR / Cr vendor control (an invoice before receipt leaves a GR/IR debit that the receipt posting later offsets; the per-receipt GR/IR open items do not carry it). Plans without `settleWithoutReceipt` are skipped (`AWAITS_RECEIPT`). Settlement is recorded once per (order, line, row) in `receiving_settlement`; purchasing keeps the row OPEN because it has no endpoint to mark it INVOICED (#289). To keep that from paying twice, a PO line (order and product, because receipts carry no PO line number) with PLAN_ROW settlements refuses invoices against its receipts (`AP-PLN-001`), and the run skips a line that already has invoiced GR/IR quantity (`LINE_INVOICED`); both checks take the same per-line advisory lock inside the posting transaction.
- Consignment settlement (`consignment-settlements:run`) turns each POSTED inventory `OWNERSHIP_CHANGE` journal of the legal entity into Dr consignment accrual / Cr vendor control, using the accrual account and amount of the journal's GL entry, once per journal. The inventory vendor is the owner text, so `receiving_settlement.vendor_id` is text. A journal whose amount is zero is skipped (`NO_AMOUNT`) and listed again on every run.
- Evaluated receipt settlement (`ers-settlements:run`, FR-18.10 minus the consumer and the self-billing document) scans the OPEN GR/IR items (nothing invoiced yet) of a vendor and/or purchase order and, for each POSTED receipt of an ERS vendor, posts one self-billed invoice `ERS-{receipt number}` through the same store path as `invoices:post`: every open line at the received quantity times the PO line's net unit price (read through the purchasing adapter with the caller's identity; the PO line is the usable line with the receipt line's product, none or several skip the receipt), Dr GR/IR at the receipt value, the difference to inventory, Cr vendor control. The ERS flag lives in receiving (`receiving_ers_vendor`, set with `PUT /v1/receiving/ers-vendors/{vendorId}`) because neither purchasing nor party has one. It is a run and not a `receipt.posted` consumer: `consumer_inbox` has no consumer in this service yet, so a scheduler calls the run. Because the invoice is an ordinary invoice, the exclusion with normal invoicing and plan settlement is the existing one: the GR/IR row lock and the per-PO-line advisory lock make an ERS-settled line over-invoice (`AP-QTY-001`) for a manual invoice, a manually invoiced line is not listed as OPEN, a plan-settled line is skipped (`PLAN_SETTLED`), and a plan run skips an ERS-settled line (`LINE_INVOICED`). Idempotent per receipt: the invoice number is unique per vendor (`ALREADY_SETTLED`). Not done: tax, the self-billing document to the vendor, BR-18.9 (block when the PO price changed since receipt), standard-cost lines (price differences always go to inventory), and the 10 s latency target.
- Vendor invoice capture (FR-18.1 to FR-18.3, partial): `POST /v1/receiving/invoice-captures` stores a draft that posts nothing. Format `UBL` parses a UBL 2.1 Invoice with the standard library (a DOCTYPE is refused); format `OCR` hands a PDF or image to `domain.DocumentExtractor`, which `cmd/receiving` does not wire (no OCR provider is chosen), so it answers 503 `COM-0503` until a provider adapter is set in `api.Ports.Extractor`; tests use `domain.FakeExtractor`. A capture is `CAPTURED` or `NEEDS_REVIEW` (confidence below 0.80, total off the line sum by more than 0.01, or no vendor tax id); the same document (SHA-256) in a legal entity answers 200 with the existing capture. A person turns a capture into an invoice with `invoices:post`; there is no automatic posting. Peppol transport is wave 35.
- Service entry sheets (FR-18.12, partial): `POST /v1/receiving/service-entry-sheets` enters a sheet against lines of an APPROVED or CONFIRMED purchase order in the caller's legal entity (vendor and currency from the PO, amounts rounded to the currency's minor units). The PENDING and ACCEPTED sheets of one PO line may not exceed its value, quantity times net price (`AP-SES-001`, serialised per PO by an advisory lock). `:accept` and `:reject` (reason required) are under `ServiceEntryAccept`; the user who entered the sheet cannot decide it (`AP-SES-002`), a decided sheet cannot be decided again (`AP-SES-003`), and a rejected sheet frees its amounts. Each decision writes `receiving.serviceentrysheet.decided.v1`. An accepted sheet does not yet create a GR/IR item or invoice: see NOT-IMPLEMENTED.md.
- One-time payee invoices (FR-18.19, partial): `POST /v1/receiving/one-time-payees` records the payee of an invoice for the legal entity's one-time vendor account. Name, address, tax id, email and bank account are encrypted with `platform/go/fieldcrypt` (per-tenant data key by HKDF from the service key, tenant and field as additional data); `passage_app` can update only the sealed columns and the erasure markers, never delete (`0018`). An optional `subjectRef` (opaque data-subject id) links a payee to compliance erasure commands. `POST /v1/receiving/invoices:post` takes `oneTimePayeeId`; the payee id (never its data) is on the invoice, `invoice.posted` and `invoice.sampled`. The bank account passes IBAN mod-97 and per-country length, or ABA, checks (`AP-BNK-001`). With fieldcrypt keys the `Idempotency-Key` record stores a tenant-keyed HMAC of the request (`hmac:<key id>:...`), never a plain digest of payee data. See NOT-IMPLEMENTED.md for what remains.
- One-time payee retention and erasure (BR-48.5, BR-48.6, #335): `POST /v1/receiving/one-time-payees:erase` (duty `receiving.payee.erase`, body `legalEntityId` and optional `subjectRef`) and the consumer of `dev.passage.privacy.erasure.requested.v1` (Kafka group `receiving-erasure`, topic `passage.privacy.erasure`, started by `receiving consume` next to the `receiving-ers` consumer) run `store.ErasePayees`. Per payee: kept while 84 months (7 years, `domain.PayeeRetentionMonths`, the owner decision for AP and payee records; compliance lists it at `GET /v1/privacy/retention-policies`) have not passed since its last activity (the later of creation and its latest invoice); kept while compliance's `GET /v1/privacy/holds:check` (`dataClass=AP_PAYEE`, `recordRef` the payee id, `subjectRef`) reports a hold; otherwise name, address, tax id, email and bank account are overwritten with empties and `erased_at` is set. The row stays because posted invoices reference it. An unanswered hold check stops the run (payees already erased stay erased) and the consumer retries it. Without `COMPLIANCE_URL` the route answers 503 `RCV-HLD-001`. A run pages through all payees of the entity (200 per page, by `(created_at, id)` cursor, so retained rows never starve later ones). The floor follows the legal entity's country, not the payee's: `LEGAL_ENTITY_COUNTRIES` (`<legal entity uuid>=<ISO country>,...`, chart value `legalEntityCountries`) maps entities to countries; payees of an entity in DE or FR (10 years) are never erased until the local rules land (LOC-0502), and payees of an entity missing from the map are kept (fail closed); both count as retained. The `:erase` POST requires an `Idempotency-Key`. Each hold check runs immediately before that payee's own erasure. Nothing schedules the retention sweep yet. `COMPLIANCE_URL` defaults in the chart to `http://compliance-compliance.<namespace>.svc:8080`.
- Vendor group on `invoice.posted` (#302): at posting (manual, ERS, audit release) receiving reads the vendor from party (`GET /v1/party/vendors/{id}`, duty `party.read`, service token, `PARTY_URL`) and puts `vendor_group_id` on the event for payables' per-group aging. AP posting does not depend on party: if party is unreachable, refuses the call or does not know the vendor, the invoice posts without the field, a warning is logged and `receiving_vendor_group_lookups_failed_total` counts it. With `PARTY_URL` unset the field is never sent. A ledger vendor-group dimension for a per-group control comparison is not built.
- Stochastic audit block (FR-18.15, simplified): `PUT /v1/receiving/audit-policy` sets a sample rate per legal entity (percent, 0 to 100, two decimals, default 0). Every invoice posted afterwards, manual or ERS, is drawn per invoice and reproducibly (BR-18.14 without threshold or rule version): blocked when `HMAC-SHA256(AUDIT_SAMPLE_SEED, invoice id)` mod 10,000 is below rate x 100, so the same invoice id, seed and rate always give the same decision. `AUDIT_SAMPLE_SEED` (at least 16 bytes) is required, from the Secret named by `auditSeedSecret` in the chart; with `PASSAGE_ALLOW_FAKES=1` and no seed a random one is used. A drawn invoice checks the AP period like any invoice (a closed period is refused whether or not it was drawn), is stored `AUDIT_BLOCKED` with the GR/IR quantity reserved and the clearings fixed, posts nothing to the ledger and emits `payables.invoice.sampled.v1`. Two decisions end the block, both under duty `InvoiceAuditRelease` (the PRD duty, separate from `VendorInvoicePost`): `:release-audit-block` re-checks the AP period, posts the stored journal under the invoice's usual ledger key, records `released_by`/`released_at` and emits `invoice.posted.v1`; `:reject-audit-block` (reason required, 1 to 500 characters) posts nothing, frees the reserved GR/IR quantity and cleared amount, sets `AUDIT_REJECTED`, records `rejected_by`/`rejected_at`/`reject_reason` and emits `invoice.rejected.v1` (the invoice number stays used for the vendor; an ERS run then re-settles the receipt as `ERS-{receipt}-R{n}`, which is always held for audit whatever the sample rate, reason `re-issue after audit rejection`). Segregation of duties (PRD duty table: `InvoiceAuditRelease` conflicts with `VendorInvoicePost` on the same invoice): the user who posted the invoice cannot release or reject it, users compare by canonical id, and an invoice with no recorded poster cannot be decided at all (`AP-AUD-003`, fail closed). Therefore `invoices:post` and `ers-settlements:run` answer 401 without an authenticated user, and a scheduler that calls the ERS run must carry an end-user actor (with service tokens, the `act` claim, #303). A second decision gets `AP-AUD-002`; a held or rejected invoice cannot be adjusted (`AP-AUD-001`). The status can only move AUDIT_BLOCKED to POSTED or AUDIT_REJECTED (database trigger). Policy changes (`PUT audit-policy`, `PUT ers-vendors/{vendorId}`) append old value, new value, user and time to `receiving_audit_policy_history` and `receiving_ers_vendor_history` (insert-only, RLS) and emit `receiving.auditpolicy.changed.v1` / `receiving.ersvendor.changed.v1` in the same transaction. The PRD's duty table lists no conflict between `MatchingPolicyMaintain` and `VendorInvoicePost`, so changing a rate is not blocked for holders of the posting duty; the trail is the control. Not done: threshold amount, amount weighting, rule versioning.
- Settlement runs settle at most 100 sources (`hasMore`) and stop on the first failure; settled sources stay settled and a repeat continues.
- The invoice endpoint lives here until wave 19 owns payables; its event uses the `payables` context the PRD names.

## Pending ledger postings (runbook)

Each ledger post is first recorded in `receiving_pending_posting` (one row per ledger key) with the subjects it touches in `receiving_pending_posting_subject`: the receipt for a receipt command; the invoice id and every referenced receipt for an invoice. The row is marked done in the same transaction that applies the effect. While a row is open, any other ledger-posting command on one of its subjects, or the same key with a different body, returns 409 `RCV-IDM-001`; the problem's `errors.pendingKey` and `errors.createdAt` name the row. Repeating the original request completes it.

A row stays open when the ledger call ended in an unknown outcome (timeout, transport error, 5xx, 408, or a 409 that is not a conflict) or the local commit failed after the ledger accepted the entry. Any other 4xx from the ledger, and a closed period, release the row at once.

When the original request cannot be repeated (the client is gone, the data changed):
1. `GET /v1/receiving/pending-postings` (duty `ReceivingAdmin`) lists open rows, oldest first.
2. `POST /v1/receiving/pending-postings/{key}/resolve` (duty `ReceivingAdmin`, `Idempotency-Key` required) re-sends the stored journal under its key. If the ledger returns an entry id it is reversed through `POST /v1/ledger/journal-entries/{id}/reverse` and the row becomes `REVERSED`, which frees the receipt and invoice; a definite rejection makes it `REJECTED`. Resolve first claims the row (`claimed_at`), so a second resolve gets 409 `RCV-IDM-001`, and the original command's commit then fails with 409 `RCV-IDM-001` instead of recording a posting that was reversed. A row younger than the ledger timeout plus the request timeout (33 s) is refused with 409 `RCV-IDM-001` because its command may still be running. A reversal into a closed period answers 422 `PER-AP-001`, any other ledger refusal 422 `RCV-LDG-001` (the reversal is dated like the original posting and carries no reason code, so a ledger that requires one refuses it). It answers 503 `COM-0503` when the ledger cannot be reached or the reversal failed; the claim is released, so call it again. A claim is a lease of 2 x ledger timeout + request timeout (36 s): a resolve process that dies mid-way leaves the row claimed only until the lease ends, after which the next resolve takes it over. Releasing and finishing run detached from the client connection, so a disconnect cannot strand a claim.
3. The user repeats the command. Its ledger key carries a generation suffix (`:r1`, `:r2`) so it does not replay the reversed entry.

`ReceivingAdmin` is not in `policies/authz/data.json` yet. Alerting: the gauge `receiving_pending_postings_oldest_age_seconds` (and `receiving_pending_postings_open`) is kept per process, so it is lost on restart and each replica only sees the postings it started. With `replicas` above 1 the gauge needs a DB-derived source (the gauge handler has no tenant context, and the application role sees one tenant at a time, so it cannot be built from `ListPending`); until then rely on the query below. The `ReceivingPendingPostingStuck` PrometheusRule fires above 900 s. After a crash use the database as the source of truth:
`SELECT tenant_id, ledger_key, subject, created_at FROM receiving_pending_posting WHERE done_at IS NULL AND created_at < now() - interval '15 minutes';` (run as the table owner, because the application role sees one tenant at a time).
