# engineering

Wave 9 (PSG-9): engineering data for the `product` context: BOMs, routings, engineering change orders. Slice 1 is the pure domain kernel, the store, HTTP API, specs, chart and web module followed, slice 2 added pure calendar and resource domain code, slice 3 added resource and calendar persistence, slice 4 exposes it over HTTP, slice 5 added routing persistence, slice 6 added read APIs for route versions, the active route as of a date, and BOM version detail, and slice 8 adds resource, resource group and capability lists and route-version activation. What is not built is in `NOT-IMPLEMENTED.md`.

## Layout

- `cmd/engineering/main.go`: wiring. Env: `DATABASE_URL` (required, from Secret `engineering-db`), `MIGRATE_ON_START=true` (dev only), `HTTP_ADDR` (default `:8080`), `ADMIN_ADDR` (default `:9090`, serves `/metrics`).
- `internal/domain/bom.go`: as-of version resolution, multi-level explosion, implosion (where-used), cycle and overlap checks, cost roll-up skeleton.
- `internal/domain/routing.go`: operation DAG validation and lead time (sequential sum, parallel branches take the max and a secondary starts with its primary, efficiency, overlap transfer batches).
- `internal/domain/eco.go`: ECO state machine, `Approver` seam to the Temporal approval workflow, release plan (expire old at `release_date - 1`, activate new).
- `internal/domain/calendar.go`, `resource.go`: shift validation, calendar day generation, resource validation, effective calendar, requirement matching.
- `internal/store`: pgx repositories under `dbx.WithTenantTx`; `Catalog` loads only the BOM versions reachable from the requested products (recursive query, down for explosion, up for where-used) into a `Snapshot` that satisfies `domain.Catalog`. `ReleaseEco` applies a `ReleasePlan` and enqueues its events in one transaction. `resource.go` holds calendar, group, capability and resource persistence: `GenerateCalendar` upserts `calendar_day` rows and enqueues one `calendar.generated` per call; `CreateResource` checks group site, calendar and capabilities and enqueues one `resource.changed`.
- `internal/api`: handlers, validation, duties, readiness (`resource.go` holds the calendar, group, capability and resource handlers, `resource_read.go` the resource, group and capability lists); `metrics.go` serves business counters plus `engineering_http_requests_total` and `engineering_http_request_duration_seconds` by route pattern. Alert on the 5xx share of requests and on explode p95 from the duration histogram.
- `internal/events/events.go`: event types and payloads.
- `migrations/0001_init.sql`: tables with `tenant_id` first, tenant RLS (enabled and forced), idempotency and outbox tables.
- `migrations/0002_resources.sql`: `work_calendar`, `calendar_day`, `resource_group`, `capability`, `resource`, `resource_capability` with the same RLS and grants.
- `api/openapi.yaml`, `events/asyncapi.yaml`, `charts/engineering`, `Dockerfile`.
- `testdata/`: `bom-golden-7x2000.json` and `.csv` (7 levels, 2,000 BOM lines), `bom-dag-7x2000.json` and `.csv` (adversarial 7-level DAG), `routing-leadtime.json` (12 fixtures), `routing-leadtime-adversarial.json` (parallel start and overlap). Expected values come from the independent oracles `gen_bom_golden.py` and `gen_routing_leadtime.py` (`python3 -I`, exact fractions); `internal/golden` loads the BOM fixtures for tests.

## Routes and duties

| Route | Duty |
|---|---|
| `POST/GET /v1/engineering/bom-versions` | `engineering.bom.write` / `engineering.read` |
| `GET /v1/engineering/bom-versions/{id}`, `GET /v1/engineering/route-versions`, `GET /v1/engineering/route-versions:active`, `GET /v1/engineering/route-versions/{id}` | `engineering.read` |
| `POST /v1/engineering/boms:explode`, `GET /v1/engineering/boms:where-used`, `POST /v1/engineering/routes:lead-time` | `engineering.read` |
| `POST /v1/engineering/ecos` | `engineering.bom.write` |
| `POST /v1/engineering/ecos/{id}:release` | `engineering.eco.approve`, or the service-only `engineering.eco.workflow`. An approved ECO is released without calling the approver seam. |
| `POST /v1/engineering/ecos/{id}:approve`, `:reject`, `:cancel` | the service-only `engineering.eco.workflow` that `workflow-ts` signs, never a person. They decide a submitted ECO as the token's acting user: 403 `ENG-ECO-SELF-APPROVAL` when that user created the ECO (`created_by`, migration 0005, backfilled from the `eco.submitted` outbox actor; an ECO with no recorded creator is refused with 403 `ENG-ECO-CREATOR-UNKNOWN`, and creating an ECO needs the acting user), `ENG-ECO-ACTOR-REQUIRED` without a user, 409 `ENG-ECO-STATE` from any other state, 200 unchanged on a repeat. `:reject` and `:cancel` take an optional `{reason}` kept as `decisionReason`. |
| `POST/GET /v1/engineering/ecrs`, `GET /ecrs/{id}`, `POST /ecrs/{id}:submit`, `:cancel` | `engineering.bom.write` to raise, submit and withdraw an engineering change request (`engineering.read` to list and get). An ECR is created `draft`; the states are draft, submitted, under_review, approved, rejected, cancelled (`ENG-ECR-STATE`, 409, from any other state). `ecr.submitted` is enqueued on submit. Only the requester withdraws (`:cancel`, 403 `ENG-ECR-NOT-REQUESTER` for anyone else); withdrawing a submitted or under-review request enqueues `ecr.cancelled`. |
| `POST /v1/engineering/ecrs/{id}:review`, `:approve`, `:reject` | `engineering.ecr.review` (a person, not the workflow). 403 `ENG-ECR-SELF-APPROVAL` for the requester, `ENG-ECR-ACTOR-REQUIRED` without a user, 200 unchanged on a repeat; `:approve` and `:reject` enqueue `ecr.approved` and `ecr.rejected`. `POST /ecos` may name an approved ECR with `ecrId` (`ENG-ECR-NOT-APPROVED`, `ENG-ECR-CONVERTED`, `ENG-ECR-PRODUCT`; 404 `ENG-ECR-NOTFOUND`). |
| `POST /v1/engineering/calendars`, `POST /v1/engineering/calendars/{id}:generate`, `POST /v1/engineering/resource-groups`, `POST /v1/engineering/capabilities`, `POST /v1/engineering/resources` | `engineering.resource.write` |
| `GET /v1/engineering/calendars/{id}/days`, `GET /v1/engineering/resources/{id}`, `GET /v1/engineering/resources`, `GET /v1/engineering/resource-groups`, `GET /v1/engineering/capabilities` | `engineering.read` |
| `POST /v1/engineering/route-versions/{id}:activate` | `engineering.route.write` |

Calendar, group, capability and resource creates honour `Idempotency-Key` (a different body under the same key is 422 `idempotency_key_reuse`); `:generate` is state-based, so a repeat upserts the same days. A calendar template is exactly seven day patterns, Monday first. `GET /resources/{id}` returns capabilities and `effectiveCalendarId`. Malformed bodies are 400 `COM-0001` with an `errors` map. Counters: `engineering_calendars_created_total`, `engineering_resources_created_total`, `engineering_resource_requests_failed_total`.

Lists page by id with `limit` (1 to 100) and `cursor`, answer `{items, nextCursor}` and reject a bad `limit` or `cursor` with 400 `COM-0001`. `GET /route-versions` filters by `productId`, `siteId`, `status` and `asOf` and returns headers with `operationCount`; `route-versions:active` needs `productId` and `siteId`, `asOf` defaults to today (UTC), and only active versions match. Counter: `engineering_route_requests_failed_total`.

`GET /resources` filters by `siteId`, `type` (machine, tool, labor, vendor, location), `groupId` and `capabilityId`; `GET /resource-groups` by `siteId`; `GET /capabilities` takes none. These three lists order by code then id, page with the same opaque cursor, and answer a bad filter, `limit` or `cursor` with 422 `COM-0001` and an `errors` map naming each field (the older lists above keep 400). Resources carry their capabilities and `effectiveCalendarId`.

`engineering.route.write` (PRD 1.9.17) guards `POST /route-versions/{id}:activate`: 200 with the full route version, a repeat on an active version is 200 with no second `routeversion.activated` event, an unknown id is 404 `ENG-ROUTE-NOTFOUND`, a version that is not a draft is 409 `ENG-ROUTE-STATE`, an overlapping active version of the same product and site is 409 `ENG-ROUTE-OVERLAP`, and an unmet requirement is 422 `ENG-ROUTE-UNSATISFIED`. Successes count in `engineering_route_versions_activated_total`. Creating a BOM version defaults to `draft`; `active` is accepted only as the first version of a product and site (checked for overlap, `ENG-BOM-ECO-REQUIRED` otherwise) and enqueues `bomversion.activated`; every later activation goes through an ECO. Creates and releases serialise per tenant and product with a transaction advisory lock, and a release re-checks overlap inside its transaction. Explosion and where-used stop at 100,000 nodes with `ENG-BOM-TOOLARGE`. An ECO is created `submitted`; `:release` asks the approver, then releases or schedules it.

## Error codes

`ENG-BOM-CYCLE`, `ENG-BOM-OVERLAP`, `ENG-BOM-NOVERSION`, `ENG-BOM-LEVELS`, `ENG-BOM-QTY`, `ENG-BOM-LINE`, `ENG-BOM-TOOLARGE`, `ENG-BOM-ECO-REQUIRED`, `ENG-BOM-PHANTOM-NOBOM`, `ENG-ROUTE-QTY`, `ENG-ROUTE-NEXT-MISSING`, `ENG-ROUTE-SECONDARY-NOPRIMARY`, `ENG-ROUTE-CYCLE`, `ENG-ECO-STATE` (409), `ENG-ECO-APPROVER-UNAVAILABLE` (503, counted in `engineering_ecos_failed_total`), `ENG-ECO-NOT-APPROVED`, `ENG-ECO-DRYRUN`, `ENG-ECO-DATE`, `ENG-ECO-HORIZON` (422, a create release date more than 365 days after today's UTC date), `ENG-ECO-BACKDATE-DUTY` (403, a create release date before today's UTC date; BR-9.10's backdate duty is not built), `ENG-CAL-SHIFT`, `ENG-CAL-RANGE`, `ENG-RES-VENDOR`, `ENG-RES-SITE` (422, as are all other domain codes), plus store codes `ENG-ECO-NOTFOUND` (404), `ENG-BOM-VERSION-NOTFOUND` (404), `ENG-BOM-NOTFOUND` (404), `ENG-ROUTE-NOTFOUND` (404), `ENG-CAL-NOTFOUND` (404), `ENG-RES-NOTFOUND` (404), `ENG-DUPLICATE` (409) and `idempotency_key_reuse` (422). The PRD 1.9.18 catalog names the first seven present codes where they exist; `NOVERSION`, `LEVELS`, `QTY`, `LINE`, `ROUTE-QTY`, `ROUTE-CYCLE`, `ECO-STATE`, `ECO-DRYRUN`, `ECO-DATE` and the store codes are not in the catalog yet and must be reconciled with it.

## Event types

The PRD names `dev.passage.engineering.bom.version.activated.v1`, which has four segments after the context and fails `platform/go/events.ValidType`. The entity is folded into one segment instead: `bomversion`, `routeversion` is reserved the same way (as `releasedproduct` is in the product service). Emitted: `bomversion.activated`, `bomversion.expired`, `eco.submitted`, `eco.approved`, `eco.released`, `resource.changed`, `calendar.generated`.

## Dependencies

`platform` (events, outbox, dbx, httpx, authz, money, ids), `shopspring/decimal` (exact quantities; float64 would break the golden), `pgregory.net/rapid` (property tests), `go-chi/chi/v5` and `jackc/pgx/v5` (the versions the kernel pins; `Register(chi.Router)` and `pgx.Tx` are the kernel's own signatures). All are already used by `services/org` and `services/product`.
