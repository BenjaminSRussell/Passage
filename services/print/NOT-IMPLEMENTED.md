# NOT-IMPLEMENTED: print (PSG-32, wave 32, slice 3)

Every PSG-32 deliverable or acceptance criterion that this service does not yet cover.
Status is either `later slice of PSG-32` (owned here, not built yet) or `handoff`
(needs code outside the wave's owned paths).

| Item | Source | Status | Reason |
| --- | --- | --- | --- |
| Job input for PDF and PCL documents (`POST /print/v1/jobs` renders built-in ZPL templates only) | FR-32.13, BR-32.12 | later slice of PSG-32 | The PDF over IPP and PCL 6 over raw TCP transports are built and tested (`internal/transport`), and `cmd/print` sends through the device-type `Router`. No job carries a PDF or PCL payload yet, so dispatch still offers jobs to `ZPL_II` devices only. |
| PDF documents from their owning waves (pick lists, count sheets, CoAs, bills of lading) | FR-32.13, §6.32.15 | handoff | The documents are produced by the waves that own them (wms, quality, shipping). This service routes and sends them once those waves hand over PDF bytes. |
| Media sizes per device, and templates sized to 300/600 dpi | FR-32.13, §6.32.13 `label_default_dpi` | later slice of PSG-32 | The registry holds the device type and dpi (203, 300, 600) but no media size. Templates are laid out for 203 dpi. |
| Hardware check of IPP and PCL 6 on the demo printers | FR-32.13, §6.32.9 | later slice of PSG-32 | The transports are tested against an `httptest` IPP server and a local TCP listener. No printer is reachable from CI. |
| Carrier and ship-from on the GS1 carton label | §6.32.15 | later slice of PSG-32 | The carton label prints ship-to, SSCC and the AI 00/400/420 barcode. Carrier and ship-from come from shipping (wave 28) and are not job fields yet. |
| Browser printing of PDF documents when no device is routed (BR-32.12 fallback) | FR-32.13, §6.32.13 `browser_print_fallback` | handoff | Browser printing runs in the device or web client, not in this service. The routing rule that decides the fallback is built (see `POST /print/v1/routing-rules`). |
| Printer selection by flow step (step, user and location) | FR-32.7 | handoff | Flow steps belong to the mobile flow service, which is outside the owned paths. The job API accepts `documentType`, `zone` and `warehouseId`, so the caller can pass the step context. |
| 10-minute print dedupe window as a per-tenant setting (BR-32.8, `print_job_dedupe_min`) | BR-32.8, §6.32.13 | later slice of PSG-32 | BR-32.8 is met by a stronger rule: a repeated Idempotency-Key returns the stored job and never re-renders, because the key is unique per tenant and does not expire. "Print again" creates a job with `reprintOf`. The setting that would let a key print again after the window is not built. Matching identical bodies sent with different keys is deliberately not done: it would swallow intended copies, such as the 20 identical LP labels of AC-32.10. |
| `print_retry_count` default of 3 | §6.32.10 `PRINT_RETRY=3`, §6.32.13 | later slice of PSG-32 | `PRINT_RETRY` is read (retries per printer after the first attempt, 0 to 10; the chart sets it per site deployment). The PRD conflicts with itself: FR-32.13 and AC-32.10 fail over after 2 attempts, which is `PRINT_RETRY=1`, while §6.32.10 and §6.32.13 default to 3. The default stays at 1 until the PRD is corrected. |
| Live printer probe for the "online" column of printer status | §6.32.14 | later slice of PSG-32 | `GET /print/v1/printers/status` and the web page report state, queue depth and last error from the last job each printer handled. No device is probed, so a printer that has not printed since it went offline still shows its last state. |
| Print queue retry and failover sweep every 15 s, and asynchronous dispatch with the SENT state | §6.32.16, §6.32.4 | later slice of PSG-32 | Dispatch runs inside `POST /print/v1/jobs`. A job whose process dies between insert and completion stays QUEUED; no sweep picks it up yet. |
| Printer edit, retire and move between queues; routing rule edit and delete | FR-32.13, §6.32.6 | later slice of PSG-32 | Only create and list exist, in the API and the web screens. |
| Template management screen and tenant templates (§6.32.6 "templates") | §6.32.6, FR-32.7 | later slice of PSG-32 | Templates are built in (`LP_LABEL`, `LOCATION_LABEL`, `ITEM_LABEL`, `GS1_CARTON_LABEL`); there is no template store or editor. |
| Tenant discovery for the daily job log purge | §6.32.19, FR-32.13 | later slice of PSG-32 | The daily 01:00 UTC purge runs in `cmd/print` (`internal/jobs`) for the tenants listed in `PRINT_PURGE_TENANT_IDS` (chart value `purgeTenantIds`). Row-level security scopes each delete to one tenant, so a tenant missing from the list is only purged on demand (`POST /print/v1/jobs:purge`). Reading the tenant list from the tenant service is not built. |
| Per-printer failure metric for the "print failures > 5/15 min per printer" alert, and the alert rule | §6.32.10 | later slice of PSG-32 | `/metrics` on the admin port (9090, scraped by the chart's `ServiceMonitor`) exports service totals `print_jobs_printed_total`, `print_jobs_failed_total` and `print_jobs_purged_total`, without a printer label. The PrometheusRule belongs to the observability owner (handoff). |
| Mobile flow runtime calling `POST /print/v1/jobs` on step completion (AC-32.5) | AC-32.5 | later slice of PSG-32 | The device flow runner (`apps/web/src/modules/mobile-flows/domain/flowRunner.ts`, used by `apps/warehouse-mobile`) completes the receive/put-away flow but does not print. The LP label needs the LP's SSCC, item, lot and expiry from the wave-31 work API, which the device does not fetch yet (the mobile service is a handoff). |
| Automation adapter (FR-32.12), RFID EPC ingest, voice adapter | FR-32.9, FR-32.12 | handoff | Owned by the wms automation and mobile services, not by this service. |
| Deploy: print service live (Argo CD application, image build, one pod per site network) | Ticket deploy line, §6.32.10 | handoff | Lives in `deploy/` and the CI pipeline, which the deployment-cicd owner controls. The chart lints and is ready for it. |
| Site network egress policy for TCP 9100 and IPP | §6.32.10, FR-32.13 | handoff | Network policy is owned by deployment-cicd and the site IT team. |
