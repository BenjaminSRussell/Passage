# Identity authorization integration

This package implements a service-side JWT verifier and OPA decision client. Configure `JWTVerifier` with a tenant's trusted issuer, expected audience, tenant ID, and JWKS URL. Route requests through its middleware before `RequireOPA`; the verifier checks RS256 signature, issuer, audience, `sub`, `tid`, `iat`, `exp`, and `nbf`, then overwrites the untrusted gateway principal with the verified subject. `RequireOPA` rejects contexts without the verifier's private marker. Duties are looked up in OPA's tenant-scoped bundle assignments; callers cannot provide duties in a header or token. An unreachable or malformed policy response returns 503.

```go
policy, err := identity.NewOPAClient("http://127.0.0.1:8181", nil)
if err != nil {
	log.Fatal(err)
}
verifier, err := identity.NewJWTVerifier(issuer, "passage-api", tenantID, jwksURL, nil)
if err != nil {
	log.Fatal(err)
}
r.With(verifier.Middleware, identity.RequireOPA(policy, http.MethodPut, "/v1/vendors")).Put("/v1/vendors/{id}", handler)
```

Run `go test ./...` from this directory. The bundle is under `../../policies/authz`; `opa test --timeout 120s ../../policies/authz` runs its Rego contract tests. The policy bundle seeds every duty the Go services enforce and starts with no assignments; the policy compiler must populate assignments per tenant before access is granted. Each route passes its HTTP method and resource path to the policy middleware.

Tenant-level writes need the `tenant.administer` duty (a flag duty, no routes) with no legal-entity scope, on top of the specific admin duty. The contract with the IdP: a token without a legal-entity claim is not by itself tenant-level; it reads every legal entity only with the all-scope duty (`org.switcher.all-scope`) and writes tenant-wide only with `tenant.administer`, so a mapper that drops the claim grants nothing extra. The platform operator (`identity.tenant.maintain`, operator tenant) seeds the first holder: `POST /v1/tenants` takes optional `adminUserId` and `adminIdpSubject`, and `POST /v1/tenants/{id}/admins` (`userId`, `reason`) grants it in an existing tenant. Before deploying, add `tenant.administer` to the duties claim of existing tenant administrators in the Keycloak duties mapper; the last active tenant-wide `tenant.administer` assignment of a tenant cannot be ended (`IDN-LAST-TENANT-ADMIN`).

Stable problem codes in this slice: `AUTH-0001` unauthenticated or invalid token, `AUTH-0003` policy denial, `AUTH-0404` tenant or gateway identity mismatch, `AUTH-0502` JWKS unavailable, `AUTH-0503` OPA unavailable.

## Schema grants and scoping

`passage_app` has SELECT and INSERT only on `identity_tenants` (insert is limited by RLS to the tenant id the transaction is scoped to, and migration 0009 adds a RESTRICTIVE INSERT policy requiring the transaction-local `passage.operator_context` to name the `identity_operator` row; only `POST /v1/tenants` sets it, after the operator check, and clears it once the tenant row is written, so the grant alone does not let a tenant-scoped session create tenants): status changes and renames belong to the migrator, so a tenant cannot reactivate itself, rename its realm, or probe other tenants' realm names (only the operator tenant can read other tenants). `identity_role_assignments` rejects overlapping grants of the same user, role and legal entity (an exclusion constraint, open-ended `valid_to` counts as infinity), so a revoke always takes effect. A caller scoped to specific legal entities does not see tenant-wide assignments (null `legal_entity_id`); only a `*` scope does.

## Effective permissions

`LoadCatalogue` parses `../../policies/authz/data.json` into an engine that mirrors `authz.rego`: `Evaluate(duties, method, resource)` returns allow, the lexically first held duty that grants it, and (on deny) the policy's least-privileged `duty_missing`. `Effective(duties)` evaluates every distinct resource pattern and method in the catalogue at a sample path (`{,/**}` becomes `/item-1`, `*` becomes `item-1`). Globs outside literal text, `*` and a trailing `{,/**}` fail at load so the engine cannot drift from OPA silently.

`NewEffectivePermissionsAPI(pool, catalogue).Register(r)` serves `GET /v1/identity/users/{id}/effective-permissions` (duty `identity.effective-permission.view`, OpenAPI in `api/openapi.yaml`). Until the role catalogue exists (#83), `identity_role_assignments.role` holds a duty name. Active assignments (`valid_from <= now() < valid_to`) are resolved: tenant-wide rows always, plus rows for `?legalEntityId=` when given. Roles that are not seeded duties are listed in `ignoredRoles` and grant nothing, as in OPA. A caller without the all-entity scope, scoped or unscoped, receives 403.

`effective_test.go` checks the engine against the real policy (OPA server, same harness as `opa_contract_test.go`): 100 routes sampled evenly across the sorted catalogue, times eight fixture principals, must match OPA on allow and `duty_missing`; the full report is also compared row by row for four principals.

## Tenant, legal-entity and role-assignment APIs

`NewTenantsAPI(pool, operatorTenantID)`, `NewLegalEntitiesAPI(pool)` and `NewRoleAssignmentsAPI(pool, catalogue, operatorTenantID)` serve `/v1/tenants` (create, list, get), `/v1/legal-entities` (create, list, get) and `/v1/authz/assignments` (assign, list by `userId` and/or `role` (one is required), get, `POST .../{id}/end` and its alias `DELETE .../{id}`). They reuse the seeded duties `identity.tenant.maintain`, `identity.legal-entity.maintain` and `identity.security-role.maintain` and the catalogue's resource patterns, so the duty count stays unchanged.

All three run on the ordinary `passage_app` pool; no path bypasses RLS. Tenant routes are operator-only: the caller must hold `identity.tenant.maintain` and belong to `operatorTenantID`. Create sets `passage.tenant_id` to the new tenant's id inside its transaction so the row passes its own RLS check (`passage_app` holds INSERT, not UPDATE or DELETE, on `identity_tenants`) and writes the audit row in the operator tenant too. List and get read through the `identity_tenants_operator_read` policy, which admits SELECT only when the caller's tenant is the single row of `identity_operator`; the migrator or deploy seeds that row with the same id as `operatorTenantID`.

Tenant-level writes (creating a legal entity, a tenant-wide assignment, ending one) run with an explicit `*` legal-entity scope set by the handler, and only when the request carries no legal-entity scope and the caller holds the matching admin duty (`identity.legal-entity.maintain` or `identity.security-role.maintain`); every other request runs with the caller's own scope. Assigning a role to yourself is refused (403 `IAM-0416`), `identity.tenant.maintain` can only be granted in the operator tenant, and past or inactive-legal-entity assignments are refused.

An assigned role must be a seeded duty name. The no-overlap rule for one user, role and legal entity is the `identity_role_assignments_no_overlap` exclusion constraint (409 `IDN-ASSIGNMENT-OVERLAP`); a revoke is `end` (never a delete), which only shortens; ending a future-dated assignment sets `valid_to = valid_from`, an empty range that overlaps nothing and grants nothing. Every mutation writes an `identity_audit` row (actor from `X-Passage-User`) and an `outbox` event (`dev.passage.identity.{tenant,legalentity,roleassignment}.{created,assigned,ended}.v1`) in the same transaction as the change.

`GET /v1/tenants` also takes `status=active|suspended|deprovisioned` and accepts the read-only duty `identity.tenant-registry.read` (from the operator tenant) in place of `identity.tenant.maintain`, so a scheduled job of another service can read the list of active tenants (the shopfloor sweeper, service grant shopfloor to identity); every other tenant route still needs `identity.tenant.maintain`.

## User directory and role/duty catalogue

`NewUsersAPI(pool)` serves `GET /v1/identity/users` (filters `status`, `q`, `legalEntityId`; keyset paging) and `GET /v1/identity/users/{id}` under the seeded duty `identity.user.maintain`. Users belong to the tenant, not to a legal entity, so every holder sees the whole tenant; `legalEntityId` narrows to users with an active (current, not ended or future) assignment for that entity and is bounded by the caller's own scope through the assignments' RLS.

`NewCatalogueAPI(catalogue)` serves `GET /v1/authz/roles[/{name}]` and `GET /v1/authz/duties[/{name}]` under `identity.security-role.maintain`. Until roles are first-class, a role is an assignable duty (the same names `POST /v1/authz/assignments` accepts); duty detail lists the routes a duty grants. The catalogue is global, read from `data.json`, so it needs no database.

### Tenant features

`NewTenantFeaturesAPI(pool)` serves `GET /v1/tenant/features` (the catalog from `platform/go/features` with the caller's tenant's on/off state, who last changed each feature and when, and the industry templates) and `PUT /v1/tenant/features` (`{"features": {"catch-weight": false}}` or `{"template": "distribution"}`). The seeded duties are `identity.feature.view` (GET, checked at the gateway) and `identity.feature.maintain` (PUT); the service itself needs only an authenticated tenant for GET, because the shell reads it for everyone, and it also accepts a tenant-level service token carrying `identity.feature.view` (granted to processmfg; `cmd/identity` now configures the service verifier and the shared replay table, migration 0013). PUT also needs `tenant.administer` with no legal-entity claim. Only explicit changes are stored (`identity_tenant_features`, migration 0012, tenant RLS); a feature with no row is on, so no existing tenant changes behaviour. A change is refused with 422 `IDN-FEATURE-DEPENDENCY` when it would leave a feature on without one it depends on, and the message names what to turn on or off first. Each changing request is serialised per tenant, audited (`tenantfeatures.updated`) and emitted as `dev.passage.identity.tenantfeatures.updated.v1`; a request that changes nothing writes nothing. Features are relevance, not security: a disabled feature's API answers with `FEAT-0001` (see `platform/go/features/README.md`), but duties stay the boundary.

### SCIM 2.0 provisioning

`NewSCIMAPI(pool, verifiers, opa)` serves `/scim/v2/Users`, `/scim/v2/Groups` (list, create, get, `PUT`, `PATCH`, `DELETE`) and the discovery documents `ServiceProviderConfig`, `Schemas` and `ResourceTypes`. It sits outside `tenant.Middleware` (the gateway cannot supply `X-Passage-Tenant` until host-to-tenant routing lands, #213): `cmd/identity` mounts the admin APIs in a group with the header middleware and SCIM in a group with its own bearer middleware.

- **Auth.** The bearer JWT's `tid` claim only selects the tenant's verifier; the issuer (`IDENTITY_SCIM_ISSUER_BASE/<realm_name>`) and JWKS URL come from the tenant registry, only `active` tenants resolve (cached for 30 seconds, so a suspension can take that long to reach SCIM), and an unknown tenant is the same 401 as a bad token; 401s carry `WWW-Authenticate: Bearer`. The policy then decides on the request method and path, and the seeded duty `identity.user.provision` (`/scim/v2{,/**}`) is a person duty, so an operator assigns it to the IdP's service account like any role. SCIM handlers open their own explicit tenant-wide transaction; the SCIM principal is never given `tenant.administer`. SCIM is mounted only when `IDENTITY_SCIM_ISSUER_BASE`, `IDENTITY_SCIM_AUDIENCE` and `IDENTITY_OPA_URL` are all set.
- **Users.** `userName` (unique per tenant, case-insensitive), `externalId`, `displayName`, `emails` (the primary one is stored), `active`; `name` only defaults `displayName`, and other attributes are ignored. A created user gets the placeholder `idp_subject` `scim:<id>`, to be bound when the Keycloak push (#80) lands. Only users that carry a `userName` are visible to SCIM, so a SCIM client cannot read or deprovision users it did not create.
- **Deactivate.** `DELETE` and `PATCH active=false` (also the string `"False"` Entra sends) set the user `deprovisioned` and end every active and future role assignment in the same transaction; each change writes an audit row and an outbox event (`user.deprovisioned`, `roleassignment.ended`), and queues the Keycloak call that disables the user (see Keycloak deprovisioning below). Reactivating does not restore access. A deprovision that would leave the tenant without an active tenant-wide `tenant.administer` holder is refused with 409 (same advisory lock as the assignment-end guard), so the IdP sees the failure. Both paths take that tenant-admin lock before any assignment row lock, so ending an assignment while its holder is deprovisioned cannot deadlock. `active` set to null or removed is a 400, never a deprovision. Role assignment grants read the user row `FOR SHARE`, so a racing grant cannot land on a deprovisioned user.
- **Keycloak deprovisioning.** The deactivating transaction inserts a row into `identity_keycloak_deprovisions` (migration 0011: reason `scim_deactivated` or `scim_deleted`, the user's `idp_subject` and `userName`, the SCIM actor), so a committed deprovisioning always has its Keycloak call pending; a repeated `DELETE` of a deprovisioned user changes nothing and queues nothing, and a reactivation closes any call that has not run as `superseded` (a call that already ran is not undone: re-enabling the Keycloak user is an administrator's step). `KeycloakDeprovisioner` (started by `cmd/identity` when `IDENTITY_KEYCLOAK_ADMIN_URL` is set) lists tenants as the operator tenant, then per tenant, under that tenant's RLS, claims due rows with a two-minute lease (`FOR UPDATE SKIP LOCKED`, so replicas never work a row together) and, outside any transaction, calls `KeycloakAdmin.DeprovisionUser` in the tenant's realm: find the user (by id when `idp_subject` is a Keycloak id, else by exact `userName` for the `scim:` placeholder), refuse one whose `tenant_id` attribute names another tenant, `PUT` its whole representation back with `enabled=false` (no attribute is dropped), then `POST .../logout`, which ends every session and sets the user's not-before so issued refresh tokens die. A missing user (404, or no username match) is done as `not_found`; a repeat of a finished call is harmless. Failures retry after 30 s doubling to an hour and park after 8 attempts, or at once for a permanent answer (400, 403, another tenant's user, an ambiguous username); `last_error` keeps the operation, status and Keycloak error code, never a token or secret. `GET /v1/identity/users/{id}/keycloak-deprovisions` (`identity.user.maintain`) lists a user's calls with their state (`pending`, `parked`, `done`); `POST .../keycloak-deprovisions/{deprovisionId}:retry` (also needs `tenant.administer` with no legal-entity claim; audited as `keycloakdeprovision.retried`) makes a parked or pending call due now with its attempts reset. An access token already issued stays valid until it expires (at most 300 s in the realm export).
- **Groups** are provisioning records, not roles: role assignments are dated, scoped and audited with the self-grant guard, so a group sync never grants access. `displayName` is not unique (RFC 7643). Members must be provisioned users of the tenant; responses list at most 500 members and `excludedAttributes=members` omits them. Because a client cannot read the full membership of a larger group, a `PUT` to a group with more than 500 members is refused with 400 `tooMany` (otherwise it would drop the members the client never saw); change such a group with `PATCH` `add`/`remove` on `members`.
- **Wire format.** Responses and errors use `application/scim+json` (including 401/403 from the shared middleware); request bodies are decoded leniently, and a body over 1 MiB is a 413 `tooLarge`. Filters support only `attr eq "value"` on `userName`/`externalId` (users) and `displayName`/`externalId` (groups); paging is `startIndex`/`count` (default and maximum 100 and 200).

## Server binary

`cmd/identity` wires every API above on `httpx.NewRouter()` (gateway-asserted `X-Passage-*` headers). Settings: `DATABASE_URL`, `IDENTITY_DUTY_CATALOGUE_PATH` (the `policies/authz/data.json` the bundle is built from), `IDENTITY_OPERATOR_TENANT_ID` (optional; without it the tenant routes and `identity.tenant.maintain` grants are refused), `MIGRATE_ON_START` with optional `MIGRATE_DATABASE_URL` for the schema owner, `HTTP_ADDR`, and for Keycloak deprovisioning `IDENTITY_KEYCLOAK_ADMIN_URL` (Keycloak's root URL, https except on loopback), `IDENTITY_KEYCLOAK_SECRETS_DIR` (one file per realm name holding that realm's `passage-identity-deprovision` client secret, read on every token fetch so rotation needs no restart), optional `IDENTITY_KEYCLOAK_CLIENT_ID` (default `passage-identity-deprovision`) and `IDENTITY_KEYCLOAK_DEPROVISION_INTERVAL` (default 30s, at least 5s); it needs `IDENTITY_OPERATOR_TENANT_ID`. `identity_operator` is limited to a single row by a constraint; seeding it with the operator tenant id stays a deploy prerequisite. The `Dockerfile` (build context is the repo root) bakes `policies/authz/data.json` and `authz.rego` into `/etc/passage/authz`, which the chart points `IDENTITY_DUTY_CATALOGUE_PATH` at. The chart `charts/identity` renders the Deployment and Service; `bundle.enabled` adds the bundle env, the `identity-bundle` Secret mount (`token`, `signing-key.pem`, `tls.crt`, `tls.key`) and the separate `<release>-bundle` Service; `keycloakDeprovision.enabled` (with `adminUrl` and `operatorTenantId`) adds the deprovisioning env and mounts the `keycloakDeprovision.secretName` Secret (default `identity-keycloak`, one key per realm) at `/var/run/passage/keycloak`, and with `externalSecret.enabled` (default) renders the ESO `ExternalSecret` that fills it from `ClusterSecretStore` `passage`, Vault keys `passage/<env>/identity/keycloak/<realm>` property `value`, for each realm in `externalSecret.realms`. Off in dev until Keycloak is behind TLS. The dev Argo app is `deploy/envs/dev/apps/identity.yaml` (SCIM off until Keycloak is behind TLS). There is no gateway route. The chart's NetworkPolicy admits port 8080 only from the Envoy Gateway proxy pods: `networkPolicy.gatewayNamespaces` (default `envoy-gateway-system`) AND `networkPolicy.gatewayPodLabels` (default the `passage-api` Gateway in `hello-ledger`, see `deploy/gateway/gateway.yaml`). Same-namespace pods are not admitted unless `networkPolicy.allowSameNamespace` is set, because admin routes trust `X-Passage-*` headers and any admitted pod could forge them. With no gateway namespace and no opt-in, 8080 is closed. When `bundle.enabled`, the bundle port is admitted only to pods carrying `networkPolicy.opaPodLabels` (default `passage.io/opa-sidecar: "true"`, same namespace plus `opaNamespaces`); `deploy/policies/opa/opa-sidecar.yaml` is a ConfigMap, so consuming service pods must carry that label themselves, and the chart refuses to render with `bundle.enabled` and empty `opaPodLabels`. `charts/identity/test-networkpolicy.sh` (CI helm job) fails if either port becomes allow-all.

**Database secrets.** `databaseSecret` (default `identity-db`, key `DATABASE_URL`) is the runtime URL for the non-owner, `NOBYPASSRLS` `passage_app` role; `migrateDatabaseSecret` (dev: `identity-db-owner`, key `DATABASE_URL`) renders `MIGRATE_DATABASE_URL` for the schema-owner role that `MIGRATE_ON_START` uses, as the org chart does. Both point at a dedicated identity database; creating it, the owner role and the two Secrets (and a `postgres-init` script like `40-org-db.sh`) is a deploy handoff, not yet in `deploy/envs/dev/apps/postgres.yaml`.

**Customer portal contacts (#30).** `CustomerContactsAPI` (`customer_contacts_api.go`, migration 0015 `identity_customer_contacts`) lets an administrator with `identity.customer-contact.maintain` invite a person to the customer portal: `POST /v1/identity/customer-contacts` (email, name, `customerId`, `legalEntityIds`), `GET` (filter `customerId`, `status`), `PATCH .../{id}` (remap), `POST .../{id}:resend` and `:disable`. The account lives in the tenant's Keycloak realm (`keycloak_contacts.go`, the same admin client as deprovisioning): the user is created enabled with the role `customer-user`, the attributes `tenant_id`, `legal_entity_id` (comma separated) and `customer_id` that the portal BFF reads as claims, and the required actions `VERIFY_EMAIL`, `UPDATE_PASSWORD` and `CONFIGURE_TOTP` (the MFA enrolment, so a contact cannot finish a first sign-in without an authenticator whatever the realm default); Keycloak emails the link (`execute-actions-email`, seven days). A retry adopts the user an earlier attempt created, another tenant's user is never touched, a remap or disable ends the contact's sessions, and the audit and event carry ids only, never the address. The caller needs scope over every legal entity named, and the legal entities must exist in the tenant; identity does not read customers (party owns them), so the customer id is taken as given and the admin screen picks it from the customer lookup. `GET /v1/identity/customer-portal/legal-entity` (service-only duty `identity.customer-portal.read`, only for the customer-portal service token acting for a customer) answers the display name of the token's own legal entity for the portal's company selector. Settings: `IDENTITY_CUSTOMER_PORTAL_CLIENT_ID` (default `passage-portal-customer`) and optional `IDENTITY_CUSTOMER_PORTAL_REDIRECT_URI`; without `IDENTITY_KEYCLOAK_ADMIN_URL` the directory can be read but nothing is created (503 `IDN-CONTACT-KEYCLOAK-OFF`). Identity must trust the portal's key: add `customer-portal=<public key>` to `PASSAGE_SERVICE_PUBLIC_KEYS`.

**Keycloak.** `deploy/keycloak` holds the dev deployment and the `passage` realm export (clients, `tid`/`le`/`duties`/`tier` mappers, audience `passage-api`, MFA flow, disabled OIDC/SAML federation placeholders); `keycloak_test.go` checks the export against this package and, with `PASSAGE_TEST_KEYCLOAK_URL` set (the `keycloak` CI job), logs a user in against a real Keycloak and passes the token through `JWTVerifier`; the live deprovisioning test runs `KeycloakAdmin` as the realm's `passage-identity-deprovision` service account, and `TestKeycloakDeprovisionClientHoldsManageUsersOnly` checks that account cannot read clients, roles, IdPs, events or realm settings, nor another realm.

**Policy bundle.** With `IDENTITY_BUNDLE_TOKEN`, `IDENTITY_BUNDLE_SIGNING_KEY_PATH`, `IDENTITY_BUNDLE_KEY_ID` and `IDENTITY_OPERATOR_TENANT_ID` set (plus `IDENTITY_BUNDLE_ADDR`, `IDENTITY_BUNDLE_TLS_CERT_PATH`, `IDENTITY_BUNDLE_TLS_KEY_PATH`, and optionally `IDENTITY_BUNDLE_REGO_PATH`), `GET /v1/identity/policy/bundle` (bearer token) is served over TLS on its own listener, never on `HTTP_ADDR`, and serves a signed OPA bundle: `authz.rego`, `data.json` (the catalogue with `assignments` rebuilt from the database, keyed tenant then IdP subject) and `.manifest` whose `revision` is a content hash, also the `ETag` (`If-None-Match` gets 304; compiles are cached 15 seconds). Only active, tenant-wide (no legal entity) assignments of active users in active tenants, whose role is a person-assignable catalogue duty, are compiled; legal-entity-scoped assignments are left out because `authz.rego` has no legal-entity rule yet. It reads across tenants through the operator tenant session plus `passage.policy_compile = 'on'` (migration 0008) and refuses to publish (503) when the operator is not registered, so a misconfiguration cannot publish an empty policy. Sidecar wiring: `deploy/policies/opa`.

Not implemented (issue #83 remainder): Keycloak attribute push (#80: the `tid`/`duties` attributes, re-enabling a reactivated user, and binding a SCIM user's `idp_subject` to its Keycloak id; deprovisioning is done), gateway host-to-tenant mapping and the tenant host column (#213), legal-entity-aware duties in rego, a reseal cron, and the live-cluster proof of sidecar bundle pull.

## Tenant residency (#605)

`identity_tenants` carries `residency` (`EU`, `US`, `UK`, `GLOBAL`; default `GLOBAL`) and an optional `region` (migration `0015_tenant_residency.sql`). `POST /v1/tenants` takes both and refuses a region the residency does not allow with 422 `OPS-1705` before anything is written; the code-to-regions table is `platform/go/residency` (one file, `residency.json`, also read by the evidence report `deploy/multi-region/tools/residency_report.py`). A tenant created without a region is unplaced; existing tenants are `GLOBAL` with no region. See `docs/ops/tenant-provisioning.md`.
