# API gateway (Envoy Gateway)

Part of #82 (item b). Services trust the `X-Depot-*` identity headers read by `platform/go/tenant` and `platform/go/authz`, so the gateway must be the only source of them. Live enforcement proof is tracked on #213.

Requires Envoy Gateway v1.4 or newer: `localJWKS` on the JWT provider and `shared` on rate-limit rules do not exist before it. The CRDs for v1.4.0 (Gateway API `GatewayClass`, `Gateway`, `HTTPRoute`; Envoy Gateway `ClientTrafficPolicy`, `SecurityPolicy`, `BackendTrafficPolicy`, `EnvoyProxy`) are vendored in `deploy/third_party/envoy-gateway-v1.4.0/crds.yaml` (Apache-2.0, extracted from the v1.4.0 `install.yaml`) and the manifests are validated against them with kubeconform.

## Request path

1. `ClientTrafficPolicy/depot-api-strip-identity-headers` removes `X-Depot-Tenant`, `-Legal-Entity`, `-LegalEntity`, `-User`, `-Duties`, `-Tier`, `-Auth-Time`, `-Service-Token` and `-Gateway-Secret` (the depot-server per-start secret, never client-supplied), and `X-Request-Id`, in `earlyRequestHeaders`, before any HTTP filter runs. Envoy then always generates the request id (`requestID: Generate`), so a client cannot choose the id the authorization records carry (B-04). `X-Depot-LegalEntity-Scope` is the one deliberate pass-through: a client sends `ALL` to ask for the all-entity read view, and `platform/go/tenant` honours it only on GET/HEAD/OPTIONS (and on POST routes a service wraps in `tenant.ReadOnlyPOST`, today analytics query) and only when the JWT-derived `X-Depot-Duties` holds `org.switcher.all-scope`; it grants nothing on its own. A route-level `RequestHeaderModifier` would run after JWT auth and delete the headers the JWT just set, so it is not used.
2. `SecurityPolicy/depot-api-jwt` (targets the Gateway, so every route and any future route is covered) validates the bearer token (issuer, audience `depot-api`, signature from the JWKS) and maps claims to headers: `tid` to `X-Depot-Tenant`, `le` to `X-Depot-Legal-Entity`, `sub` to `X-Depot-User`, `duties` to `X-Depot-Duties`, `tier` to `X-Depot-Tier`. Requests without a valid token get 401. A token whose `tid` is the nil platform tenant in its canonical form (`00000000-0000-0000-0000-000000000000`) is denied here; claim matching is exact-string only, so uppercase or unhyphenated spellings are not matched at the gateway. `platform/go/tenant` canonicalizes and rejects them (#257).
3. The same SecurityPolicy's `extAuth` asks the OPA in `authz-opa.yaml` about every request that passed the JWT filter (B-04, ADR-0017; "Authorization (ext_authz)" below). OPA's refusal is the single-host gateways' problem: `403 AUTH-0003` with `errors.duty_missing`, or `400 GW-0400` for a path that is not canonical (any percent-encoding included). When OPA cannot answer (not ready, unreachable, timed out) Envoy fails closed with a bare `403` and no body, where the single-host gateways answer `503 AUTH-0503`: Envoy Gateway v1.4 has no setting for the status on error. Alerts `DepotAuthzEnvoyCheckErrors` and `DepotAuthzOPAUnavailable` tell an outage from a refusal.
4. `BackendTrafficPolicy/depot-api-tenant-rate-limit` applies a global per-tenant limit keyed on `X-Depot-Tenant` by tier from `X-Depot-Tier`: starter 600/min, professional 3000/min, enterprise 12000/min. Every rule is `shared: true`, so a tenant's budget is shared across all routes rather than per route. A token with a missing or unknown tier matches the inverted-regex fallback rule and is limited to the starter 600/min (fail closed). Burst allowances (100/500/2000) are not expressible in this API and are not configured.

## Authorization (ext_authz)

One enforcement model on the three gateways (B-04, D23, ADR-0017): Envoy asks the same policy (`policies/authz`, identity's signed bundle) as devgateway and `depot-server`, and the services keep their own duty check behind it.

- `SecurityPolicy/depot-api-jwt` `extAuth`: gRPC to Service `depot-authz-opa` port 9191, `failOpen: false` (no answer, no request), and only `x-depot-tenant`, `x-depot-user`, `x-depot-legal-entity` and `x-request-id` sent to OPA, never the bearer token or cookies. It is on the gateway-level policy, so it covers every generated route; a SecurityPolicy on a route or a listener of `depot-api` would replace it for those routes, and `test_gateway.py` (`AuthzEnforcement`) fails on one.
- `envoyproxy.yaml`: Envoy Gateway runs `ext_authz` before `jwt_authn` by default. `EnvoyProxy/depot-api-proxy` (the Gateway's `infrastructure.parametersRef`) puts it after, so OPA sees the identity headers the JWT filter set from the verified token; the client's copies are removed in `earlyRequestHeaders` before either runs.
- `authz-opa.yaml`: OPA with the Envoy plugin (`openpolicyagent/opa:1.21.2-envoy-6`, digest-pinned), two replicas, answering `data.authz.envoy`. That rule decides on the verified subject, the method and the path the service receives (the public path without `/api`, or the service base of the D22 prefixes, `gateway_service_bases`, which `test_gateway.py` checks against the generated routes). It pulls identity's bundle from Service `identity-bundle:8443` like the sidecar in `deploy/policies/opa`. It is ready (`/health/ready`, the ConfigMap's `health.rego`) only once a verified bundle is active, the local mask is loaded and the bundle answers `data.authz.envoy`. Its REST API stays on loopback; a NetworkPolicy admits only the Envoy pods of `depot-api` to port 9191. Its pods carry `depot.io/opa-sidecar: "true"`, the label identity's NetworkPolicy admits to the bundle port.
- Decision logs: on, to the pod log, with `mask_decision: /system/log/mask`, which erases the whole input. The mask is the ConfigMap's `mask.rego`, loaded beside the bundle under `data.system`, which identity's bundle roots never claim, so no bundle can switch it off. Each logged decision keeps `result.record`, the `authz.decision` record (`platform/go/README.md`), with `labels.log_class: audit.other`.
- The record's subject is logpseudo's pseudonym of the user, computed in rego under the dedicated key in Secret `depot-log-pseudonym` (key `key`, base64 of 32 bytes; the `DEPOT_LOG_PSEUDONYM_KEY` the Go services read, so one key gives one pseudonym everywhere). The Secret is optional and created by hand; without it the subject is `[redacted]`. Generate a fresh 32-byte key for it and never copy fieldcrypt's master key into it: this Secret is mounted in the OPA pods, and field-encryption keys derive from the master key. Until the Secret is wired into the service charts, the fieldcrypt-keyed services pseudonymize under fieldcrypt's key, so their records and Envoy's name the same user with different pseudonyms (accepted until the wiring lands; ADR-0017).
- `envoy-podmonitor.yaml` scrapes the depot-api Envoy pods' ext_authz counters (`envoy_cluster_ext_authz_denied`, `_error`, `_ok`), so requests Envoy refuses are counted although no service sees them. `DepotAuthzEnvoyDenySpike` alerts on them.
- Secret `depot-authz-opa-bundle` (keys `token`, `ca.pem`, `public-key-oneline`) holds the same values as the sidecar's `opa-bundle` Secret: identity's `IDENTITY_BUNDLE_TOKEN`, the CA of identity's bundle certificate and identity's bundle public key on one line (`awk '{printf "%s\n",$0}' public.pem`). Create it by hand in `hello-ledger` until identity's bundle secrets are managed. Identity serves the bundle only with chart value `bundle.enabled`, which is off in dev: until both exist, the OPA is not ready and every API request through Envoy is refused (fail closed). The Kubernetes request path did not work end to end before (the issuer is not wired, D32).

What is checked and what is not: `gateway_test.rego` runs the shared route table (`policies/authz/testdata/route_table.json`) against `data.authz.envoy`, and `services/identity/authztest` runs OPA with this ConfigMap's decision-log settings, `mask.rego` and `health.rego` against a served bundle. It checks the masked log and the pseudonym against Go, and that a bundle without the mask or envoy rule logs nothing raw and leaves the pod not ready; devgateway and `depot-server` run the same table end to end. No live Envoy runs in CI, so the filter order, the headers Envoy sends and the plugin's handling of the answer are checked only against the Envoy Gateway v1.4 CRDs and the plugin's documented contract (#213).

## Routes and listeners

The API routes are generated (D31, B-02a, #661): `deploy/scripts/gen_httproutes.py` writes `httproutes.yaml` and the `targetRefs` of `BackendTrafficPolicy/depot-api-tenant-rate-limit`, and `make -C deploy test-gateway` runs it with `--check`, so a route cannot drift from the code. Do not edit either by hand; change the code and rerun the generator. As built there are 83 HTTPRoutes to 60 Services (before: 17 routes, 15 services). The generator takes:

- **Prefixes** from the web shell: every `/api/v1/<prefix>` in `apps/web/src`, `apps/technician/src` and `apps/warehouse-mobile/src` (tests and the demo backend left out), as a literal or as a path joined to a bare `/api/v1` root (the assets client's `/assets` and `/leases`, the generic case routes of the service client, the migration-factory client's `/migration` and `/cutover`). When a client file has another `/api/v1/<x>` base too, only the literals in a call that passes the root count, however the call is wrapped over lines. The portal SPAs are not scanned: their `/api/v1/...` goes to their own BFF on Gateway `depot-portals` (below). 79 prefixes today, plus `workflows` (workflow-ts's decision API, which has no OpenAPI document) and `ar` (prediction-py's invoice prediction, #47), which partners and agents call on `/v1`.
- **Owner** from the OpenAPI documents (`<service>/api/openapi.yaml`): the service whose paths start with `/v1/<prefix>`, `/api/v1/<prefix>`, `/<prefix>/v1` or `/<prefix>`. A prefix no dev chart's document serves stops the generator with the files that call it.
- **Backend** from the dev Argo CD Application of that chart (release name and namespace) and the chart's `templates/service.yaml` with its values and the dev values file (the Service name and its `http` port). `test_argocd_apps.py` renders each of those charts with helm and checks that the Service and port exist. Several charts name their Service `<release>-<chart>` (`pricing-pricing`, `sales-sales`, `analytics-analytics`, `hr-depot-hr`, ...): the hand-written routes to `pricing`, `sales` and `analytics` named Services that do not exist.

Each route is named after its prefix and has two rules, one per public path: `/api/v1/<prefix>` (the browser) and `/v1/<prefix>` (partners and agents). A split route (below) has instead one rule per path element under `/api/v1/<prefix>` and one rule holding all its `/v1/<prefix>/<element>` matches. Both public paths reach the service under the base its OpenAPI document uses: `/v1/<prefix>` by convention (`/api/v1/<prefix>` rewritten, `/v1/<prefix>` passed through). Recorded exceptions (D22), where both public paths are rewritten to the service's own base (prediction-py, the former fifth, documents `/v1` since B-02a and keeps a hidden `/api/v1` alias, so `predictions` and `ar` follow the convention):

| Prefix | Service | Service base |
|---|---|---|
| `agents`, `copilot` | `agent-runtime` (agents-ts) | `/api/v1/<prefix>` |
| `migration`, `cutover` | `depot-migration-factory-migration-factory` | `/api/v1/<prefix>` |
| `edi` | `edi` | `/edi/v1` |
| `print` | `print` | `/print/v1` |
| `mcp` | `mcp-gateway` (mcp-ts) | `/mcp` |

The agents API (DEPOT-294) has no web BFF in front of it (ADR-0009: the shell sends its bearer token to this Gateway). Its route-table entry is HTTPRoute `agents`: `/api/v1/agents/**` is passed through and `/v1/agents/**` is rewritten to `/api/v1/agents`, both to `agent-runtime:8080`, so these reach the runtime: `/copilot/conversations` and `/copilot/conversations/{id}/messages` (streamed `text/event-stream` responses; every rule sets `timeouts.request: 0s`, because Envoy's route timeout is a finite 15s when none is set, and the route and its policies carry no buffer or compression setting; `test_gateway.py` `AgentsApiRoute` pins both), `/budgets`, `/definitions`, `/availability`, `/approvals`, `/runs` with `/runs/{id}/actions/{id}/decision` and `:undo`, and `/briefings` with `:generate` and `:mark-read`. Authorization is the ext_authz OPA: the two conversation POSTs are granted by duty `mcp.copilot.use` (`policies/authz/data.json`); every other agents-ts path has its own duty entry in `policies/authz/data.json` and a Rego allowed and denied case (DEPOT-320; `services/agents-ts/test/actions-api.test.ts` fails when an `openapi.yaml` operation has no entry). `/api/v1/knowledge/*` has duty entries on the service base but is not routed here. The route already existed; DEPOT-294 added the first duty entry and the tests. On a single-host depot-server install the shipped `node.yaml` service `agents-ts` has `route: agents` and `keepApiPrefix: true`, so `/api/v1/agents/**` reaches it under `/api/v1/agents/**` (the gateway strips `/api` for every route, and agents-ts serves only `/api/v1/...`); `tools/depot-server/agents_stream_test.go` runs the proxy tests against the shipped route key `agents`.

Prefixes served by a Service of another name, as before: `inbox`, `workitems`, `notify` and `batch` by `batch`; `data` and `metadata` by `metadata` (port 80); `controlling` by `costacct`; `consol` by `consolidation`; `procurement` by `purchasing-purchasing` (port 80); `reporting` by `finreport`; `service` and the generic case routes by `fieldservice`; `sod`, `security`, `trade`, `privacy` and `compliance` by `compliance-compliance`; `authz`, `tenant`, `legal-entities` and `identity` by `identity`. `batch` and `metadata` run in namespaces of their own (`deploy/envs/dev/apps/services.yaml`), so their backendRefs carry the namespace and a `ReferenceGrant` named `depot-api-routes` in each of those namespaces admits HTTPRoutes from `hello-ledger` to that one Service; the hand-written `inbox` and `data` routes pointed at `hello-ledger` and reached nothing. ReferenceGrant's CRD comes with the Envoy Gateway chart but is not in the vendored file, so `validate-gateway-schema` skips it and `test_gateway.py` checks it.

`production` is shared: the production service owns the prefix, and processmfg's document has 25 path elements after it that production does not serve (`batch-orders`, `formulas`, `batches:merge`, ...). Those get routes of their own and win as the longer prefix. Their names come from chunking: the elements, sorted, are cut into groups of 15 (an HTTPRoute holds at most 16 rules, one of them the `/v1` pass-through), named `processmfg-1`, `processmfg-2`, ... (plain `processmfg` when one group is enough), so adding elements to processmfg's document can renumber them. Gateway API matches a prefix path element by element, so `batches` and `batches:merge` are separate matches.

Not routed, because neither the shell nor the portals call them through this Gateway: the charts with an API but no route at all (audit, close, carrier-gateway, configurator, forecast, scheduler-opt, hello-ledger), and the prefixes `events` (batch), `tenants` (identity), `knowledge` (agent-runtime), batch's `/v1/workflows/definitions` and `/instances`, receivables' `/webhooks/v1` and the edi partner endpoints on the AS2 edge. Health endpoints are not routed. Envoy keeps removing the client identity headers listed above (every `X-Depot-*` header but `X-Depot-LegalEntity-Scope`); the generated routes add no header filter. In dev the Envoy proxies reach the services only once the B-01a NetworkPolicies admit Gateway `depot-api`.

The portal BFFs call their services inside the cluster, not through this Gateway. Their `upstreams` values named `<service>.<service>.svc`, namespaces no environment has; the dev and stage values now name the Services in `hello-ledger` (`receivables-receivables`, `sales-sales`, `purchasing-purchasing:80`, ...), and `test_gateway.py` checks each against the same Service table.

The Gateway has two listeners. `https` (443, TLS terminate, Secret `depot-api-tls`, to be issued by cert-manager or supplied by the environment) is the listener for stage and prod. `http-dev` (80) is for dev only; remove it in any non-dev environment.

## Region health edge (DPT-50, OPS-1703)

DNS health checks read `GET /healthz/region` of each region without a Depot token, so it cannot sit behind the JWT SecurityPolicy that targets Gateway `depot-api`. It has a Gateway of its own, `depot-region`, like the AS2 edge: `region-gateway.yaml` holds the Gateway (one HTTPS listener `region-https`, hostname `region.dev.depot.dev`), its Certificate, HTTPRoute `ops-region-health` (the exact path `/healthz/region`, `GET`, to Service `ops` port 8080 and nothing else), a ClientTrafficPolicy that strips the identity headers and requires TLS 1.2, and a per-address rate limit. The answer names the region and its role (`200` while PRIMARY, `503` with `Retry-After: 30` otherwise). `test_gateway.py` (`RegionHealthEdge`) checks that no SecurityPolicy reaches it and nothing else is routed there. Per region, override the hostname in the environment's overlay (`region.<env>.depot.dev`).

## Customer and supplier portal edge (#30, #511)

The portals sign in with their own Keycloak clients and keep a cookie session in their BFF, so their requests carry no Depot JWT and cannot pass the JWT SecurityPolicy on `depot-api`. They have a Gateway of their own, `depot-portals` (`portal-gateway.yaml`):

- Two HTTPS listeners, `customer-https` (`customer.dev.depot.dev`, Secret `depot-portal-customer-tls`) and `supplier-https` (`supplier.dev.depot.dev`, Secret `depot-portal-supplier-tls`), with cert-manager Certificates from ClusterIssuer `depot-local-ca` in dev. No plain-HTTP listener.
- HTTPRoutes `customer-portal` and `supplier-portal`, one per listener, to the BFF Services `customer-portal:8080` and `supplier-portal:8080` (release names from `deploy/envs/dev/apps/services.yaml`), for the path prefixes `/bff/` and `/api/v1/` only; the BFFs' health checks stay inside the cluster.
- `ClientTrafficPolicy/depot-portals-client`: TLS 1.2 or newer, and every `X-Depot-*` header removed in `earlyRequestHeaders` (including `X-Depot-LegalEntity-Scope`, which only the API gateway passes through).
- `SecurityPolicy/depot-portal-{customer,supplier}-cors`: CORS for the portal's own origin only, with credentials, so no other site can read a portal answer with the session cookie or send a preflighted request; the BFF also checks `Origin` and the CSRF token. No JWT, OIDC or ext-auth filter.
- `BackendTrafficPolicy/depot-portal-{customer,supplier}-limits`: a global limit of 1200 requests a minute per client address and portal (IPv4 and IPv6, `sourceCIDR` Distinct). Every rule is `shared: true`, so one address has one bucket across `/bff/` and `/api/v1/` of a portal (without it Envoy Gateway counts each route match separately); the two portals count separately. This is on top of the BFFs' per-session limits. Like the AS2 limit it needs the real client address at Envoy.
- The supplier BFF limits its public routes (`/bff/prospects`, `/bff/invites/*`) per client address. Behind this edge the TCP peer is always an Envoy pod, so its `trustedProxies` is the Envoy pods' range in each environment (`10.42.0.0/16`, the k3s pod CIDR, in dev; the stage cluster's pod CIDR in stage), and the BFF reads the client from `X-Forwarded-For`. The customer BFF has only per-session limits.

Open: the portal apps' static files are not served here (no image hosts them yet; they would be a second backend on the same listeners, with `sw.js` served `Cache-Control: no-cache`). WAF rules are not expressible in Envoy Gateway. For stage and prod, override the hostnames (`customer.<env>.depot.dev`) and the issuer in the environment's overlay, together with the portals' `appOrigin` and `oidc.redirectUri`. `test_gateway.py` (`PortalEdge`) checks the listeners, certificates, routes, the absence of any JWT policy, CORS, header removal and the rate limit.

## AS2 edge (#483)

Trading partners post AS2 messages and asynchronous MDNs to the edi AS2 listener without a Depot token: edi authenticates each request by its AS2 signature against the partner certificate pinned on the transport (see `services/edi/README.md`, "AS2 listener security"). They come in through a second Gateway, `depot-as2`, so the JWT SecurityPolicy, which targets Gateway `depot-api`, cannot apply to them, and the API routes cannot be reached without a token through it:

- `as2-gateway.yaml`: Gateway `depot-as2`, one listener `as2-https` (443, TLS terminate, hostname `as2.dev.depot.dev`, Secret `depot-as2-tls`). No plain-HTTP listener.
- `as2-certificate.yaml`: cert-manager Certificate `depot-as2-tls` for that hostname (RSA 2048, many AS2 stacks lack ECDSA suites), from ClusterIssuer `depot-local-ca` in dev. cert-manager's CRDs are not vendored, so `validate-gateway-schema` skips the Certificate and `test_gateway.py` checks it.
- `as2-httproute.yaml`: HTTPRoute `edi-as2`, the only route on the AS2 Gateway: `POST` with path prefix `/as2/v1/` to Service `edi-as2` port 8081 (the edi chart with `transports.as2.enabled`). Nothing else of edi and no other service is routed there.
- `as2-clienttrafficpolicy.yaml`: TLS 1.2 or newer, and the `X-Depot-*` headers removed in `earlyRequestHeaders` (the listener ignores them anyway).
- `as2-backendtrafficpolicy.yaml`: `requestBuffer.limit: 8Mi`, the listener's own body cap, so oversized bodies get 413 at the edge; and a global rate limit of 600 requests a minute per client address (IPv4 and IPv6, `sourceCIDR` Distinct; same rate-limit service as the tenant limit). Behind it edi keeps a token bucket per AS2 endpoint (`EDI_AS2_RATE_PER_MINUTE`, default 120 with bursts of 60). The per-address limit needs the real client address at Envoy (`externalTrafficPolicy: Local` on the Envoy Service, or PROXY protocol); behind a load balancer that rewrites the source it limits all partners together.

The edi chart's NetworkPolicy admits only the Envoy proxies of `depot-as2` (namespace `envoy-gateway-system`, labels `gateway.envoyproxy.io/owning-gateway-name: depot-as2` and `owning-gateway-namespace: hello-ledger`) to the AS2 port; the API and metrics ports keep their previous reach (#82 item 2). `deploy/envs/dev/values/edi.yaml` turns the listener and the workers on with `EDI_AS2_PUBLIC_URL=https://as2.dev.depot.dev`.

Operations: point DNS for `as2.<env>.depot.dev` at the load balancer address of the `depot-as2` Envoy Service (its own address, not depot-api's). In dev the certificate comes from the local CA, which partners do not trust; for stage and prod set the hostname (`as2.stage.depot.dev`, `as2.prod.depot.dev`, like the hello-ledger hosts) and issue the certificate from a publicly trusted issuer (ACME), or give partners the CA to pin. Partners that allow-list our address need the AS2 Envoy Service's address. The edge has no allow-list of partner addresses: the signature is the authentication.

## Plant edge for iot-edge connectors (#25)

iot-edge connectors redeem a one-time enrollment token without a session and then call the shop floor service with the mTLS client certificate they were issued, so they come in through a third Gateway, `depot-edge` (`edge-gateway.yaml`, `edge-certificate.yaml`, `edge-clienttrafficpolicy.yaml`, `edge-httproute.yaml`), outside the JWT SecurityPolicy:

- The listener (`edge-https`, 443, hostname `edge.<env>.depot.dev`) asks for a client certificate but does not require one (`clientValidation.optional`): a connector with no certificate yet may call only `POST /v1/shopfloor/edge-nodes/{id}:enroll`, whose body token is its credential. A certificate that is presented must chain to the edge CA in Secret `depot-edge-ca-trust` (key `ca.crt`, the CA certificate of the shop floor chart's `edgePki` issuer).
- Envoy forwards the verified certificate's subject in `X-Forwarded-Client-Cert` (`SanitizeSet`: built from the verified certificate, a client-sent value is dropped). The shop floor service reads the common name `edge:<node id>`, finds the node's tenant (`edge_node_tenant`, migration shopfloor/0026), and treats the call as that connector with the one connector duty; it still matches the name to the node's bound `connectorSubject`. A request that already carries a tenant is left alone.
- The only route, `shopfloor-edge`, exposes what a connector calls (`:enroll`, `:renew-certificate`, `:heartbeat`, `GET .../config`, `GET .../control-recipes`, `POST .../control-recipes/{rid}:report` and `POST /v1/shopfloor/machine-events`) and nothing else of the shop floor service; `test_gateway.py` checks the matches against the paths the service serves and the connector calls. Enforcement against a live Envoy is #213, and a rate limit on the public redeem route is open.

## Dev JWKS and claim contract

`depot-dev-jwks` holds a static placeholder public key (kid `depot-dev-placeholder`); no private key is kept, so nothing can mint accepted tokens until #80 supplies an IdP. To switch to the IdP, replace `localJWKS` in the SecurityPolicy provider with `remoteJWKS: {uri: https://<idp>/realms/<realm>/protocol/openid-connect/certs}` and set `issuer` to the realm URL. Realm-per-tenant needs one provider per realm.

`duties` must be a single string claim holding the comma-joined duty names (for example `ap_clerk,approver`), because `tenant.go` splits `X-Depot-Duties` on commas. Envoy base64-JSON-encodes array claims when copying them to a header, so a string array breaks parsing. In Keycloak, use a "Hardcoded claim" or script mapper that emits one string (JSON type String, multivalued off); do not use the multivalued "User Realm Role" style mapper.

## Assumptions to confirm with #80 and #213

- Claim names `tid` (matches `services/identity/jwt.go`), `le`, `duties`, `tier` are the Keycloak mapper outputs.
- The Envoy Gateway install provides the CRDs, `ClientTrafficPolicy.headers.earlyRequestHeaders` support, and the global rate-limit service. It is the Argo CD app `deploy/envs/dev/apps/envoy-gateway.yaml` (OCI chart `docker.io/envoyproxy/gateway-helm`, pinned v1.4.6, sync wave 0, ServerSideApply for the CRDs); its values point `config.envoyGateway.rateLimit` at the Valkey in `deploy/envoy-gateway/ratelimit-valkey.yaml` (counters only, no persistence), which every `Global` rate limit here needs. When that Valkey or the rate-limit service cannot answer within 20 ms, the limits fail open (`failClosed: false`, `timeout: 20ms`): requests pass unlimited instead of getting 500, because the limits share capacity and are not an access control, and the single counter pod must not be able to stop the whole API (B-09 part b; `docs/ops/runbooks/ratelimit-valkey-down.md`). Stage runs this directory through a generated copy, `deploy/envs/stage/platform/gateway` (`deploy/scripts/stage_apps.py`): `depot-api` has only its `https` listener, for `app.stage.depot.dev`, with `depot-api-tls` issued by the stage CA (`api-certificate.yaml`); the JWT provider `depot-stage-idp` trusts the issuer `https://idp.stage.depot.dev/realms/depot` and fetches the realm's keys from the in-cluster Keycloak Service (`remoteJWKS` with `backendRefs` to `keycloak:8080`, which Keycloak's NetworkPolicy admits from these Envoy pods) instead of the dev placeholder JWKS, which stage leaves out; the other edges get stage hosts and the `depot-stage-ca` issuer; the ext_authz OPA's bundle Secret is an ExternalSecret; there is no PodMonitor while stage has no monitoring. `test_argocd_apps.py` checks that no stage listener is plain HTTP and every listener's certificate is issued in stage. ## Service tokens

Decision (#226): signed service-principal tokens now, SPIFFE/mTLS later. A service that calls another no longer forwards the end user's duties; it sends `X-Depot-Service-Token`, an Ed25519-signed token (`platform/go/tenant/service.go`) with claims `iss` (caller), `aud` (target), `tid`, `le` (one explicit legal entity), `act` (the end user, which the target records as the actor), `duties` (the caller's own grant for that target), `iat`, `exp` (at most 60 seconds) and `jti`. The target's middleware replaces every user header with the token's principal; an invalid, expired, mis-addressed, replayed or over-granted token is a 401, never a fallback to user headers.

- Grants are static: `policies/authz/data.json` `service_grants` (caller, then target, then duties), mirrored in `tenant.serviceGrants` and kept equal by a test. Today: receiving to ledger (`ledger.entry.post`, `ledger.journal.reverse`), receiving to close (`period.check`), close to ledger (`ledger.ledger.lookup`, `ledger.entry.post`, `ledger.journal.reverse`, `ledger.balance.read`, `ledger.account.lookup`, and the flag `ledger.period.postclosed`, the one flag duty any grant holds, which close signs only on the closing entry of a year-end run and on the reversals of a re-run), receiving to purchasing (`procurement.invoicing-plan.settle`, #289; `procurement.purchase-order.lookup`, #305), receiving to inventory (`inventory.ownership-change.read`, #305), payables to ledger (`ledger.balance.read`, `ledger.ledger.lookup`, `ledger.entry.lookup`, `ledger.entry.post`), costing to ledger (`ledger.entry.post`, `ledger.balance.read`, `ledger.ledger.lookup`; PPV vouchers, close adjustment and the inventory tie-out), payables to fx (`fx.rate.lookup`, #305), payables to tax (`tax.withholding.calculate`, #350), payables to party (`party.vendor-bank.reveal`, #352), receiving to party (`party.read`, #354), party to numbering (`numbering.sequence.allocate`), hr to numbering (`numbering.sequence.allocate`, requisition numbers; Duties marked `service_only` in the catalogue are never assignable to a person and are named as the `duty_missing` hint only on routes no person duty grants; a read route accepts either its human duty or the service duty (`RequireAnyDuty`), and callers sign only the exact duty of each call (`ApplyDuties`).
- No umbrella grants (#341): the grant tables hold only the narrow duties. The umbrella ones kept for the 0.1.0 rolling deploy (`ledger.journal.post` and `ledger.journal.read` for receiving and payables to ledger, `numbering.write` for party to numbering, #321, #333) are removed, so a token that still carries one is over-granted and gets 401. Every caller has signed only the narrow duties since #333.
- The gateway strips the header from clients (`ClientTrafficPolicy`), so only in-cluster callers holding a signing key can present one.
- The legal entity is explicit and bound to the end user: `Mint` refuses an entity outside the user's `LegalEntityScopeList` (or any entity for a no-entity ALL-scope read), so a service cannot act in an entity the user could not.
- Grants are one route per duty. Service-only duties: `numbering.sequence.allocate` (`POST .../next`; `numbering.write` still also covers creating a sequence), `ledger.entry.post` (`POST /journal-entries`), `ledger.entry.lookup` (`GET /journal-lines`, which takes a `documentId` filter), `ledger.ledger.lookup` (`GET /ledgers/{id}`). Person duties `ledger.entry.validate`, `ledger.batch.post` and `ledger.set.post` open `/validate`, a batch post and a ledger-set post alone; every route also still accepts its umbrella duty (`ledger.journal.post`, `ledger.journal.read`), so existing roles keep working with no assignment change. Services sign only the narrow duties, and the grant tables list only those (#341).
- Callers set `DEPOT_SERVICE_NAME` and `DEPOT_SERVICE_SIGNING_KEY_FILE` (a mounted secret holding the base64 32-byte Ed25519 seed; `DEPOT_SERVICE_SIGNING_KEY` is the inline form) and optionally `DEPOT_SERVICE_KEY_ID`. Targets set `DEPOT_SERVICE_NAME` and `DEPOT_SERVICE_PUBLIC_KEYS` (`caller[:kid]=base64pub,...`, not secret). Several keys per caller (distinct `kid`) allow rotation: add the new public key everywhere, switch the caller's seed and `kid`, then drop the old key. A repeated caller and kid, or a malformed value, stops the target at startup. Charts: targets (ledger, close, numbering, purchasing, inventory, fx, product, payables, party) take `serviceIdentity.publicKeys`; callers (receiving, costing, payables, party, batch, workflow-ts, close) take `serviceIdentity.signingKeySecret` (a Secret with key `signing-key`, mounted read-only at `/var/run/depot/service-identity`, mode 0440 with pod `fsGroup: 65532`) and `serviceIdentity.keyId`. The all-scope exception in Mint applies only to read-only grants.
- Rollout order (#321): a target checks every token against its own build's grant table, and callers sign only the exact duty of each call, so a caller that signs something its target's build or configuration does not know yet gets 401. Always configure and deploy targets first, callers second, in this order: (1) set the target's `serviceIdentity.publicKeys` for each of its callers and apply the target's migration `service_token_replay` (below; a target build with public keys refuses to start without it); (2) roll out the target version that knows the callers' duties (`ledger.entry.post`, `ledger.entry.lookup`, `ledger.ledger.lookup`, `numbering.sequence.allocate`); (3) only then deploy the callers' versions and signing-key Secrets. Caller to target pairs: receiving to ledger, close, purchasing and inventory; payables to ledger and fx; costing to ledger (set the ledger's `serviceIdentity.publicKeys` for costing first, and costing's `ledgerUrl`, `LEDGER_URL`, and signing key); consolidation to ledger (balance read, `ledger.balance.read`) and intercompany to ledger (`ledger.entry.post`, `ledger.journal.reverse`, `ledger.ledger.lookup`), each the same way: the ledger's `serviceIdentity.publicKeys` for the caller first, then the caller's `ledgerUrl` and signing key (without them consolidation cannot collect and intercompany cannot post, and both answer 503 on those routes); party to numbering; batch to product; workflow-ts to payables; close to ledger (close also needs `ledgerUrl`, `LEDGER_URL`); ledger to close (period status, duty `period.check`; ledger also needs `closeUrl`, `CLOSE_URL`, and its signing key, and close needs the ledger public key). Ledger to fx (rates for ledger sets that span currencies, duty `fx.rate.lookup`; optional `fxUrl`, `FX_URL`, which needs the signing key, and fx needs the ledger public key). Payables is both a target (of workflow-ts) and a caller, so it goes after ledger and fx and before workflow-ts; close likewise goes after ledger and before receiving. Party is a target of receiving (vendor lookup, #354) and payables (bank reveal), so it goes after numbering and before receiving and payables; set its `serviceIdentity.publicKeys` and apply `service_token_replay` first. The payables to tax grant is seeded, but tax does not verify service tokens yet. Roll back in the reverse order, callers first.
- Replay memory has two layers. Each process keeps an expiry heap capped by `DEPOT_SERVICE_REPLAY_CACHE_SIZE` (default 100000, sized for about 1700 tokens/s per pod over the 60s lifetime; a full cache rejects). Every target that has a database (ledger, close, numbering, purchasing, inventory, fx, product, payables, party) also records each accepted `iss:jti` in its own table `service_token_replay` (tenant-scoped, one migration per service identical to `dbx.ServiceTokenReplayDDL`, a test keeps them equal), where an insert conflict means another replica already accepted the token, so a captured token cannot be replayed on a second pod within its 60s life. The store fails closed: a database error refuses the token with a retryable 503 `COM-0503` (`Retry-After: 1`, so callers do not treat it as an auth fault) and is logged and counted (`depot_service_token_replay_store_failures_total`; refused replays are `depot_service_token_replays_refused_total`; alert on the first). `tenant.ShareReplayCache(ctx, pool)` runs at startup after migrations and refuses to start when service tokens are enabled (public keys configured) and the table or `service_token_replay_purge()` is missing, so apply the migration before deploying a target build. Row-level security is enabled but not forced on the table (allowlisted in `tools/rlscheck`): `depot_app` may only insert under the tenant policy and call the `SECURITY DEFINER` purge, which deletes every tenant's expired ids and runs at most once a minute per process. mTLS between pods remains the follow-up.
- Every accepted token is logged (`service call`: caller, end-user actor, legal entity, path, correlation id).
- With no signing key a caller keeps forwarding the user's own headers (previous behaviour) for reads (receiving to purchasing and inventory, payables to fx, payables to ledger); state-changing calls (ledger posts, plan row settlement, payment runs, numbering allocation) refuse to send unsigned. A malformed key stops startup.
