# API gateway (Envoy Gateway)

Part of #82 (item b). Services trust the `X-Passage-*` identity headers read by `platform/go/tenant` and `platform/go/authz`, so the gateway must be the only source of them. Live enforcement proof is tracked on #213.

Requires Envoy Gateway v1.4 or newer: `localJWKS` on the JWT provider and `shared` on rate-limit rules do not exist before it. The CRDs for v1.4.0 (Gateway API `GatewayClass`, `Gateway`, `HTTPRoute`; Envoy Gateway `ClientTrafficPolicy`, `SecurityPolicy`, `BackendTrafficPolicy`) are vendored in `deploy/third_party/envoy-gateway-v1.4.0/crds.yaml` (Apache-2.0, extracted from the v1.4.0 `install.yaml`) and the manifests are validated against them with kubeconform.

## Request path

1. `ClientTrafficPolicy/passage-api-strip-identity-headers` removes `X-Passage-Tenant`, `-Legal-Entity`, `-LegalEntity`, `-User`, `-Duties`, `-Tier` and `-Service-Token` in `earlyRequestHeaders`, before any HTTP filter runs. `X-Passage-LegalEntity-Scope` is the one deliberate pass-through: a client sends `ALL` to ask for the all-entity read view, and `platform/go/tenant` honours it only on GET/HEAD/OPTIONS (and on POST routes a service wraps in `tenant.ReadOnlyPOST`, today analytics query) and only when the JWT-derived `X-Passage-Duties` holds `org.switcher.all_scope`; it grants nothing on its own. A route-level `RequestHeaderModifier` would run after JWT auth and delete the headers the JWT just set, so it is not used.
2. `SecurityPolicy/passage-api-jwt` (targets the Gateway, so every route and any future route is covered) validates the bearer token (issuer, audience `passage-api`, signature from the JWKS) and maps claims to headers: `tid` to `X-Passage-Tenant`, `le` to `X-Passage-Legal-Entity`, `sub` to `X-Passage-User`, `duties` to `X-Passage-Duties`, `tier` to `X-Passage-Tier`. Requests without a valid token get 401. A token whose `tid` is the nil platform tenant in its canonical form (`00000000-0000-0000-0000-000000000000`) is denied here; claim matching is exact-string only, so uppercase or unhyphenated spellings are not matched at the gateway. `platform/go/tenant` canonicalizes and rejects them (#257).
3. `BackendTrafficPolicy/passage-api-tenant-rate-limit` applies a global per-tenant limit keyed on `X-Passage-Tenant` by tier from `X-Passage-Tier`: starter 600/min, professional 3000/min, enterprise 12000/min. Every rule is `shared: true`, so a tenant's budget is shared across all routes rather than per route. A token with a missing or unknown tier matches the inverted-regex fallback rule and is limited to the starter 600/min (fail closed). Burst allowances (100/500/2000) are not expressible in this API and are not configured.

## Routes and listeners

Each service has an `HTTPRoute` named after it. `/api/v1/<svc>` is rewritten to `/v1/<svc>` (the BFF convention from #199); `/v1/<svc>` passes through for partners and agents. Health endpoints are not routed. Add a service by adding its HTTPRoute and listing it in the `targetRefs` of the BackendTrafficPolicy (the SecurityPolicy targets the Gateway); `deploy/scripts/test_gateway.py` fails if a route is left out.

The Gateway has two listeners. `https` (443, TLS terminate, Secret `passage-api-tls`, to be issued by cert-manager or supplied by the environment) is the listener for stage and prod. `http-dev` (80) is for dev only; remove it in any non-dev environment.

## Dev JWKS and claim contract

`passage-dev-jwks` holds a static placeholder public key (kid `passage-dev-placeholder`); no private key is kept, so nothing can mint accepted tokens until #80 supplies an IdP. To switch to the IdP, replace `localJWKS` in the SecurityPolicy provider with `remoteJWKS: {uri: https://<idp>/realms/<realm>/protocol/openid-connect/certs}` and set `issuer` to the realm URL. Realm-per-tenant needs one provider per realm.

`duties` must be a single string claim holding the comma-joined duty names (for example `ap_clerk,approver`), because `tenant.go` splits `X-Passage-Duties` on commas. Envoy base64-JSON-encodes array claims when copying them to a header, so a string array breaks parsing. In Keycloak, use a "Hardcoded claim" or script mapper that emits one string (JSON type String, multivalued off); do not use the multivalued "User Realm Role" style mapper.

## Assumptions to confirm with #80 and #213

- Claim names `tid` (matches `services/identity/jwt.go`), `le`, `duties`, `tier` are the Keycloak mapper outputs.
- The Envoy Gateway v1.4+ install (#213) provides the CRDs, `ClientTrafficPolicy.headers.earlyRequestHeaders` support, and a global rate-limit service backed by Valkey. The Argo CD app `deploy/envs/dev/apps/gateway.yaml` is annotated `passage.dev/requires` and uses `SkipDryRunOnMissingResource` so it can sync once the CRDs exist.
- Services are still reachable inside the cluster without the gateway; restricting that is item 2 of #82.
- Host-to-tenant matching (a request host must resolve to the token's tenant) is deferred until the tenant registry in #83 exists.

## Tests

`make -C deploy test-gateway` first validates the rendered kustomization against the vendored CRDs with `kubeconform -strict` (`go install github.com/yannh/kubeconform/cmd/kubeconform@v0.6.7`), then runs `scripts/test_gateway.py` with `kubectl kustomize`: header removal covers every header in `tenant.go` plus the explicit list, the SecurityPolicy targets the Gateway, rate-limit rules are shared, keyed on tenant, with the 600/min fallback, the TLS listener, and the `/api` rewrite. It needs `pyyaml`.

## Service tokens

Decision (#226): signed service-principal tokens now, SPIFFE/mTLS later. A service that calls another no longer forwards the end user's duties; it sends `X-Passage-Service-Token`, an Ed25519-signed token (`platform/go/tenant/service.go`) with claims `iss` (caller), `aud` (target), `tid`, `le` (one explicit legal entity), `act` (the end user, which the target records as the actor), `duties` (the caller's own grant for that target), `iat`, `exp` (at most 60 seconds) and `jti`. The target's middleware replaces every user header with the token's principal; an invalid, expired, mis-addressed, replayed or over-granted token is a 401, never a fallback to user headers.

- Grants are static: `policies/authz/data.json` `service_grants` (caller, then target, then duties), mirrored in `tenant.serviceGrants` and kept equal by a test. Today: receiving to ledger (`ledger.entry.post`, `ledger.journal.reverse`), receiving to close (`period.check`), close to ledger (`ledger.ledger.lookup`), receiving to purchasing (`procurement.invoicing-plan.settle`, #289; `procurement.purchase-order.lookup`, #305), receiving to inventory (`inventory.ownership-change.read`, #305), payables to ledger (`ledger.balance.read`, `ledger.ledger.lookup`, `ledger.entry.lookup`, `ledger.entry.post`), payables to fx (`fx.rate.lookup`, #305), payables to tax (`Calculate withholding tax`, #350), payables to party (`party.vendor_bank.reveal`, #352), receiving to party (`party.read`, #354), party to numbering (`numbering.sequence.allocate`), batch to product, workflow-ts to payables (`payment-run.execute`). Duties marked `service_only` in the catalogue are never assignable to a person and are named as the `duty_missing` hint only on routes no person duty grants; a read route accepts either its human duty or the service duty (`RequireAnyDuty`), and callers sign only the exact duty of each call (`ApplyDuties`).
- No umbrella grants (#341): the grant tables hold only the narrow duties. The umbrella ones kept for the 0.1.0 rolling deploy (`ledger.journal.post` and `ledger.journal.read` for receiving and payables to ledger, `numbering.write` for party to numbering, #321, #333) are removed, so a token that still carries one is over-granted and gets 401. Every caller has signed only the narrow duties since #333.
- The gateway strips the header from clients (`ClientTrafficPolicy`), so only in-cluster callers holding a signing key can present one.
- The legal entity is explicit and bound to the end user: `Mint` refuses an entity outside the user's `LegalEntityScopeList` (or any entity for a no-entity ALL-scope read), so a service cannot act in an entity the user could not.
- Grants are one route per duty. Service-only duties: `numbering.sequence.allocate` (`POST .../next`; `numbering.write` still also covers creating a sequence), `ledger.entry.post` (`POST /journal-entries`), `ledger.entry.lookup` (`GET /journal-lines`, which takes a `documentId` filter), `ledger.ledger.lookup` (`GET /ledgers/{id}`). Person duties `ledger.entry.validate`, `ledger.batch.post` and `ledger.set.post` open `/validate`, a batch post and a ledger-set post alone; every route also still accepts its umbrella duty (`ledger.journal.post`, `ledger.journal.read`), so existing roles keep working with no assignment change. Services sign only the narrow duties, and the grant tables list only those (#341).
- Callers set `PASSAGE_SERVICE_NAME` and `PASSAGE_SERVICE_SIGNING_KEY_FILE` (a mounted secret holding the base64 32-byte Ed25519 seed; `PASSAGE_SERVICE_SIGNING_KEY` is the inline form) and optionally `PASSAGE_SERVICE_KEY_ID`. Targets set `PASSAGE_SERVICE_NAME` and `PASSAGE_SERVICE_PUBLIC_KEYS` (`caller[:kid]=base64pub,...`, not secret). Several keys per caller (distinct `kid`) allow rotation: add the new public key everywhere, switch the caller's seed and `kid`, then drop the old key. A repeated caller and kid, or a malformed value, stops the target at startup. Charts: targets (ledger, close, numbering, purchasing, inventory, fx, product, payables, party) take `serviceIdentity.publicKeys`; callers (receiving, payables, party, batch, workflow-ts, close) take `serviceIdentity.signingKeySecret` (a Secret with key `signing-key`, mounted read-only at `/var/run/passage/service-identity`, mode 0440 with pod `fsGroup: 65532`) and `serviceIdentity.keyId`. The all-scope exception in Mint applies only to read-only grants.
- Rollout order (#321): a target checks every token against its own build's grant table, and callers sign only the exact duty of each call, so a caller that signs something its target's build or configuration does not know yet gets 401. Always configure and deploy targets first, callers second, in this order: (1) set the target's `serviceIdentity.publicKeys` for each of its callers and apply the target's migration `service_token_replay` (below; a target build with public keys refuses to start without it); (2) roll out the target version that knows the callers' duties (`ledger.entry.post`, `ledger.entry.lookup`, `ledger.ledger.lookup`, `numbering.sequence.allocate`); (3) only then deploy the callers' versions and signing-key Secrets. Caller to target pairs: receiving to ledger, close, purchasing and inventory; payables to ledger and fx; party to numbering; batch to product; workflow-ts to payables; close to ledger (close also needs `ledgerUrl`, `LEDGER_URL`). Payables is both a target (of workflow-ts) and a caller, so it goes after ledger and fx and before workflow-ts; close likewise goes after ledger and before receiving. Party is a target of receiving (vendor lookup, #354) and payables (bank reveal), so it goes after numbering and before receiving and payables; set its `serviceIdentity.publicKeys` and apply `service_token_replay` first. The payables to tax grant is seeded, but tax does not verify service tokens yet. Roll back in the reverse order, callers first.
- Replay memory has two layers. Each process keeps an expiry heap capped by `PASSAGE_SERVICE_REPLAY_CACHE_SIZE` (default 100000, sized for about 1700 tokens/s per pod over the 60s lifetime; a full cache rejects). Every target that has a database (ledger, close, numbering, purchasing, inventory, fx, product, payables, party) also records each accepted `iss:jti` in its own table `service_token_replay` (tenant-scoped, one migration per service identical to `dbx.ServiceTokenReplayDDL`, a test keeps them equal), where an insert conflict means another replica already accepted the token, so a captured token cannot be replayed on a second pod within its 60s life. The store fails closed: a database error refuses the token with a retryable 503 `COM-0503` (`Retry-After: 1`, so callers do not treat it as an auth fault) and is logged and counted (`passage_service_token_replay_store_failures_total`; refused replays are `passage_service_token_replays_refused_total`; alert on the first). `tenant.ShareReplayCache(ctx, pool)` runs at startup after migrations and refuses to start when service tokens are enabled (public keys configured) and the table or `service_token_replay_purge()` is missing, so apply the migration before deploying a target build. Row-level security is enabled but not forced on the table (allowlisted in `tools/rlscheck`): `passage_app` may only insert under the tenant policy and call the `SECURITY DEFINER` purge, which deletes every tenant's expired ids and runs at most once a minute per process. mTLS between pods remains the follow-up.
- Every accepted token is logged (`service call`: caller, end-user actor, legal entity, path, correlation id).
- With no signing key a caller keeps forwarding the user's own headers (previous behaviour) for reads (receiving to purchasing and inventory, payables to fx, payables to ledger); state-changing calls (ledger posts, plan row settlement, payment runs, numbering allocation) refuse to send unsigned. A malformed key stops startup.
