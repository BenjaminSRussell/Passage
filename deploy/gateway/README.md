# API gateway (Envoy Gateway)

Part of #82 (item b). Services trust the `X-Passage-*` identity headers read by `platform/go/tenant` and `platform/go/authz`, so the gateway must be the only source of them. Live enforcement proof is tracked on #213.

Requires Envoy Gateway v1.4 or newer: `localJWKS` on the JWT provider and `shared` on rate-limit rules do not exist before it. The CRDs for v1.4.0 (Gateway API `GatewayClass`, `Gateway`, `HTTPRoute`; Envoy Gateway `ClientTrafficPolicy`, `SecurityPolicy`, `BackendTrafficPolicy`) are vendored in `deploy/third_party/envoy-gateway-v1.4.0/crds.yaml` (Apache-2.0, extracted from the v1.4.0 `install.yaml`) and the manifests are validated against them with kubeconform.

## Request path

1. `ClientTrafficPolicy/passage-api-strip-identity-headers` removes `X-Passage-Tenant`, `-Legal-Entity`, `-LegalEntity`, `-User`, `-Duties`, `-Tier` and `-Service-Token` in `earlyRequestHeaders`, before any HTTP filter runs. `X-Passage-LegalEntity-Scope` is the one deliberate pass-through: a client sends `ALL` to ask for the all-entity read view, and `platform/go/tenant` honours it only on GET/HEAD/OPTIONS (and on POST routes a service wraps in `tenant.ReadOnlyPOST`, today analytics query) and only when the JWT-derived `X-Passage-Duties` holds `org.switcher.all-scope`; it grants nothing on its own. A route-level `RequestHeaderModifier` would run after JWT auth and delete the headers the JWT just set, so it is not used.
2. `SecurityPolicy/passage-api-jwt` (targets the Gateway, so every route and any future route is covered) validates the bearer token (issuer, audience `passage-api`, signature from the JWKS) and maps claims to headers: `tid` to `X-Passage-Tenant`, `le` to `X-Passage-Legal-Entity`, `sub` to `X-Passage-User`, `duties` to `X-Passage-Duties`, `tier` to `X-Passage-Tier`. Requests without a valid token get 401. A token whose `tid` is the nil platform tenant in its canonical form (`00000000-0000-0000-0000-000000000000`) is denied here; claim matching is exact-string only, so uppercase or unhyphenated spellings are not matched at the gateway. `platform/go/tenant` canonicalizes and rejects them (#257).
3. `BackendTrafficPolicy/passage-api-tenant-rate-limit` applies a global per-tenant limit keyed on `X-Passage-Tenant` by tier from `X-Passage-Tier`: starter 600/min, professional 3000/min, enterprise 12000/min. Every rule is `shared: true`, so a tenant's budget is shared across all routes rather than per route. A token with a missing or unknown tier matches the inverted-regex fallback rule and is limited to the starter 600/min (fail closed). Burst allowances (100/500/2000) are not expressible in this API and are not configured.

## Routes and listeners

Each service has an `HTTPRoute` named after it. `/api/v1/<svc>` is rewritten to `/v1/<svc>` (the BFF convention from #199); `/v1/<svc>` passes through for partners and agents. The one exception is the `inbox` route (My work, `GET /v1/inbox`), which is served by the `batch` Service. Health endpoints are not routed. Add a service by adding its HTTPRoute and listing it in the `targetRefs` of the BackendTrafficPolicy (the SecurityPolicy targets the Gateway); `deploy/scripts/test_gateway.py` fails if a route is left out.

The Gateway has two listeners. `https` (443, TLS terminate, Secret `passage-api-tls`, to be issued by cert-manager or supplied by the environment) is the listener for stage and prod. `http-dev` (80) is for dev only; remove it in any non-dev environment.

## AS2 edge (#483)

Trading partners post AS2 messages and asynchronous MDNs to the edi AS2 listener without a Passage token: edi authenticates each request by its AS2 signature against the partner certificate pinned on the transport (see `services/edi/README.md`, "AS2 listener security"). They come in through a second Gateway, `passage-as2`, so the JWT SecurityPolicy, which targets Gateway `passage-api`, cannot apply to them, and the API routes cannot be reached without a token through it:

- `as2-gateway.yaml`: Gateway `passage-as2`, one listener `as2-https` (443, TLS terminate, hostname `as2.dev.passage.dev`, Secret `passage-as2-tls`). No plain-HTTP listener.
- `as2-certificate.yaml`: cert-manager Certificate `passage-as2-tls` for that hostname (RSA 2048, many AS2 stacks lack ECDSA suites), from ClusterIssuer `passage-local-ca` in dev. cert-manager's CRDs are not vendored, so `validate-gateway-schema` skips the Certificate and `test_gateway.py` checks it.
- `as2-httproute.yaml`: HTTPRoute `edi-as2`, the only route on the AS2 Gateway: `POST` with path prefix `/as2/v1/` to Service `edi-as2` port 8081 (the edi chart with `transports.as2.enabled`). Nothing else of edi and no other service is routed there.
- `as2-clienttrafficpolicy.yaml`: TLS 1.2 or newer, and the `X-Passage-*` headers removed in `earlyRequestHeaders` (the listener ignores them anyway).
- `as2-backendtrafficpolicy.yaml`: `requestBuffer.limit: 8Mi`, the listener's own body cap, so oversized bodies get 413 at the edge; and a global rate limit of 600 requests a minute per client address (IPv4 and IPv6, `sourceCIDR` Distinct; same rate-limit service as the tenant limit). Behind it edi keeps a token bucket per AS2 endpoint (`EDI_AS2_RATE_PER_MINUTE`, default 120 with bursts of 60). The per-address limit needs the real client address at Envoy (`externalTrafficPolicy: Local` on the Envoy Service, or PROXY protocol); behind a load balancer that rewrites the source it limits all partners together.

The edi chart's NetworkPolicy admits only the Envoy proxies of `passage-as2` (namespace `envoy-gateway-system`, labels `gateway.envoyproxy.io/owning-gateway-name: passage-as2` and `owning-gateway-namespace: hello-ledger`) to the AS2 port; the API and metrics ports keep their previous reach (#82 item 2). `deploy/envs/dev/values/edi.yaml` turns the listener and the workers on with `EDI_AS2_PUBLIC_URL=https://as2.dev.passage.dev`.

Operations: point DNS for `as2.<env>.passage.dev` at the load balancer address of the `passage-as2` Envoy Service (its own address, not passage-api's). In dev the certificate comes from the local CA, which partners do not trust; for stage and prod set the hostname (`as2.stage.passage.dev`, `as2.prod.passage.dev`, like the hello-ledger hosts) and issue the certificate from a publicly trusted issuer (ACME), or give partners the CA to pin. Partners that allow-list our address need the AS2 Envoy Service's address. The edge has no allow-list of partner addresses: the signature is the authentication.

## Plant edge for iot-edge connectors (#25)

iot-edge connectors redeem a one-time enrollment token without a session and then call the shop floor service with the mTLS client certificate they were issued, so they come in through a third Gateway, `passage-edge` (`edge-gateway.yaml`, `edge-certificate.yaml`, `edge-clienttrafficpolicy.yaml`, `edge-httproute.yaml`), outside the JWT SecurityPolicy:

- The listener (`edge-https`, 443, hostname `edge.<env>.passage.dev`) asks for a client certificate but does not require one (`clientValidation.optional`): a connector with no certificate yet may call only `POST /v1/shopfloor/edge-nodes/{id}:enroll`, whose body token is its credential. A certificate that is presented must chain to the edge CA in Secret `passage-edge-ca-trust` (key `ca.crt`, the CA certificate of the shop floor chart's `edgePki` issuer).
- Envoy forwards the verified certificate's subject in `X-Forwarded-Client-Cert` (`SanitizeSet`: built from the verified certificate, a client-sent value is dropped). The shop floor service reads the common name `edge:<node id>`, finds the node's tenant (`edge_node_tenant`, migration shopfloor/0026), and treats the call as that connector with the one connector duty; it still matches the name to the node's bound `connectorSubject`. A request that already carries a tenant is left alone.
- The only route, `shopfloor-edge`, exposes what a connector calls (`:enroll`, `:renew-certificate`, `:heartbeat`, `GET .../config`, `GET .../control-recipes`, `POST .../control-recipes/{rid}:report` and `POST /v1/shopfloor/machine-events`) and nothing else of the shop floor service; `test_gateway.py` checks the matches against the paths the service serves and the connector calls. Enforcement against a live Envoy is #213, and a rate limit on the public redeem route is open.

## Dev JWKS and claim contract

`passage-dev-jwks` holds a static placeholder public key (kid `passage-dev-placeholder`); no private key is kept, so nothing can mint accepted tokens until #80 supplies an IdP. To switch to the IdP, replace `localJWKS` in the SecurityPolicy provider with `remoteJWKS: {uri: https://<idp>/realms/<realm>/protocol/openid-connect/certs}` and set `issuer` to the realm URL. Realm-per-tenant needs one provider per realm.

`duties` must be a single string claim holding the comma-joined duty names (for example `ap_clerk,approver`), because `tenant.go` splits `X-Passage-Duties` on commas. Envoy base64-JSON-encodes array claims when copying them to a header, so a string array breaks parsing. In Keycloak, use a "Hardcoded claim" or script mapper that emits one string (JSON type String, multivalued off); do not use the multivalued "User Realm Role" style mapper.

## Assumptions to confirm with #80 and #213

- Claim names `tid` (matches `services/identity/jwt.go`), `le`, `duties`, `tier` are the Keycloak mapper outputs.
- The Envoy Gateway v1.4+ install (#213) provides the CRDs, `ClientTrafficPolicy.headers.earlyRequestHeaders` support, and a global rate-limit service backed by Valkey. The Argo CD app `deploy/envs/dev/apps/gateway.yaml` is annotated `passage.dev/requires` and uses `SkipDryRunOnMissingResource` so it can sync once the CRDs exist.
- Services are still reachable inside the cluster without the gateway; restricting that is item 2 of #82.
- Host-to-tenant matching (a request host must resolve to the token's tenant) is deferred until the tenant registry in #83 exists.

## Tests

`make -C deploy test-gateway` first validates the rendered kustomization against the vendored CRDs with `kubeconform -strict` (`go install github.com/yannh/kubeconform/cmd/kubeconform@v0.6.7`), then runs `scripts/test_gateway.py` with `kubectl kustomize`: header removal covers every header in `tenant.go` plus the explicit list, the SecurityPolicy targets the Gateway, rate-limit rules are shared, keyed on tenant, with the 600/min fallback, the TLS listener, and the `/api` rewrite. For the AS2 edge it checks that every HTTPRoute attaches to exactly one Gateway, that only `edi-as2` attaches to `passage-as2`, that the JWT SecurityPolicy targets the whole `passage-api` Gateway and no policy reaches the AS2 Gateway or route, that the AS2 route is `POST /as2/v1/` to `edi-as2` on the chart's port with the listener's hostname, the Certificate's DNS name and Secret, TLS 1.2, the stripped headers, the 8Mi buffer equal to `maxAS2Body` in `services/edi/internal/api/as2in.go`, the per-address rate limit, and the edi chart's gateway labels. `services/edi/charts/edi/test-as2.sh` (CI `charts` job) renders the chart and checks that the AS2 port admits only those proxies. It needs `pyyaml`.

## Service tokens

Decision (#226): signed service-principal tokens now, SPIFFE/mTLS later. A service that calls another no longer forwards the end user's duties; it sends `X-Passage-Service-Token`, an Ed25519-signed token (`platform/go/tenant/service.go`) with claims `iss` (caller), `aud` (target), `tid`, `le` (one explicit legal entity), `act` (the end user, which the target records as the actor), `duties` (the caller's own grant for that target), `iat`, `exp` (at most 60 seconds) and `jti`. The target's middleware replaces every user header with the token's principal; an invalid, expired, mis-addressed, replayed or over-granted token is a 401, never a fallback to user headers.

- Grants are static: `policies/authz/data.json` `service_grants` (caller, then target, then duties), mirrored in `tenant.serviceGrants` and kept equal by a test. Today: receiving to ledger (`ledger.entry.post`, `ledger.journal.reverse`), receiving to close (`period.check`), close to ledger (`ledger.ledger.lookup`, `ledger.entry.post`, `ledger.journal.reverse`, `ledger.balance.read`, `ledger.account.lookup`, and the flag `ledger.period.postclosed`, the one flag duty any grant holds, which close signs only on the closing entry of a year-end run and on the reversals of a re-run), receiving to purchasing (`procurement.invoicing-plan.settle`, #289; `procurement.purchase-order.lookup`, #305), receiving to inventory (`inventory.ownership-change.read`, #305), payables to ledger (`ledger.balance.read`, `ledger.ledger.lookup`, `ledger.entry.lookup`, `ledger.entry.post`), costing to ledger (`ledger.entry.post`, `ledger.balance.read`, `ledger.ledger.lookup`; PPV vouchers, close adjustment and the inventory tie-out), payables to fx (`fx.rate.lookup`, #305), payables to tax (`tax.withholding.calculate`, #350), payables to party (`party.vendor-bank.reveal`, #352), receiving to party (`party.read`, #354), party to numbering (`numbering.sequence.allocate`), hr to numbering (`numbering.sequence.allocate`, requisition numbers; set numbering's `serviceIdentity.publicKeys` for hr first), hr to compliance (`compliance.legal-hold.check`, candidate retention purge #266; set compliance's `serviceIdentity.publicKeys` for hr first), batch to product, workflow-ts to payables (`payment-run.execute`), workflow-ts to engineering (`engineering.eco.workflow`, service-only: `:approve`, `:reject`, `:cancel` and `:release` of an ECO, never a person), workflow-ts to quality (`quality.capa.execute`), workflow-ts to transport (`transport.tender.execute`, service-only: tender start, read and expiry sweep; transport also requires the token issuer to be `workflow-ts`) and workflow-ts to party (`party.approve`, #426: `:approve` and `:reject` of a pending change, signed for the approver the workflow-ts decision route authenticated; party still refuses the requester; set party's `serviceIdentity.publicKeys` first; and the service-only `party.merge.execute`, #450: `:approve` and `:reject` of a merge request, in a tenant-level token that names no legal entity and carries no other duty). Duties marked `service_only` in the catalogue are never assignable to a person and are named as the `duty_missing` hint only on routes no person duty grants; a read route accepts either its human duty or the service duty (`RequireAnyDuty`), and callers sign only the exact duty of each call (`ApplyDuties`).
- No umbrella grants (#341): the grant tables hold only the narrow duties. The umbrella ones kept for the 0.1.0 rolling deploy (`ledger.journal.post` and `ledger.journal.read` for receiving and payables to ledger, `numbering.write` for party to numbering, #321, #333) are removed, so a token that still carries one is over-granted and gets 401. Every caller has signed only the narrow duties since #333.
- The gateway strips the header from clients (`ClientTrafficPolicy`), so only in-cluster callers holding a signing key can present one.
- The legal entity is explicit and bound to the end user: `Mint` refuses an entity outside the user's `LegalEntityScopeList` (or any entity for a no-entity ALL-scope read), so a service cannot act in an entity the user could not.
- Grants are one route per duty. Service-only duties: `numbering.sequence.allocate` (`POST .../next`; `numbering.write` still also covers creating a sequence), `ledger.entry.post` (`POST /journal-entries`), `ledger.entry.lookup` (`GET /journal-lines`, which takes a `documentId` filter), `ledger.ledger.lookup` (`GET /ledgers/{id}`). Person duties `ledger.entry.validate`, `ledger.batch.post` and `ledger.set.post` open `/validate`, a batch post and a ledger-set post alone; every route also still accepts its umbrella duty (`ledger.journal.post`, `ledger.journal.read`), so existing roles keep working with no assignment change. Services sign only the narrow duties, and the grant tables list only those (#341).
- Callers set `PASSAGE_SERVICE_NAME` and `PASSAGE_SERVICE_SIGNING_KEY_FILE` (a mounted secret holding the base64 32-byte Ed25519 seed; `PASSAGE_SERVICE_SIGNING_KEY` is the inline form) and optionally `PASSAGE_SERVICE_KEY_ID`. Targets set `PASSAGE_SERVICE_NAME` and `PASSAGE_SERVICE_PUBLIC_KEYS` (`caller[:kid]=base64pub,...`, not secret). Several keys per caller (distinct `kid`) allow rotation: add the new public key everywhere, switch the caller's seed and `kid`, then drop the old key. A repeated caller and kid, or a malformed value, stops the target at startup. Charts: targets (ledger, close, numbering, purchasing, inventory, fx, product, payables, party) take `serviceIdentity.publicKeys`; callers (receiving, costing, payables, party, batch, workflow-ts, close) take `serviceIdentity.signingKeySecret` (a Secret with key `signing-key`, mounted read-only at `/var/run/passage/service-identity`, mode 0440 with pod `fsGroup: 65532`) and `serviceIdentity.keyId`. The all-scope exception in Mint applies only to read-only grants.
- Rollout order (#321): a target checks every token against its own build's grant table, and callers sign only the exact duty of each call, so a caller that signs something its target's build or configuration does not know yet gets 401. Always configure and deploy targets first, callers second, in this order: (1) set the target's `serviceIdentity.publicKeys` for each of its callers and apply the target's migration `service_token_replay` (below; a target build with public keys refuses to start without it); (2) roll out the target version that knows the callers' duties (`ledger.entry.post`, `ledger.entry.lookup`, `ledger.ledger.lookup`, `numbering.sequence.allocate`); (3) only then deploy the callers' versions and signing-key Secrets. Caller to target pairs: receiving to ledger, close, purchasing and inventory; payables to ledger and fx; costing to ledger (set the ledger's `serviceIdentity.publicKeys` for costing first, and costing's `ledgerUrl`, `LEDGER_URL`, and signing key); consolidation to ledger (balance read, `ledger.balance.read`) and intercompany to ledger (`ledger.entry.post`, `ledger.journal.reverse`, `ledger.ledger.lookup`), each the same way: the ledger's `serviceIdentity.publicKeys` for the caller first, then the caller's `ledgerUrl` and signing key (without them consolidation cannot collect and intercompany cannot post, and both answer 503 on those routes); party to numbering; batch to product; workflow-ts to payables; close to ledger (close also needs `ledgerUrl`, `LEDGER_URL`); ledger to close (period status, duty `period.check`; ledger also needs `closeUrl`, `CLOSE_URL`, and its signing key, and close needs the ledger public key). Ledger to fx (rates for ledger sets that span currencies, duty `fx.rate.lookup`; optional `fxUrl`, `FX_URL`, which needs the signing key, and fx needs the ledger public key). Payables is both a target (of workflow-ts) and a caller, so it goes after ledger and fx and before workflow-ts; close likewise goes after ledger and before receiving. Party is a target of receiving (vendor lookup, #354) and payables (bank reveal), so it goes after numbering and before receiving and payables; set its `serviceIdentity.publicKeys` and apply `service_token_replay` first. The payables to tax grant is seeded, but tax does not verify service tokens yet. Roll back in the reverse order, callers first.
- Replay memory has two layers. Each process keeps an expiry heap capped by `PASSAGE_SERVICE_REPLAY_CACHE_SIZE` (default 100000, sized for about 1700 tokens/s per pod over the 60s lifetime; a full cache rejects). Every target that has a database (ledger, close, numbering, purchasing, inventory, fx, product, payables, party) also records each accepted `iss:jti` in its own table `service_token_replay` (tenant-scoped, one migration per service identical to `dbx.ServiceTokenReplayDDL`, a test keeps them equal), where an insert conflict means another replica already accepted the token, so a captured token cannot be replayed on a second pod within its 60s life. The store fails closed: a database error refuses the token with a retryable 503 `COM-0503` (`Retry-After: 1`, so callers do not treat it as an auth fault) and is logged and counted (`passage_service_token_replay_store_failures_total`; refused replays are `passage_service_token_replays_refused_total`; alert on the first). `tenant.ShareReplayCache(ctx, pool)` runs at startup after migrations and refuses to start when service tokens are enabled (public keys configured) and the table or `service_token_replay_purge()` is missing, so apply the migration before deploying a target build. Row-level security is enabled but not forced on the table (allowlisted in `tools/rlscheck`): `passage_app` may only insert under the tenant policy and call the `SECURITY DEFINER` purge, which deletes every tenant's expired ids and runs at most once a minute per process. mTLS between pods remains the follow-up.
- Every accepted token is logged (`service call`: caller, end-user actor, legal entity, path, correlation id).
- With no signing key a caller keeps forwarding the user's own headers (previous behaviour) for reads (receiving to purchasing and inventory, payables to fx, payables to ledger); state-changing calls (ledger posts, plan row settlement, payment runs, numbering allocation) refuse to send unsigned. A malformed key stops startup.
