# Keycloak (dev) and the passage realm

Part of #80. `kustomization.yaml` turns `realm-passage.json` into a ConfigMap that Keycloak imports at start (`--import-realm`); `deploy/envs/dev/apps/keycloak.yaml` is the Argo CD app. Secrets are never in the repo: create `keycloak-db` (`url` as a JDBC URL, `username`, `password`) and `keycloak-admin` (`username`, `password`) in the namespace first.

## What the realm pins

- Realm `passage` (identity's tenant registry maps `identity_tenants.realm_name` to `<IDENTITY_SCIM_ISSUER_BASE>/<realm_name>`; one realm per tenant, copy this file and change `realm`).
- RS256 access tokens, 300 s lifespan (identity rejects anything over 10.5 minutes).
- Clients: `passage-web` (public, authorization code with PKCE S256, no direct grants) and `passage-services` (confidential, service account for SCIM and machine callers; its secret is generated by Keycloak on import).
- Mappers on both clients: audience `passage-api`, and the string claims the gateway and `services/identity/jwt.go` read: `tid` (user attribute `tenant_id`), `le` (`legal_entity_id`), `duties` (`duties`, one comma-joined string, never multivalued), `tier` (`tier`).
- MFA: the bound browser flow `passage-browser-mfa` requires username and password, then a REQUIRED second-factor subflow: a CONDITIONAL sub-subflow that demands WebAuthn when the user has a WebAuthn credential, followed by a REQUIRED OTP form. A user with no factor is sent to `CONFIGURE_TOTP` (a default required action) rather than failing, and no path completes on a password alone. WebAuthn user verification is required. Both IdP placeholders set `postBrokerLoginFlowAlias` to `passage-post-broker-mfa`, which applies the same second factor after federated login.
- Network: `networkpolicy.yaml` admits 8080 only from the gateway proxy pods (`envoy-gateway-system`, owning gateway `passage-api`) and from identity pods in the same namespace (token and JWKS). The edge route must expose only `/realms/passage/*` and `/resources/*`; `/admin` and `/realms/master` must be blocked at the gateway.
- `passage-web` redirect URI is the exact `https://app.passage.example.invalid/auth/callback` (the web app has no OIDC callback route yet, so this is the agreed path, patch it per environment); post-logout redirect is `https://app.passage.example.invalid/`.
- Refresh tokens rotate: `revokeRefreshToken` true with `refreshTokenMaxReuse` 0, so a stolen refresh token from the public SPA client dies on first reuse.
- Machine callers: `passage-services` maps `tid`, `le`, `duties` and `tier` from user attributes, and a service account user carries none. Set those attributes on the client's service-account user through the admin API (same admin-only attributes as a person), or the token has no `tid` and identity answers 401. Dedicated hardcoded-claim mappers per tenant are the alternative once tenants get their own realm copy.
- Hostname: `KC_HOSTNAME` in `deployment.yaml` is a placeholder host with `KC_HOSTNAME_STRICT=true`; patch it per environment with a kustomize patch (the CI job runs `start-dev` with strict off).
- Federation placeholders `corporate-oidc` and `corporate-saml`, disabled, hosts at `idp.example.invalid`, no client secret. Set the real endpoints and client secret through the admin API or console and enable them per tenant. Each carries a `tenant` mapper (`hardcoded-attribute-idp-mapper`, sync mode FORCE) that sets `tenant_id` to `REPLACE_WITH_TENANT_ID`: set it to the realm's tenant. The tenant comes from the realm, never from the upstream IdP, and no IdP mapper may write `tenant_id`, `legal_entity_id`, `duties` or `tier`; duties come from Passage role assignments.
- OTP policy is pinned (TOTP, HmacSHA1, 6 digits, 30 s, look-ahead 1, codes single-use); the CI login computes codes with it.

## Tests

`services/identity/keycloak_test.go` and `keycloak_login_test.go`. The realm tests always run and check the export against identity's expectations: audience, the `tid`/`le`/`duties`/`tier` single-string claims (`duties` comma-joined, as apps/web `parseDuties` reads it), token lifespan, the MFA flows (browser and post-broker), the pinned OTP policy, admin-only token attributes, IdP mappers that keep token claims local, and no embedded secrets.

The live tests run only when `PASSAGE_TEST_KEYCLOAK_URL` is set. The `keycloak` job in `.github/workflows/ci.yml` starts `quay.io/keycloak/keycloak:26.0.8` with `docker run` (a `services:` container cannot take the `start-dev --import-realm` arguments) with this realm and a per-run random admin password, then runs `go test -run Keycloak`:

- `TestKeycloakOIDCLoginWithOTPThenDeprovision`: authorization code with PKCE for `passage-web`, password, TOTP enrolment (`CONFIGURE_TOTP`), code exchange; a second login through the OTP form; identity's `JWTVerifier` accepts the token and the duty claims arrive; refresh works; then the user is disabled in Keycloak and both refresh (`invalid_grant`) and a fresh login fail.
- `TestKeycloakFederatedLoginThroughOIDCAndSAMLIdPs`: two Keycloak-to-Keycloak stand-ins (realms `ci-upstream-oidc` and `ci-upstream-saml` in the same server) wired to `corporate-oidc` and `corporate-saml`; each federated login goes through the upstream password form (and the signed SAML POST binding), the post-broker TOTP enrolment, and yields a token identity accepts with `tid` from the tenant mapper, no duties, and a federated-identity link.
- The earlier tests: direct-grant login through `JWTVerifier`, a new user sent to `CONFIGURE_TOTP`, and a password-only login never receiving a code.

All of these were run against a local Keycloak 26.0.8 distribution (`kc.sh start-dev --import-realm`) on 2026-11-05. WebAuthn is not exercised: it needs a browser with a virtual authenticator (Playwright).
